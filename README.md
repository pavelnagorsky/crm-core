# CRM Core

Backend CRM на NestJS, Prisma и PostgreSQL: бренды и филиалы, календарь и бронирования, клиенты, услуги, продажи, склад и зарплата.

## Запуск

Настроить переменные окружения по `.env.example`, затем установить зависимости и подготовить базу:

```sh
npm install
npm run db:deploy
npm run db:generate
npm run start:dev
```

Миграции применяются к `DATABASE_URL` из конфигурации окружения. Для полноценного развёртывания нужны SQL-миграции: `db:push` не создаёт используемые приложением view и collation. Подробности — в [документе каталога](docs/architecture/services-catalog.md#пустая-база-и-восстановление-view).

Swagger UI: `/api`, OpenAPI JSON: `/api-json`. Бизнес-маршруты не имеют общего префикса `/api`.

## Вход через Google

Обычный OAuth и Google One Tap используют `POST /auth/google` с JSON:

```json
{ "type": "oauth", "authCode": "<authorization code>" }
```

```json
{ "type": "one-tap", "oneTapCode": "<credential из Google callback>" }
```

`type` по умолчанию равен `oauth`, поэтому прежние запросы с одним `authCode` продолжают работать. Для One Tap нужно передавать Google ID token из `response.credential`, а не access token. Backend проверяет подпись, срок действия, issuer, audience и подтверждённый email.

В Google Cloud настройте OAuth client типа Web application и разрешённые JavaScript origins frontend. В окружении backend укажите `GOOGLE_CLOUD_CLIENT_ID` и `GOOGLE_CLOUD_CLIENT_SECRET`; frontend должен использовать тот же client ID. One Tap требует только client ID на backend.

Frontend получает authorization code через Google SDK и отправляет его как `authCode`. Backend обменивает код на Google ID token с `redirect_uri: 'postmessage'`. В сценарии One Tap frontend отправляет уже полученный ID token как `oneTapCode`, без обмена кода. Оба сценария завершаются проверкой ID token и выдачей сессии CRM.

Успешный ответ имеет статус `201`, access token в `responseValue.accessToken` и refresh token в HttpOnly cookie. Для браузерного запроса используйте `credentials: 'include'`; origin frontend должен входить в `ALLOWED_ORIGINS`. Некорректное тело запроса возвращает `400`, отклонённый Google token/code — `401`. Создание пользователя и вход по email выполняются существующим `AuthService.handleOAuth` через `UserService`.

## Вход через Yandex и VK

Frontend получает код авторизации через SDK провайдера и отправляет JSON в REST API:

```http
POST /auth/yandex
Content-Type: application/json

{ "authCode": "<authorization code>" }
```

```http
POST /auth/vk
Content-Type: application/json

{ "authCode": "<code>", "state": "<state>", "deviceId": "<device_id>" }
```

Backend обменивает код на access token провайдера, получает профиль с email и вызывает общий `AuthService.handleOAuth`. Ответ и refresh cookie такие же, как при входе через Google; неверный запрос возвращает `400`, ошибки провайдера или отсутствие email — `401`. Токены Yandex и VK не возвращаются клиенту и не сохраняются как токены сессии CRM.

Для Yandex используются существующие `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET`. Приложению нужен доступ к email (`login:email`). Обмен кода идёт через `https://oauth.yandex.ru/token`, профиль — через `https://login.yandex.ru/info`. [Документация Yandex ID](https://yandex.ru/dev/id/doc/ru/user-information).

Для VK используются существующие `VK_CLIENT_ID`, `VK_CODE_VERIFIER` и `DOMAIN`. Frontend передаёт `code`, `state` и `device_id` из SDK callback как `authCode`, `state` и `deviceId`. SDK должен использовать тот же `codeVerifier`, что указан в `VK_CODE_VERIFIER`, и `redirectUrl`, равный `${DOMAIN}/auth/oauth/callback`; адрес должен быть зарегистрирован в VK ID. Frontend проверяет `state` своего входа перед отправкой кода, backend проверяет совпадение `state` в ответе обмена VK. Для получения email приложению нужен scope `email`. [Реализация обмена кода в VK ID SDK](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts).

## Локальный кэш клиентского бронирования

Кэш подключён через `@nestjs/cache-manager` и `cache-manager` со стандартным хранилищем в памяти. Библиотеки отвечают за хранение, TTL, объединение параллельных загрузок и обновление перед истечением TTL. `booking-setup` собирается из компактных данных доменных сервисов; готовые ответы, комбинации фильтров и массивы свободных слотов по датам не сохраняются.

| Данные                                          | Ключ   | TTL / обновление до истечения |
| ----------------------------------------------- | ------ | ----------------------------- |
| Публичный профиль бренда                        | Бренд  | 24 / 2 часа                   |
| Настройки и публичные контакты филиала          | Филиал | 24 / 2 часа                   |
| Категории, услуги и состав комплексов           | Филиал | 24 / 2 часа                   |
| Публичные данные сотрудников и связи с услугами | Филиал | 24 / 2 часа                   |
| Каталог товаров и категории                     | Бренд  | 24 / 2 часа                   |
| Доступные товары и розничные цены филиала       | Филиал | 24 / 2 часа                   |
| Смены активных сотрудников в ограниченном окне  | Филиал | 24 / 2 часа                   |

В расписании хранятся только сотрудник, дата и границы смены. Окно начинается с текущего дня в часовом поясе филиала и соответствует его горизонту бронирования. Запросы вне окна читают смены из БД без создания дополнительных ключей. Смена локального дня делает старое окно непригодным.

Занятость календаря, остатки, права доступа и проверки записи внутри транзакции читаются из БД. Публичные маршруты используют `Cache-Control: no-store`, чтобы браузерный кэш не обходил серверную инвалидацию.

### Подключение и инвалидация

Инфраструктура находится в `src/shared/cache`. Имена пространств ключей собраны в `CacheNamespace`, зависимости для инвалидации — в `CacheDependency`. Типизированные определения `*_CACHE` находятся в `cache/` модуля-владельца: состав идентификатора, зависимости и политика. Ключ формируется централизованно как `namespace:identity`, части составного идентификатора экранируются и разделяются двоеточием. Версионирование ключей не требуется: кэш хранится в памяти процесса и очищается при его перезапуске.

Сервис подключает `AppCacheModule` и использует один API:

```ts
return this.cache.getOrLoad(
  SERVICE_CATALOG_CACHE,
  { brandId, locationId },
  () => this.loadSnapshot(locationId),
);
```

Загрузчик принадлежит домену и выбирает только нужные поля через Prisma `select`. Общие данные хранятся один раз: например, товары бренда отдельно от цен филиала, услуги отдельно от ссылок на них в комплексах. Возвращаемые значения копируются с сохранением `Date` и `Prisma.Decimal`, чтобы вызывающий код не мог изменить содержимое кэша.

Каждая запись в БД инвалидирует соответствующую зависимость **после успешного commit**, до аудита и других побочных действий:

```ts
await this.db.$transaction(/* domain operation */);
await this.cache.invalidate(CacheDependency.serviceCatalog(locationId));
```

`AppCacheService` добавляет к библиотечному `wrap` доменные зависимости и проверку актуальности. Для каждой изменённой зависимости хранится номер последней инвалидации, а у значения — номер на момент начала загрузки. Перед возвратом проверяется, не менялась ли хотя бы одна зависимость за это время. Это защищает и от старого результата загрузки, и от фонового обновления, завершившегося после записи в БД, без hooks и обхода внутреннего хранилища.

Инвалидация логическая: зависимое значение сразу перестаёт быть пригодным для выдачи, а физически заменяется при следующем чтении. Удаление бренда или филиала инвалидирует дочерние наборы по зависимости жизненного цикла. Метки инвалидации живут в текущем процессе; ключи данных не содержат номера ревизий. Независимые наборы продолжают использоваться.

Если полученная запись уже неактуальна, выполняется одна перезагрузка через `wrap`. Если и её пересекло изменение зависимости, запрос читает БД без сохранения результата в кэш. Ошибки загрузчика не повторяются автоматически. Эта проверка предотвращает выдачу инвалидированных данных из кэша, но не превращает несколько доменных чтений в общую транзакцию: критические проверки бронирования остаются внутри транзакции записи.

### Заполнение по запросу

Кэш заполняется только при обращении к соответствующим данным через `getOrLoad`. При запуске приложения, создании и изменении филиала загрузка кэша не выполняется; периодического обхода филиалов нет. Первый запрос при отсутствии, истечении срока или инвалидации значения ждёт чтения из БД, параллельные обращения к одному ключу объединяются средствами `cache-manager`.

TTL всех наборов — 24 часа, окно фонового обновления — последние 2 часа. Обновление запускается при чтении действующего значения в этом окне: запрос получает сохранённое значение, а загрузчик обновляет его в фоне. Без обращений данные не обновляются. Актуальность после изменений обеспечивает немедленная инвалидация; TTL служит дополнительным сроком обновления. Расписание также проверяется на соответствие текущему локальному дню независимо от TTL. Ошибка фонового обновления не удаляет ещё действующее значение, но истёкшие и инвалидированные данные не выдаются.

Дополнительных ограничений количества записей, размера значения и числа смен нет. Структура кэша следует домену: один набор на бренд или филиал, а не на каждую комбинацию аргументов запроса.

Политики TTL заданы в определениях кэша и `cache-policies.ts`. Единственная переменная окружения — `CACHE_ENABLED`, по умолчанию `true`. Значение `false` отключает кэш и фоновые обновления для локального профилирования. После инвалидации, сбоя обновления или запроса вне окна чтение из БД всё ещё возможно.

Инвалидация действует только внутри текущего процесса. Несколько экземпляров приложения, внешние SQL-изменения и отдельные процессы записи требуют общего механизма инвалидации; до его появления такой режим нужно запускать с отключённым кэшем.
