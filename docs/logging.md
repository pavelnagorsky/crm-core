# Логи приложения

После деплоя файлы доступны на VPS в `/opt/crm-core/logs` (или `DEPLOY_PATH/logs`,
если путь деплоя изменён). Папка подключена к контейнеру, поэтому пересоздание
контейнера при деплое не удаляет историю. Внутри приложения путь — `/app/logs`.

## Как посмотреть через ispmanager

В файловом менеджере открыть папку логов:

- `app.log` — все сообщения: успешные операции, предупреждения и ошибки.
- `errors.log` — только `ERROR` и `FATAL`, включая stack trace.
- `archive/` — предыдущие файлы, сжатые в gzip. Скачать и распаковать для просмотра.

Сначала найти ошибку по времени в `errors.log`, скопировать её `requestId`,
затем найти этот ID в `app.log`: будут видны сообщения сервисов и результат HTTP-запроса.
Ожидаемые отказы, например OAuth без email или недоступный слот, записываются как `WARN`
в `app.log` и не попадают в `errors.log`.

```text
[2026-11-04 12:42:10.123 UTC] WARN: [YandexOAuthStrategy] requestId=abc oauth failed: provider=yandex reason=EMAIL_MISSING_OR_INVALID
[2026-11-04 12:42:10.125 UTC] WARN: [HTTP] requestId=abc POST /auth/yandex status=401 duration=142ms
```

Время в файлах — **UTC**, то есть на 3 часа меньше времени Минска.
HTTP-ответы содержат заголовок `X-Request-Id`, доступный фронтенду через CORS.
Корректный входящий ID (до 64 букв, цифр, `_`, `-`, `.`) сохраняется;
при отсутствии или некорректном значении генерируется UUID. Этот ID служит для поиска,
а не для идентификации пользователя.

Контекст запроса автоматически доступен существующим NestJS-логгерам сервисов.
Задачи cron и сообщения вне HTTP-запроса пишутся без `requestId`.

## Хранение и доступ

Ротация выполняется приложением, отдельный cron или logrotate не нужен:

- ежедневно в 00:00 UTC и при достижении 20 МБ;
- до 14 архивов **для каждого** файла, старейшие удаляются автоматически;
- при высокой активности 14 архивов могут покрывать меньше 14 дней;
- текущие файлы дополняются при перезапуске приложения;
- файлы `*.history` служебные: нужны для ограничения числа архивов, их не удалять отдельно.

Логи также выводятся читаемым текстом в Docker stdout. Workflow ограничивает
эту дополнительную копию тремя файлами по 20 МБ.

Приложение работает с UID/GID 1000 (`node` в контейнере), директория имеет права 750,
файлы — 640. Если пользователь ispmanager не имеет доступа к этой директории,
администратор должен выдать ему чтение. Например, при наличии POSIX ACL:

```bash
# Вместо panel-user указать системного пользователя панели.
sudo setfacl -R -m u:panel-user:rX /opt/crm-core/logs
sudo setfacl -m d:u:panel-user:rX /opt/crm-core/logs
sudo setfacl -m d:u:panel-user:rX /opt/crm-core/logs/archive
```

Последняя команда нужна, если `archive/` уже существует. Для новой директории
архива ACL наследуется от `logs/`. Папку логов не размещать внутри публичного web-root.

## Настройки

- `LOG_LEVEL=info` — обычный режим. Также поддерживаются `trace`, `debug`, `warn`,
  `error`, `fatal`, `silent`.
- `LOG_DIRECTORY=logs` — локальная директория. Workflow устанавливает `/app/logs`
  и подключает к ней постоянную папку VPS.

HTTP-логгер не записывает заголовки, тела запросов и query-параметры.
Ошибка выводится с сообщением и stack trace, без дополнительных полей HTTP-клиента.
В новых сообщениях сервисов нельзя помещать пароли, OAuth-коды, токены или тела запросов.
