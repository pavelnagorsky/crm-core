# Деплой

Workflow: `.github/workflows/deploy.yml`.

| Ветка | Назначение |
| --- | --- |
| `development` | ежедневная работа |
| `stage` | push выкатывает стейдж (окружение GitHub `stage`) |
| `main` | прод: workflow добавим позже, окружение `production` с теми же именами секретов |

## Как работает

1. `checks` и `image` идут параллельно. `checks`: `prisma validate`, lint, typecheck, тесты, сборка.
   `image`: собирает образы и кладёт в GHCR: `ghcr.io/pavelnagorsky/crm-core:<sha>` (runtime) и
   `:<sha>-migrate` (Prisma CLI для миграций).
2. `deploy` (после обоих): rsync копирует на сервер `compose.yaml`, `docker/` и `scripts/deploy/`,
   затем по SSH запускает `scripts/deploy/deploy.sh`. Сервер ничего не собирает, только скачивает образы.
3. `deploy.sh`: скачивает образы (вход в GHCR токеном этого запуска, во временный docker config),
   применяет миграции, поднимает инфраструктуру, перечитывает конфиг `lb`, без простоя заменяет
   реплики API (`scripts/deploy/rollout.sh`), перезапускает `worker`. После успеха пишет
   `IMAGE_TAG=<sha>` в `.env` и оставляет 3 последних релиза образов.
4. Если новая реплика не стала `healthy` за 180 с, rollout печатает её логи, удаляет новые реплики
   и падает; старые продолжают работать на предыдущей версии.

Повторить деплой: Actions - Deploy - Run workflow на ветке `stage`.

Откат на прошлый релиз (на сервере, `<sha>` из `docker images ghcr.io/pavelnagorsky/crm-core`):

```bash
cd /opt/klendo-core
IMAGE_TAG=<sha> bash scripts/deploy/deploy.sh
```

Образы уже лежат на сервере, вход в GHCR не нужен. Миграции не откатываются (см. ниже).

## Стек Docker Compose

Описание стека - `compose.yaml` в корне. Сервисы:

| Сервис | Назначение |
| --- | --- |
| `api` | HTTP API (`APP_ROLE=api`, без кронов). Число реплик - `API_REPLICAS` в `.env` сервера (стейдж - 1, прод - 2-3). `lb` находит все реплики по DNS-имени `api` |
| `worker` | Кроны (`APP_ROLE=worker`), тот же образ |
| `lb` | nginx, балансировщик на `127.0.0.1:${APP_PORT:-3000}`; лимиты по IP; хостовый nginx (TLS) проксирует на него |
| `redis` | Кэш, счётчики rate limit, блокировки кронов |
| `loki`, `alloy`, `grafana`, `prometheus`, экспортеры | Логи и метрики (Grafana на `127.0.0.1:3200`, только через SSH-туннель) |
| `migrate` | Одноразовый: применяет миграции |
| `postgres` | Только локально (профиль `local`); на сервере БД снаружи, адрес в `DOCKER_DATABASE_URL` |
| `backup` | Ежедневный `pg_dump` в приватный бакет GCS (профиль `backup`): [бэкапы](backups.md) |

Образ приложения: локально `klendo-core:local` (собирается compose), на сервере
`${CORE_IMAGE}:${IMAGE_TAG}` из GHCR. Контейнеры видят Postgres хоста как `host.docker.internal`
(`extra_hosts: host-gateway`).

Логи приложения идут в stdout и собираются в Loki. Как искать ошибку по `requestId` - в
[инструкции по логам](logging.md).

- Пользователь деплоя должен состоять в группе `docker` и владеть `/opt/klendo-core`.

## GitHub Environment `stage`

| Имя | Тип | Значение |
| --- | --- | --- |
| `DEPLOY_SSH_KEY` | secret | приватный ключ пользователя деплоя |
| `DEPLOY_KNOWN_HOSTS` | secret | проверенные строки `ssh-keyscan` сервера |
| `ENV_FILE` | secret | всё содержимое `.env.stage` (секреты бэкенда, `CORE_IMAGE`) |
| `DEPLOY_HOST` | variable | адрес сервера |
| `DEPLOY_USER` | variable | пользователь деплоя |
| `DEPLOY_PORT` | variable | необязательно, по умолчанию `22` |
| `DEPLOY_PATH` | variable | необязательно, по умолчанию `/opt/klendo-core` |

Токен GHCR не нужен: деплой передаёт на сервер `GITHUB_TOKEN` своего запуска (`packages: read`).

## Файлы окружений

Compose читает только `.env` в каталоге проекта. Код и `compose.yaml` одинаковые, окружения
различаются содержимым `.env`.

| Файл | Где живёт | В git |
| --- | --- | --- |
| `.env.example` | репозиторий | да: шаблон со всеми переменными, без секретов |
| `.env` | у разработчика и на каждом сервере | нет |
| `.env.stage`, `.env.production` | у владельца и в менеджере паролей; содержимое - секрет `ENV_FILE` окружения GitHub | нет |

Каждый деплой записывает `.env` на сервер из секрета `ENV_FILE` (весь файл целиком), затем `deploy.sh`
дописывает `IMAGE_TAG`. Поменять настройку: обновить секрет и перезапустить деплой.
Новая переменная в коде - сразу в `.env.example` и в оба серверных файла.

## Миграции

**Миграции обязаны быть совместимы с предыдущей версией кода.** Во время замены реплик
(и при неудачном деплое, остановившемся посередине) несколько минут одновременно работают
старый и новый код на уже применённой новой схеме. Поэтому деструктивные изменения
(удаление и переименование колонок и таблиц, ужесточение `NOT NULL`, смена типов) делаются
в два релиза: сначала код перестаёт использовать поле, в следующем релизе миграция его
удаляет. Автоматического отката БД нет.

## Письма и очередь задач (pg-boss)

Все письма пишутся в журнал (`EmailMessage`) и отправляются через pg-boss. Он хранит задачи в
схеме `pgboss` той же БД и при старте сам создаёт и мигрирует её. Пользователю из `DATABASE_URL`
нужно право `CREATE` на базу. Если его нет, один раз создать схему вручную:
`CREATE SCHEMA pgboss AUTHORIZATION <user>;`. Prisma эту схему не видит и не трогает.

- Если очередь не стартовала, приложение всё равно работает: письма копятся в журнале, очередь
  пытается подняться каждые 30 с и забирает их. В админке это видно как статус `DOWN`.
- Пул pg-boss - до 3 соединений сверх пула Prisma (см. [соединения с БД](#соединения-с-бд)).
- При остановке письма, которые уже отправляются, дописываются. Прерванная попытка повторится
  через ~2 минуты.
- SMTP: `SMTP_HOST` (по умолчанию `smtp.hoster.by`), `SMTP_PORT` (465 - TLS сразу, другие -
  STARTTLS), логин `EMAIL` / `EMAIL_PW`.
- Журнал, повтор и отмена писем, проверка SMTP - в админке, API `/admin/notifications/emails`
  ([frontend-email-notifications.md](frontend-email-notifications.md)).

`.dockerignore` исключает из контекста сборки локальные зависимости, сборку,
Git, `.env` и ключи. Конфигурация и секреты передаются только при запуске.

## Соединения с БД

Каждый процесс держит пул Prisma размером `DATABASE_POOL_SIZE` (по умолчанию 10) и пул pg-boss
на 3 соединения. Итого:

```
(2 api + 1 worker) × (10 Prisma + 3 pg-boss) = 39 соединений + миграции
```

Стандартный `max_connections = 100` в PostgreSQL - с запасом. При увеличении
`DATABASE_POOL_SIZE` или числа реплик пересчитать по этой формуле.
