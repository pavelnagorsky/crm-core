# Frontend: управление ролями и выдачей доступа

Контракты проверены по backend на 2026-10-18. Здесь описана интеграция управления доступом: экраны, выдача роли, изменение назначения, отзыв, приглашения и настройки permissions. Ограничения обычных разделов CRM остаются в [модели ролей](./architecture/rbac.md) и [карте API](./architecture/rbac-permissions-map.md).

## 1. Какие экраны сделать

Рекомендуемый интерфейс — раздел **«Настройки → Доступы»** с выбранным брендом и областью «Весь бренд» / «Филиал». Внутри три независимые вкладки:

| Вкладка | Назначение | Основные действия |
| --- | --- | --- |
| **Участники** | Существующие назначения аккаунтов | Пригласить, изменить роль, отозвать конкретное назначение |
| **Приглашения** | Ссылки, по которым доступ ещё выдаётся или уже выдан | Создать, скопировать новую ссылку, перевыпустить, отозвать |
| **Права ролей** | Шаблоны действий для MANAGER/STAFF | Изменить разрешённые настройки роли, сбросить overrides |

Дополнительно нужен маршрут **`/invitation`** для получателя ссылки: предпросмотр → вход/регистрация → явное принятие → переход в CRM.

Из карточки сотрудника добавить вход «Выдать доступ»: филиал и профиль уже выбраны, роль STAFF. Это открывает тот же диалог приглашения, а не отдельный старый staff-invitation API.

Это предложение по расположению экранов. Backend уже реализует перечисленные ниже операции, но не задаёт layout и названия frontend-маршрутов, кроме формируемой ссылки `/invitation#token=...`.

Назначение готовой роли работает без настройки отдельных permissions. Вкладка «Права ролей» — дополнительная возможность владельца; не включать её в обязательный процесс приглашения сотрудника.

## 2. Термины и области

| Сущность | Что означает |
| --- | --- |
| Аккаунт, `userId` | Пользователь, который входит в приложение |
| Рабочий профиль, `staffId` | Сотрудник филиала: расписание, услуги, история работы. Может существовать без аккаунта |
| Назначение, `membershipId` | Одна прямая роль аккаунта в бренде или филиале |
| Grant приглашения | Будущее назначение роли; станет membership после принятия |
| Политика роли | Разрешённые/запрещённые действия для MANAGER или STAFF в области |

Фиксированные роли: OWNER — владелец, MANAGER — управляющий, STAFF — сотрудник. Пользовательских ролей и персональных permission-исключений API не создаёт.

- В бренде назначаются OWNER/MANAGER; STAFF бренда запрещён.
- В филиале назначаются OWNER/MANAGER/STAFF. Для STAFF обязателен активный рабочий профиль именно этого филиала.
- Роль бренда действует во всех его активных филиалах, включая будущие. Роль филиала действует только в нём.
- Прямая роль филиала добавляет права к унаследованным. Нельзя снизить права брендового MANAGER, назначив ему локального STAFF или запретив действие в локальном шаблоне.
- Один аккаунт может иметь разные роли в разных филиалах и одновременно роль бренда. На аккаунт и область допускается одно прямое membership.
- Назначение роли и изменение шаблона — разные действия: смена роли меняет доступ выбранного человека, шаблон действует на соответствующие назначения роли.

В `/users/me/access` управление доступом проверяется через **B** для бренда и **L** для филиала. `sharedPermissions` (**G**) относится к общим клиентам/товарам и не используется для администрирования ролей.

## 3. Кому показывать вкладки и кнопки

Загрузить `GET /users/me/access`. Ответ в `responseValue` содержит `platformAdmin` и `scopes`. Для B найти строку с нужным `brandId` и `locationId: null`; для L — строку нужного филиала. Проверять массив `permissions`. Готовые scoped permissions уже учитывают наследование; не вычислять их из названия роли.

| Операция | Нужное право в целевой области |
| --- | --- |
| Выдать/изменить/отозвать STAFF | `access.staff.manage` в L филиала |
| Выдать/изменить/отозвать MANAGER | `access.manager.manage` в B бренда или L филиала |
| Выдать/изменить/отозвать OWNER | `access.owner.manage` в B бренда или L филиала |
| Читать/менять/сбрасывать шаблон прав | `access.policy.manage` в B бренда или L филиала |

Смена роли требует прав **на старую и новую роль** в той же области. Поэтому разрешение управлять STAFF не позволяет понизить MANAGER до STAFF или повысить STAFF до MANAGER.

| Пользователь при defaults | Участники и приглашения | Права ролей |
| --- | --- | --- |
| OWNER бренда | Все допустимые роли бренда и его филиалов | Бренд и его филиалы |
| OWNER филиала | Все роли своего филиала; не брендовые назначения | Свой филиал |
| MANAGER бренда | STAFF во всех доступных филиалах бренда | Закрыто |
| MANAGER филиала | STAFF этого филиала | Закрыто |
| STAFF | Закрыто | Закрыто |
| Платформенный ADMIN | Административный доступ | Административный доступ |

`access.staff.manage` у MANAGER настраивается, поэтому таблица defaults не заменяет проверку фактических permissions.

Практические предикаты:

- Раздел «Доступы» видим, если есть хотя бы одно из четырёх прав выше в выбранной области или в доступном филиале бренда.
- «Участники» и «Приглашения» видимы при хотя бы одном `access.*.manage` для роли в соответствующей области. Один `access.policy.manage` сам по себе не разрешает списки участников.
- «Права ролей» видима только при `access.policy.manage` в **текущей** области. Управляющему не показывать пустую/заблокированную вкладку.
- «Пригласить» показывает только разрешённые сочетания роли/области. В бренде никогда не предлагать STAFF.
- Для каждой строки «Изменить роль» и «Отозвать» проверяются её собственные роль и область. Для нового значения роли проверяется также новое permission.
- `platformAdmin: true` обходит permission-проверки. Пустой `scopes` у ADMIN не означает отсутствие доступа; списки брендов/филиалов брать из соответствующих API.

Прямую ссылку на закрытую вкладку обрабатывать экраном «Нет доступа». Пока контекст загружается, не показывать защищённые действия.

## 4. Вкладка «Участники»

### Списки и реальные поля

```http
GET /brands/:brandId/access/memberships?page=1&pageSize=25
GET /locations/:locationId/access/memberships?page=1&pageSize=25
```

Данные `responseValue`:

```ts
type MembershipList = {
  items: Array<{
    id: string;
    userId: string;
    brandId: string;
    locationId: string | null;
    role: 'OWNER' | 'MANAGER' | 'STAFF';
    createdAt: string;
    updatedAt: string;
  }>;
  version: number;
  page: number;
  totalItems: number;
  totalPages: number;
  isExport: boolean;
};
```

Важные особенности текущего API:

- **Брендовый список включает и прямые назначения бренда, и доступные для администрирования назначения его филиалов.** Филиальный список содержит только прямые назначения указанного филиала.
- Сервер выдаёт только назначения, которыми вызывающий вправе управлять. MANAGER не получает OWNER/MANAGER-строки как список «только для чтения».
- Это список назначений, а не уникальных людей. Один `userId` может встретиться несколько раз. Если объединять их в одну карточку, сохранить отдельные ID и действия каждого назначения.
- Для изменения/удаления строки выбирать URL по `row.locationId`: `null` → бренд, значение → соответствующий филиал. Получение строки в брендовом списке не делает её брендовым назначением.
- Наследуемые роли не создают дополнительные membership-строки в филиальном списке. Не рисовать для них выдуманный membershipId.
- `version` — общая версия доступа бренда, не версия одной строки. Хранить её вместе с загруженным списком.
- В DTO нет имени, email, аватара, staffId и platform-role пользователя. Имя/контакт можно дополнить из уже разрешённых данных сотрудника по `userId`; у OWNER/MANAGER рабочего профиля может не быть. Для таких аккаунтов доступен только идентификатор. Полноценная таблица имён всех участников потребует расширения backend; endpoint поиска произвольных аккаунтов здесь не реализован.
- `/users/me/access` описывает только текущий аккаунт. Запрашивать через него effective permissions другого участника нельзя.

Колонки для доступного контракта: «Аккаунт/сотрудник», «Роль», «Область», «Дата назначения», «Действия». Для локальной строки подписывать название филиала по загруженному справочнику.

`page` по умолчанию 1, `pageSize` 25; `isExport=true` возвращает все доступные строки. Хотя общий DTO принимает `orderBy`/`orderDirection`, этот controller их не применяет: назначения сортируются по ID. Поля server-side поиска по имени/email/роли отсутствуют. Query `locationId` используется списком приглашений; для списка участников выбирать нужный URL, а не рассчитывать на такой фильтр.

### Изменение роли

```http
PATCH /locations/:locationId/access/memberships/:membershipId
Content-Type: application/json
```

```json
{
  "role": "STAFF",
  "staffId": "<uuid-active-staff-in-this-location>",
  "expectedVersion": 7
}
```

Для роли MANAGER/OWNER `staffId` не отправлять. Для любого PATCH с целевой STAFF профиль обязателен, в том числе если роль уже STAFF. В брендовом PATCH поле STAFF недопустимо.

Успех: `BaseResponseDto<{ id: string }>`. Перечитать списки и версии; если менялся текущий аккаунт, обновить JWT и контекст. Повышение STAFF до MANAGER сохраняет рабочий профиль. Для понижения до STAFF выбрать профиль этого филиала, свободный или уже связанный с тем же аккаунтом. Профиль другого аккаунта и второй профиль того же аккаунта в одном филиале сервер отклонит.

### Отзыв

```http
DELETE /locations/:locationId/access/memberships/:membershipId
If-Match: 7
```

Для брендового назначения использовать `/brands/:brandId/access/memberships/:membershipId`. `If-Match` содержит числовую версию из списка, например `7` или `"7"`. Успех — 204, JSON не читать.

Подтверждение: «Отозвать назначение STAFF в филиале …». Не писать «Полностью заблокировать аккаунт»: другие назначения человека могут продолжать давать доступ. Отзыв локальной роли не снимает роль бренда, отзыв брендовой не удаляет независимые локальные роли. Списки вызывающего могут быть неполными из-за ограничений администрирования; frontend не может обещать отсутствие всех иных доступов.

Удаление STAFF-membership освобождает связь рабочего профиля с аккаунтом. Аккаунт, профиль и история работы не удаляются.

## 5. Диалог «Пригласить / Выдать доступ»

Новый участник, включая уже зарегистрированного, получает доступ через приглашение. Прямого публичного API «назначить роль произвольному userId» нет.

Поля диалога:

1. Один выбранный бренд.
2. Одно или несколько назначений: область, филиал при LOCATION, роль; для STAFF — рабочий профиль.
3. Необязательный email для доставки письма.
4. Кнопка «Создать приглашение», затем результат с новой ссылкой и кнопкой «Скопировать».

```http
POST /brands/:brandId/access/invitations
```

STAFF одного филиала:

```json
{
  "grants": [
    {
      "scope": "LOCATION",
      "locationId": "<uuid-location>",
      "role": "STAFF",
      "staffId": "<uuid-staff>"
    }
  ],
  "deliveryEmail": "employee@example.com"
}
```

Управляющий всем брендом:

```json
{
  "grants": [
    { "scope": "BRAND", "role": "MANAGER" }
  ]
}
```

Правила валидации:

- От 1 до 50 grants; все принадлежат одному бренду.
- В одной области не должно быть двух grants: один брендовый и по одному на каждый филиал. Бренд и его отдельный филиал — разные области, они могут присутствовать вместе.
- BRAND допускает OWNER/MANAGER, без locationId и staffId.
- LOCATION требует locationId; STAFF требует staffId, для OWNER/MANAGER staffId не передаётся.
- Профиль STAFF должен быть ACTIVE и принадлежать выбранному филиалу. Загрузить его через разрешённый список сотрудников; создание недостающего профиля отдельно требует `staff.manage` и не следует из `access.staff.manage`.
- Для нового приглашения STAFF предлагать прежде всего свободные профили с `userId: null`. Ссылка не адресована аккаунту: уже связанный профиль примет только тот же аккаунт. Окончательную совместимость сервер проверяет при принятии.
- Выдающий должен иметь право на каждую роль в каждой области. Если одно назначение недопустимо, весь запрос отклоняется; частичной выдачи нет.
- В форме STAFF карточка сотрудника и роль аккаунта — разные сущности. `roleTitle` сотрудника («Парикмахер») не заменяет BusinessRole.

Успех 201, `responseValue` содержит:

```ts
type InvitationLink = {
  invitation: {
    id: string;
    brandId: string;
    issuerId: string;
    expiresAt: string;
    acceptedAt: string | null;
    revokedAt: string | null;
    grants: Array<{
      role: 'OWNER' | 'MANAGER' | 'STAFF';
      locationId: string | null;
      staffId: string | null;
    }>;
  };
  token: string;
  url: string;
};
```

Ссылку брать из `url`, а не собирать самостоятельно. Создание приглашения ещё не добавляет человека в «Участников». Роль и привязка STAFF появляются после успешного accept.

Срок ссылки фиксирован — 7 дней. Поле выбора срока и `expiresAt` в request отсутствуют. Email необязателен и служит доставке: **любой авторизованный аккаунт, которому доступна ссылка, может попытаться её принять**; совпадение email не проверяется. Перед выдачей OWNER показать явное подтверждение полного доступа и возможности управлять совладельцами.

## 6. Вкладка «Приглашения»

```http
GET /brands/:brandId/access/invitations?page=1&pageSize=25
GET /brands/:brandId/access/invitations?locationId=<uuid>&page=1&pageSize=25
```

Филиального `/locations/:locationId/access/invitations` нет. `brandId` — контейнер, а не требование брендового членства: локальный управляющий использует тот же URL с фильтром своего филиала.

Ответ — пагинация `{ items, page, totalItems, totalPages, isExport }`; элементы имеют форму `InvitationLink.invitation`. Поля `token`, `url`, `status`, `deliveryEmail`, `acceptedById`, `createdAt`, `version` в списке **не возвращаются**. Scope grant определяется по `locationId`: null → BRAND, значение → LOCATION. Для отображения названия филиала/сотрудника использовать разрешённые справочники.

Сервер включает приглашение только если вызывающий вправе администрировать **все** его grants. Фильтр филиала не обрезает grants и не даёт доступа к недоступным назначениям. Приглашение на несколько филиалов может отсутствовать у управляющего одним из них. Сортировка фиксирована по createdAt DESC, затем ID; сортировка/поиск/фильтр по статусу через отдельные query-поля не реализованы.

Статус для отображения вычислять из дат:

| Условие, в указанном порядке | Статус | Действия |
| --- | --- | --- |
| `acceptedAt != null` | Принято | Просмотр. Менять доступ через membership |
| `revokedAt != null` | Отозвано | Просмотр; для новой выдачи создать новое приглашение |
| `expiresAt <= now` | Истекло | Можно перевыпустить или отозвать |
| Иначе | Ожидает принятия | Можно перевыпустить или отозвать |

Это статус по сохранённым датам, не гарантия успешного принятия: доступ автора, активность бизнеса и профиль могли измениться. Сервер повторно проверяет их при preview/accept.

### Копирование и перевыпуск

Токен/ссылка возвращаются **только при создании и перевыпуске**. После закрытия диалога старую ссылку из списка получить нельзя. Не показывать «Скопировать действующую ссылку», если её нет в текущем состоянии интерфейса.

```http
POST /brands/:brandId/access/invitations/:invitationId/reissue
```

Без тела и без If-Match. Успех 201 — новый `InvitationLink`. Старый токен аннулируется, срок снова 7 дней; автором становится перевыпустивший. Принятое или отозванное приглашение не перевыпускается, истёкшее — может.

Команду назвать «Создать новую ссылку» / «Перевыпустить» и предупредить, что предыдущая перестанет работать. Перевыпуск **не отправляет письмо повторно** в текущем коде. Не обозначать эту кнопку «Повторно отправить email».

### Отзыв ссылки

```http
DELETE /brands/:brandId/access/invitations/:invitationId
```

Без If-Match, ответ 204. Принятое приглашение отозвать нельзя; для снятия уже выданного доступа менять memberships. Отзыв ссылки не удаляет ранее существующие назначения аккаунта.

## 7. Получатель ссылки: `/invitation`

Backend формирует `<frontend.domain>/invitation#token=<64-character-token>`. Это отдельный пользовательский маршрут, доступный без членства в каком-либо бизнесе.

1. Прочитать `token` из fragment, проверить наличие и сохранить на время перехода через вход/регистрацию. Не передавать его в query backend; по возможности убрать fragment из адреса через replaceState после сохранения. Хранение через redirect — в краткоживущем состоянии/sessionStorage с очисткой после завершения, не в журнале аналитики.
2. Вызвать публичный `POST /access/invitations/preview` с `{ "token": "..." }`.
3. Показать бренд, назначения, срок и кнопку принятия. Для неавторизованного пользователя — вход/регистрация с возвратом на этот экран.
4. После входа показать, под каким собственным аккаунтом будет принято приглашение; разрешить сменить аккаунт. Не принимать доступ автоматически по открытию ссылки.
5. По явному нажатию вызвать авторизованный `POST /access/invitations/accept` с тем же `{ token }`.
6. После успеха выполнить refresh JWT, перечитать `/users/me/access` и доступные бренды/филиалы, затем открыть доступную область. Accept возвращает приглашение, **не access token**.
7. Удалить временный токен приглашения и показать завершение. Не отправлять приглашённого в обязательный onboarding создания собственного бренда.

Preview, `responseValue`:

```json
{
  "brandName": "Название бренда",
  "expiresAt": "2026-10-24T12:00:00.000Z",
  "grants": [
    { "role": "STAFF", "locationName": "Название филиала" }
  ]
}
```

`locationName: null` означает назначение на бренд. Preview не возвращает IDs профиля/областей, персональные данные или отдельный `canAccept`: доступность отражается успешным ответом либо ошибкой.

Регистрация через `POST /auth/register` сейчас возвращает обычный успех, **не авторизует и не возвращает токены**. После регистрации пройти существующий вход/OAuth и вернуться к приглашению. Не предполагать, что сам register завершил сессию. Бизнес-роли и наличие собственного бренда для accept не требуются.

Accept применяет все grants атомарно. Если у аккаунта уже есть более высокая роль в той же области, приглашение её не понижает. Повторный accept того же токена тем же аккаунтом идемпотентен и не восстанавливает впоследствии отозванные назначения. У другого аккаунта повтор отклоняется. Preview уже принятой ссылки отклоняется даже для прежнего получателя: в нём нет пользовательского контекста.

Preview/accept ограничены общим лимитом 30 запросов в минуту на IP в пределах backend-процесса. Не опрашивать preview непрерывно и не повторять accept бесконечно.

## 8. Вкладка «Права ролей»

### Область и роли

Брендовая настройка задаёт шаблоны MANAGER/STAFF. STAFF в этой вкладке означает шаблон для локальных сотрудников, **не разрешение назначать STAFF на бренд**.

Филиальная настройка меняет шаблоны прямых локальных назначений в филиале. Она не ограничивает роль, унаследованную от бренда. Для локального OWNER показывать только филиальную настройку, не разрешать сохранять её на бренд.

Редактируемые вкладки ролей — «Управляющий» и «Сотрудник». OWNER имеет полный набор своей области, не настраивается и в `entries` не возвращается. Можно показать статическое пояснение «Владелец имеет полный доступ» без формы.

### Чтение политики

```http
GET /brands/:brandId/access/policies
GET /locations/:locationId/access/policies
```

Ответ `responseValue` — `{ version, entries }`. В бренде возвращаются только редактируемые сочетания MANAGER/STAFF и permission; в филиале — только редактируемые сочетания для permissions с областью L или B/L. Неизменяемые права и внутреннее `file.brand.manage` в `entries` отсутствуют. Полный реестр содержит 49 permissions; редактор не должен достраивать отсутствующие строки.

| Поле entry | Как использовать |
| --- | --- |
| `role` | MANAGER или STAFF |
| `permission` | Стабильный ключ для сохранения; подпись для пользователя хранится на frontend |
| `defaultAllowed` | Встроенное значение без overrides |
| `inheritedAllowed` | В бренде — встроенное значение; в филиале — вычисленный шаблон бренда |
| `override` | null = наследовать, true = явно разрешить, false = явно запретить в выбранной области |
| `allowed` | Фактическое значение шаблона после применения overrides и зависимостей |
| `configurable` | Для возвращаемых строк true; неизменяемые сочетания backend не включает в редактор |
| `dependencies` | Права, без которых это действие не работает |

Строка интерфейса: понятное название действия, выбор **«Наследовать / Разрешить / Запретить»**, итоговое разрешено/запрещено и пояснение наследования. Обычного boolean-switch недостаточно: он теряет различие между наследованием и явным значением.

Группы действий: «Бизнес и доступы», «Календарь и записи», «Продажи», «Клиенты», «Товары и услуги», «Склад», «Персонал», «Зарплата», «Онлайн-запись», «Аналитика и история». API возвращает ключи, но не локализованные названия, группы или scope каждого permission; frontend нужен словарь метаданных на основе [реестра](../src/modules/access/constants/permission-registry.ts) и [модели ролей](./architecture/rbac.md). Неизвестный ключ не должен автоматически становиться редактируемым.

Пояснения источника:

- `override != null` — «Настройка бренда» либо «Настройка филиала» по текущей области.
- `override == null` в бренде — «По умолчанию».
- `override == null` в филиале — «Наследуется от бренда». Локальный ответ не сообщает, было ли родительское значение задано явно: для точной детализации нужен отдельный разрешённый GET политики бренда. Локальному OWNER он может быть недоступен.
- Если явное разрешение выключено зависимостью, показывать `allowed: false` и причину, а не только выбранное ALLOW. Такое возможно после изменения родительского шаблона. Сохранённый override не удаляется автоматически.

### Сохранение

```http
PATCH /locations/:locationId/access/policies
```

```json
{
  "expectedVersion": 12,
  "changes": [
    { "role": "STAFF", "permission": "order.return", "value": "DENY" },
    { "role": "STAFF", "permission": "booking.export", "value": "INHERIT" }
  ]
}
```

Для бренда URL `/brands/:brandId/access/policies`. Отправлять только изменённые пары role/permission: неупомянутые сохраняются. Массив от 1 до 120, без дубликатов пары. При отсутствии изменений кнопку сохранения выключить.

ALLOW/DENY сохраняют override, INHERIT удаляет его. Нельзя отправлять OWNER, `configurable: false` или B/G-permission в локальный PATCH. Нельзя создать новое имя permission или расширить допустимые сочетания ролей.

Успех — полный `{ version, entries }`: заменить состояние формы серверным результатом, убрать dirty-state и обновить JWT/контекст текущего аккаунта. Политики обновляют доступ затронутых участников; старый access token автора также может стать устаревшим.

### Зависимости

Backend отклоняет несогласованный шаблон целиком с `ACCESS_POLICY_INVALID`. Например, ALLOW для `order.return` при запрещённом `order.read` не включает чтение автоматически.

- При включении действия пройти `dependencies` рекурсивно и предложить включить недостающие права.
- При выключении чтения предложить выключить все зависимые действия, включая транзитивные.
- Показать весь набор изменений до сохранения и отправить одним PATCH. Если необходимое изменение недоступно для настройки, объяснить невозможность такого сочетания.
- «Наследовать» брать из `inheritedAllowed`, учитывать зависимости; не заменять его на ALLOW только потому, что сегодня inheritedAllowed=true.
- Использовать `allowed` для итогового состояния шаблона, а `/users/me/access` — для реального доступа текущего аккаунта. Это разные ответы.

### Сброс

```http
DELETE /brands/:brandId/access/policies/MANAGER/overrides
If-Match: 12
```

Аналогично для STAFF или `/locations/:locationId/access/policies/:role/overrides`. Успех — 204, затем GET политики.

Подписи различать: **«Сбросить к стандартным правам»** у бренда, **«Сбросить к правам бренда»** у филиала. Операция относится к одной роли. Сброс бренда не удаляет overrides филиалов; сброс филиала не меняет брендовый шаблон. OWNER сбрасывать нельзя.

## 9. Наследование: что пояснять пользователю

Пример: у Анны MANAGER бренда и STAFF филиала А. В филиале А её права — объединение обоих источников. Локальный DENY для STAFF:`order.return` не уберёт возврат, разрешённый MANAGER бренда.

Поэтому нельзя обещать, что локальная настройка выключит действие всем людям филиала. Пояснение над формой: «Настройки действуют на прямые роли филиала. Доступ, полученный через роль бренда, сохраняется».

Локальный OWNER может управлять своим локальным MANAGER, но не менять/удалять брендовый MANAGER того же человека. Снять наследуемую роль можно только через её исходное брендовое назначение с правами на бренд.

У membership нет поля `inherited`; это прямое назначение. `directRole`/`inheritedRole` есть в собственном `/users/me/access`. Готового endpoint полной матрицы эффективного доступа произвольного участника сейчас нет. Не рисовать результат «все права этого человека» из одного шаблона роли.

## 10. Владельцы и жизненный цикл STAFF

У бренда может быть несколько равноправных OWNER. Создатель не имеет скрытого старшинства. OWNER может назначать и снимать других OWNER в своей области; удаление/понижение **последнего OWNER бренда** сервер запрещает с `ACCESS_LAST_OWNER`. Локальный OWNER не обязателен.

Действия над собой допустимы с теми же проверками. После снятия/понижения собственной роли закрыть недоступные экраны после обновления JWT. Не определять последнего владельца только по текущей странице списка: она может быть неполной; окончательная проверка выполняется сервером.

При деактивации/удалении рабочего профиля отзывается прямой STAFF-доступ этого аккаунта в филиале и ожидающие приглашения, содержащие данный профиль. Если приглашение содержит несколько grants, отзывается всё приглашение. Независимые OWNER/MANAGER сохраняются. Повторная активация профиля доступ автоматически не возвращает — нужно новое приглашение/назначение допустимым путём.

`staff.manage` управляет рабочими профилями, `access.staff.manage` — доступом аккаунтов. Не заменять одно другим в интерфейсе.

Отдельный `POST /admin/brands/:brandId/owner-replacement` предназначен платформенному ADMIN, не обычному владельцу. Тело `{ previousUserId, newUserId, reason }`; старое брендовое OWNER-назначение удаляется, существующему целевому аккаунту выдаётся OWNER, прочие совладельцы не меняются. Ответ `{ id: brandId }`. Эту операцию размещать только в интерфейсе поддержки, если он реализуется; для обычной выдачи OWNER использовать приглашение.

Платформенного ADMIN нельзя администрировать другим аккаунтом через бизнес-доступы. DTO membership не сообщает platform-role целевого пользователя, поэтому frontend не всегда может заранее скрыть такую строковую команду; корректно обрабатывать серверный 403.

## 11. Версии, обновление токена и ошибки

Есть две независимые версии:

| Версия | Где получить | Для чего |
| --- | --- | --- |
| `AccessState.revision`, в API `version` | GET policies / GET memberships | Защита PATCH и DELETE от параллельного изменения доступа бренда |
| `User.tokenEpoch` | Frontend не редактирует | Сервер отзывает ранее выданные access JWT |

Первая версия общая для бренда: изменения другого филиала, приглашения или участника тоже могут сделать открытый редактор устаревшим. Она не равна версии одной роли/приглашения. Список приглашений её не возвращает; invite create/reissue/revoke/accept expectedVersion и If-Match не требуют.

| Ответ | Обработка |
| --- | --- |
| 409 `ACCESS_VERSION_CONFLICT` | Перечитать политику/список и version. Сохранить черновик для сравнения, предложить повторное применение после просмотра; не подменять version и не повторять запись автоматически |
| 400 `ACCESS_POLICY_INVALID` | Проверить configurable, область, дубли и зависимости; ни одна часть PATCH не сохранена |
| 400/409 `ACCESS_GRANT_INVALID` | Неверная роль/область/профиль, занятая привязка. Перечитать профиль/список, показать причину; частичного accept нет |
| 409 `ACCESS_LAST_OWNER` | Объяснить, что сначала нужно назначить другого владельца бренда |
| 404/410 `ACCESS_INVITATION_INVALID` | Ссылка не найдена либо недоступна/истекла/использована. Не обещать точную причину по одному общему коду; предложить новую ссылку у администратора бизнеса |
| 409 `ACCESS_INVITATION_INVALID` при reissue/revoke | Действие несовместимо с состоянием приглашения; перечитать список |
| 403 | Недостаточно прав, права автора приглашения изменились либо защищён платформенный аккаунт. Обновить контекст при необходимости; не пытаться другим API обойти отказ |
| 404 ресурса | Бренд/филиал/назначение недоступны или отсутствуют; закрыть устаревшую область/строку |
| 429 | Ограничение preview/accept. Показать паузу, не делать бесконечный автоматический retry; ориентироваться на HTTP-статус, отдельный access-код не гарантирован |
| 409 `TOKEN_PAYLOAD_STALE` с `action: REFRESH_ACCESS_TOKEN` | Единый refresh, затем новый контекст; это не конфликт редактирования version |

После accept, успешного изменения/сброса политики и изменения собственных назначений proactively обновить JWT. В остальных сценариях использовать общий обработчик STALE:

1. Объединить параллельные `POST /auth/refresh` в один запрос с refresh cookie; сохранить новый `responseValue.accessToken`.
2. Перечитать `/users/me/access`, навигацию и доступные действия; данные чужого/отозванного бизнеса очистить.
3. Допустить максимум один повтор запроса, отклонённого guards как STALE, если действие осталось разрешено. Для accept сохранить исходный invitation token.
4. Не повторять уже успешную mutation ради обновления UI. Для обновления списков нужны GET, не новый PATCH/POST.
5. При неуспешном refresh завершить сессию. Обычный `ACCESS_VERSION_CONFLICT` не лечится refresh JWT.

Пути указаны без префикса `/api`: `/api` — Swagger UI, `/api-json` — схема. Обычные ответы — `BaseResponseDto`, полезные данные в `responseValue`. Все DELETE ниже — 204 без тела.

| Метод и путь | Успешный responseValue |
| --- | --- |

## 13. Приёмка

- OWNER видит три вкладки своей области; MANAGER — только разрешённое управление STAFF; STAFF не видит раздел.
- Локальный OWNER не может менять брендовые назначения и шаблоны, но может редактировать свой филиал.
- В брендовой таблице корректно различаются брендовые и локальные строки; смена/отзыв используют URL области строки, не области списка.
- Приглашение STAFF выбирает активный профиль; выдача MANAGER/OWNER не требует создания Staff. В одном приглашении поддерживаются несколько филиалов одного бренда.
- Создание приглашения не создаёт видимый membership до accept. Ошибка одного grant не выдаёт остальные.
- Ссылка копируется из create/reissue. Перевыпуск предупреждает о старой ссылке и не обещает email. Принятую/отозванную ссылку нельзя перевыпустить.
- Вход/регистрация возвращают на приглашение; register не воспринимается как login. Получатель видит аккаунт и явно принимает доступ без создания своего бренда.
- После accept обновляются токен и бизнес-навигация; повтор того же accept не создаёт дубликатов.
- Политики поддерживают три значения и зависимости; неизменяемые и внутренние файловые права в редакторе отсутствуют. OWNER не редактируется. Сброс бренда/филиала имеет разные подписи и правильный If-Match.
- Локальный DENY не обещает отозвать брендовый источник. Отзыв одного membership не обещает блокировку всего аккаунта.
- Потеря прав при открытом экране, конфликт version, последний OWNER и недоступный STAFF-профиль обрабатываются без потери данных или бесконечного retry.
- UI использует только поля текущих DTO; имена людей, полный effective-access другого аккаунта и статус отправки email не выдумываются из отсутствующих данных.

### Упрощённые permissions от 2026-10-18

Редактор использует `booking.manage` для создания, изменения, рабочих статусов и отмены записи; `order.manage` — для создания, изменения и проведения продажи, а также удаления полностью чернового заказа; `client.manage` — для отдельного создания и редактирования карточки клиента. Чтение календаря использует `booking.read`, упаковки — `product.catalog.manage`. Неизменяемые права и внутреннее `file.brand.manage` не показываются в редакторе; существующие файловые endpoints пока продолжают проверять внутреннее право.
