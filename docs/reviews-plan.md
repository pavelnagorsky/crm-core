# Отзывы: план реализации

Статус: фаза 1 (ядро) реализована на ветке `feature/reviews-core`, фаза 2 (импорт xlsx) — на ветке `feature/reviews-import`, описание — `docs/reviews.md`. Фаза 3 не начата. Обновлён 2026-11-11.

Отступление от плана: ссылки на карты не добавлены в `LocationPublicResponseDto`. Клиент получает их в `reviewLinks` вместе с формой отзыва на странице управления записью, а фронтенд показывает их после отправки отзыва. Публичный профиль их не раскрывает.



Отступления в фазе 2:
- Заголовок `Имя` относится к паре `Имя` + `Фамилия`. Если колонки `Фамилия` нет, `Имя` делится по первому пробелу, как колонка `Автор`, поэтому поведение из раздела 6.2 сохраняется.
- Дата со смещением (`…Z`, `…+03:00`) принимается как точный момент, без пересчёта по поясу филиала.
- У ответа из файла `repliedAt` равен дате отзыва: даты ответа в файле нет, а дата импорта вводила бы в заблуждение.
- Запись аудита `REVIEW_IMPORT_COMPLETED` пишется, только если загружен хотя бы один отзыв.
- Потоковый ридер ExcelJS теряет части архива под нагрузкой, когда лист лежит раньше `sharedStrings.xml` (так пишут и Excel, и ExcelJS): лист уходит во временный файл, и итерация по zip заканчивается раньше времени. `XlsxUtils.rows` перед чтением перепаковывает нужные части через JSZip в безопасном порядке. `jszip` объявлен прямой зависимостью.

Замер (раздел 8, пункт 1): оба прохода разбора 50 000 коротких строк занимают около 5 с на машине разработчика. Запись в БД (100 пачек по 500) отдельно не замерялась. Решение владельца продукта: ответ до 10 с допустим, дополнительный замер не нужен.

## Принятые решения

| Вопрос | Решение |
| --- | --- |
| Текст отзыва | Обязателен для всех отзывов, включая импортированные |
| Оценка и сотрудники | Отзыв даётся на визит, сотрудники подтягиваются из записи автоматически. Одна оценка и один текст дублируются на каждого мастера визита, отдельных оценок мастерам нет. В файле импорта мастер указывается так же (допускается несколько). Раздел 2 |
| Форма отзыва | Прямо на странице управления записью, у завершённого визита сразу видна форма. Письмо с запросом дополнительное, не единственный вход. Раздел 4 |
| Ссылки на карты | На уровне филиала, показываются только на экране «Спасибо» после отзыва, в письме их нет. Раздел 6.3 |
| Часовой пояс дат импорта | Время филиала (`Location.timezone`), раздел 6.2 |
| Порог средней оценки | От 3 отзывов |
| Срок отзыва | 14 дней после визита. Это срок жизни той же ссылки управления записью, отдельной ссылки нет |
| Интеграции с Google, Яндекс, YClients | Не делаем |
| Импорт отзывов | Из xlsx, сразу следующим этапом после ядра, без фоновых задач. Один шаг, как импорт клиентов, но с отчётом об ошибках по строкам. Лимит 25 МБ и 50 000 строк. Раздел 6 |
| Откат импорта | Не делаем |
| Удаление отзыва | Есть: одиночное жёсткое удаление менеджером с записью в аудит. Массового удаления и отката партии нет |
| Источник отзыва | Необязательная строка, хранится и видна только менеджерам, клиентам не показывается, в рейтинге не участвует. Значения вне списка не ошибка |
| Автор отзыва | Имя и фамилия могут быть `null`. Фронтенд сам подставляет текст «Гость» или подобный |

## 1. Нужен ли менеджмент отзывов

Да, но минимальный. Без него отзыв нельзя убрать, если он оскорбительный или оставлен по ошибке, и бизнес не может ответить на него. Уровень «как в YClients»:

| Возможность | Когда | Комментарий |
| --- | --- | --- |
| Клиент оставляет оценку 1–5 и текст по ссылке управления | v1 | Только после завершённого визита |
| Публичный список отзывов и рейтинг в публичном букинге | v1 | Локация и каждый сотрудник |
| Рейтинг и отзывы сотрудника в панели управления | v1 | Карточка и список сотрудников |
| Скрыть или показать отзыв | v1 | Причина обязательна, пишется в аудит |
| Публичный ответ бизнеса | v1 | Один ответ на отзыв, можно изменить и удалить |
| Удаление отзыва | v1 | Жёсткое, по одному, для исключительных случаев (спам, просьба клиента удалить персональные данные, ошибочный импорт). Обычный путь — скрытие. В аудите остаётся снимок удалённого отзыва |
| Премодерация до публикации | нет | Отзыв публикуется сразу; клиент подтверждён визитом |
| Ссылки «Оставить отзыв на Google / Яндекс Картах» после отзыва | v1 | Настраиваются на уровне филиала (`Location`). Раздел 6.3 |
| Импорт отзывов из XLSX | v2, сразу после ядра | Перенос из другой CRM, раздел 6.2 |
| Уведомление владельцу о плохой оценке | позже | Фаза 3 |

## 2. Модель данных

Новый модуль `ReviewsModule`, владелец таблиц `Review` и `ReviewStaff`. Публичный API для других модулей: `ReviewsFacade`. Репозиториев нет: `DatabaseService` инжектится прямо в сервисы.

```prisma
enum ReviewStatus { PUBLISHED HIDDEN }

model Review {
  id             String       @id @default(uuid())
  locationId     String
  bookingId      String?      @unique            // один отзыв на визит
  clientId       String?                         // SetNull при удалении клиента

  rating         Int          @db.SmallInt       // общая оценка визита; CHECK (rating BETWEEN 1 AND 5) в SQL миграции
  text           String       @db.VarChar(2000)  // обязателен
  authorFirstName String?     @db.VarChar(100)   // снимок из Booking; null, если автор неизвестен (импорт)
  authorLastName  String?     @db.VarChar(100)   // пустая строка в снимке сохраняется как null
  reviewedAt     DateTime                        // дата отзыва

  status         ReviewStatus @default(PUBLISHED)
  hiddenAt       DateTime?
  hiddenReason   String?      @db.VarChar(500)

  replyText      String?      @db.VarChar(2000)
  repliedAt      DateTime?
  repliedByName  String?      @db.VarChar(250)   // снимок

  createdAt      DateTime     @default(now())
  updatedAt      DateTime     @updatedAt

  location  Location        @relation(onDelete: Cascade)
  booking   Booking?        @relation(onDelete: SetNull)
  client    Client?         @relation(onDelete: SetNull)
  staff     ReviewStaff[]

  @@index([locationId, status, reviewedAt, id])
}

model ReviewStaff {
  reviewId  String
  staffId   String
  staffName String @db.VarChar(250)               // снимок
  review    Review @relation(onDelete: Cascade)
  staff     Staff  @relation(onDelete: Cascade)   // сотрудник удалён: отзыв остаётся на уровне локации
  @@id([reviewId, staffId])
  @@index([staffId])
}
```

Другие изменения схемы:

- `Booking.reviewRequestSentAt DateTime?` — по образцу `reminderSentAt`.
- `Location.reviewsEnabled Boolean @default(true)` — собирать ли отзывы и отправлять письма.
- Поля импорта в `Review` (`source String? @db.VarChar(100)`, `importKey String?`, `importBatchId String?`, уникальный индекс `(locationId, importKey)`) добавляются миграцией той фазы, когда делается импорт. В v1 их нет. `source` — свободная строка для менеджеров, `importBatchId` наружу не отдаётся и нужен только для разборов через SQL.

### Оценка и сотрудники

Клиент оставляет **один отзыв на визит**. Сотрудников он не выбирает: сервер берёт неповторяющиеся `staffId` из позиций записи (`BookingItem`) в момент первого сохранения и фиксирует их.

| Состав визита | Что видит клиент | Что сохраняется |
| --- | --- | --- |
| Один сотрудник (основной случай) | Одна оценка и текст | `Review.rating`; одна строка `ReviewStaff` |
| Несколько сотрудников (комбо-услуга, маникюр у одного, стрижка у другого) | Та же форма: одна оценка и текст | `Review.rating`; по строке `ReviewStaff` на каждого мастера. Отзыв дублируется на всех |

Решение владельца продукта: отдельных оценок мастерам нет. Один отзыв засчитывается каждому мастеру визита с одной и той же оценкой.

- Услуга и мастер в записи всегда связаны (`BookingItem` хранит `staffId`), поэтому состав мастеров берётся из записи без участия клиента.
- Рейтинг локации считается по `Review.rating`, рейтинг мастера — по `Review.rating` опубликованных отзывов, которые к нему привязаны через `ReviewStaff`. Колонки оценки в `ReviewStaff` нет.
- Один отзыв с двумя мастерами увеличивает счётчик у обоих, но в рейтинге локации он учитывается один раз.
- Правка отзыва меняет оценку и текст для всех привязанных мастеров. Состав мастеров фиксируется при первом сохранении и не пересчитывается, даже если запись позже изменили.
- Привязка к мастеру при импорте работает так же: в файле указывается мастер (или несколько), отзыв привязывается ко всем найденным. Подробности в разделе 6.2.

### Прочие решения

- **Автор.** Дублируем имя и фамилию из `Booking.clientFirstName/LastName`. В публичном ответе показываем «Анна К.», полное имя только в админке.
- **Агрегаты.** Не денормализуем. Считаем через `groupBy` по индексам и кэшируем в app-cache, сброс при создании, правке, скрытии. Расхождения счётчиков невозможны.
- **Автор правит отзыв.** Клиент может изменить оценку и текст, пока действует ссылка (upsert). Удалить не может. Текст остаётся обязательным и при правке.

## 3. Правила показа и пустое состояние

Единый источник истины — бэкенд. Фронтенд не вычисляет «показывать или нет», а использует поля ответа.

```ts
ReviewSummaryDto { count: number; average: number | null; distribution: Record<1|2|3|4|5, number> }
```

Константа `REVIEWS_MIN_FOR_AVERAGE = 3`.

| Опубликованных отзывов | Что показывать |
| --- | --- |
| 0 | Ничего: без «0.0» и пустых звёзд, блок отзывов не рендерится, в карточке сотрудника рейтинга нет |
| 1–2 | Список отзывов и «N отзыва». Средняя оценка `average: null`, звёзды-итог не рисуем |
| 3 и больше | Средняя оценка с одним знаком после запятой, количество, распределение |

- В админке пустое состояние не скрываем: «Отзывов пока нет» и подсказка, что клиентам уходит письмо с запросом.
- Скрытые отзывы не входят в `count` и `average`.
- Правила одинаковы для локации и для сотрудника, у сотрудника считаются по привязанным к нему опубликованным отзывам.

## 4. Клиентский сценарий

Отзыв оставляется на странице `/booking/manage` по существующему токену, без нового механизма авторизации.

**Условия:** `booking.status === COMPLETED`, запись не удалена, `Location.reviewsEnabled`, ссылка ещё действует. Правило — чистая функция в `reviews/rules/`, принимает минимальную форму записи. Модуль reviews не импортирует bookings.

**Эндпоинты** (в `BookingClientController`, guard `JwtBookingClientGuard`, `Cache-Control: no-store`):

| API | Назначение |
| --- | --- |
| `PUT /public/bookings/me/review` | Создать или обновить. Тело `{ rating: 1..5, text: string }`. Ответ `ClientReviewDto` |
| (поля в `GET /public/bookings/me`) | `canReview: boolean`, `review: ClientReviewDto \| null`, `canReviewUntil` |

Автор, сотрудники и локация берутся из записи на сервере. Если отзыв не разрешён, `403 / REVIEW_NOT_ALLOWED`. Пустой после обрезки пробелов текст отклоняется валидацией DTO. Новые `ErrorCode`: `REVIEW_NOT_ALLOWED`, `REVIEW_NOT_FOUND`, `REVIEW_REPLY_NOT_FOUND`. Текст перед сохранением чистим от разметки (`sanitize-html`, режим «только текст»).

**Форма на странице управления.** Клиенты редко открывают отдельные письма, поэтому основной вход — сама страница управления записью, а не письмо. Когда `canReview = true` и отзыва ещё нет, страница показывает форму отзыва прямо вверху, не за кнопкой или вкладкой. Если отзыв уже есть, показывается он с возможностью править до конца срока. Так любой клиент, открывший свою ссылку управления после визита, сразу видит форму. Письмо с запросом остаётся как дополнительное напоминание и ведёт на ту же страницу. Для этого бэкенд ничего не добавляет к описанному выше, всё сводится к полям `canReview` и `review`.

**Срок.** Сейчас ссылка действует до `endAt + 72 ч`. Для `COMPLETED` записей доступ продлевается до `endAt + 14 дней`: просмотр и отзыв, отмена и перенос остаются недоступны. Срок проверяется на каждом запросе по записи в БД, поэтому уже выданные ссылки продлятся сами. Исключение — старые JWT с фиксированным `exp`. Меняется `clientAccessExpiresAt` в `booking-client.rules.ts` и документ `booking-client-management.md`.

**Запрос отзыва.** Новый крон в `BookingCronService`: раз в час берёт записи `COMPLETED`, где `endAt` был больше 2 часов назад, но не позже 7 дней, есть `clientEmail`, `reviewRequestSentAt IS NULL`, отзыва нет, у локации включены отзывы. Запись «забирается» через `updateMany` по образцу `reminderSentAt`. Письмо `ReviewRequestNotification` содержит ссылку управления. Других каналов в проекте нет, только email. Менеджер может отправить ссылку вручную через `POST .../client-token`.

Граница модулей: `BookingsModule` импортирует `ReviewsModule`; `ReviewsModule` не знает о bookings, поэтому цикла нет.

## 5. Публичный букинг и панель

**Публичный флоу** (без аккаунта):

- `GET /public/booking-pages/:slug` и `GET /public/booking-widgets/:widgetId` получают поле `reviews: { summary, latest: ReviewItem[3] }`.
- `BookingSetupStaffDto` получает `reviewSummary: { count, average } | null`. Подмешиваем в контроллере через `ReviewsFacade.getStaffSummaries(staffIds)`, а не внутри кэшируемого `getBookingSetup`, чтобы не усложнять инвалидацию кэша.
- `GET /public/locations/:locationId/reviews?page&pageSize&staffId&rating` — пагинация через `PaginationRequestDto` / `PaginationResponseDto`. `staffId` проверяем на принадлежность локации. Публичный кэш короткий.
- Элемент: `id`, `authorName` (маскированное, «Анна К.», либо `null`, если автор неизвестен), `rating`, `text`, `reviewedAt`, `reply { text, repliedAt } | null`, `staff [{ id, name }]`.

**Панель управления** (права `review:read` / `review:write`, по образцу `booking-channel:*`):

| API | Назначение |
| --- | --- |
| `GET /locations/:locationId/reviews` | Список. Фильтры: `staffId`, `status`, `rating`, `search`, `from`, `to`, `isExport` |
| `GET /locations/:locationId/reviews/summary` | Сводка с распределением, опционально по `staffId` |
| `GET /locations/:locationId/reviews/:id` | Один отзыв с полным именем и записью |
| `PATCH /locations/:locationId/reviews/:id/visibility` | `{ status, reason? }`, причина обязательна при скрытии |
| `DELETE /locations/:locationId/reviews/:id` | 204. Жёсткое удаление вместе с `ReviewStaff`, сброс кэша сводок, аудит со снимком |
| `PUT /locations/:locationId/reviews/:id/reply` | `{ text }` |
| `DELETE /locations/:locationId/reviews/:id/reply` | 204 |

- В `StaffResponseDto` и `StaffDirectoryItemDto` добавляем `reviewSummary`. `StaffModule` импортирует `ReviewsModule`; сводку отдаёт `ReviewsFacade` батчем по списку id, чужие таблицы не трогаем.
- Отзывы сотрудника — тот же список с `staffId` (вкладка «Отзывы» в карточке сотрудника). Отдельного маршрута в `StaffController` не нужно.
- Права: v1 только владелец и менеджер. Доступ сотрудника к собственным отзывам — отдельная задача по RBAC.
- Аудит: `AuditEntity.REVIEW`; события `REVIEW_CREATED` (роль `CLIENT`), `REVIEW_UPDATED`, `REVIEW_VISIBILITY_CHANGED`, `REVIEW_REPLIED`, `REVIEW_REPLY_DELETED`, `REVIEW_DELETED`.
- Последствия удаления. Если автор не импортированный и ссылка ещё действует, клиент сможет оставить отзыв заново. Удалённый импортированный отзыв вернётся при повторной загрузке того же файла, поскольку его `importKey` исчез. Оба случая приемлемы.
- Источник (`source`) отдаётся только в админских DTO.
- Новые claim добавляем в `claim.enum.ts`, `permission-registry.ts`, `role-bags.ts`, обновляем `rbac-permissions-map.md` и `frontend-permissions.json`.

## 6. Нужен ли импорт и в каком виде

### 6.1 Реальные сценарии

| Сценарий | Нужно ли | Решение |
| --- | --- | --- |
| **Бизнес переходит из другой CRM** (YClients, Altegio, Dikidi и т. п.), у него накоплены отзывы собственных клиентов | Да, единоразово при подключении. Без этого публичная страница стартует «с нуля»: по правилам раздела 3 клиент не видит ничего, тогда как у бизнеса уже 4,9 по 600 отзывам | Лёгкий импорт xlsx (6.2) |
| **Перенос отзывов с Google или Яндекс Карт** | Нет. Насколько известно, штатной выгрузки отзывов владельцу в xlsx нет, то есть собирать пришлось бы вручную. Отзывы не подтверждены визитом и принадлежат другой площадке, условия повторной публикации у Google и Яндекса не проверены. Клиент и так видит их на картах | Не делаем. Никаких бейджей источника, интеграций и API-синхронизации |
| **Бизнес хочет больше отзывов на картах** | Да, это то, что ему реально нужно от отзывов | Две ссылки в настройках филиала (`googleReviewUrl`, `yandexReviewUrl`) и показ их на экране «Спасибо за отзыв» всем клиентам. Показывать только довольным нельзя: Google запрещает выборочно просить отзывы у довольных клиентов. Решено делать, раздел 6.3 |

Вывод: интеграций нет. Импорт из xlsx нужен мигрирующим клиентам и делается отдельным этапом сразу после ядра. Ядро импорта не ждёт: пустое состояние из раздела 3 корректно обрабатывает старт без отзывов. Ссылки на карты делаем в первой версии, раздел 6.3.

### 6.3 Ссылки на карты (на уровне филиала)

Сами ссылки ничего не публикуют: клиент переходит по ним и пишет отзыв на Google или Яндекс Картах самостоятельно. Автоматической публикации от имени клиента нет ни у одной площадки.

**Схема.** В `Location` добавляются два необязательных поля: `googleReviewUrl String? @db.VarChar(2048)` и `yandexReviewUrl String? @db.VarChar(2048)`. Привязка к филиалу, а не к бренду, потому что у каждого филиала своя карточка организации на картах. Поля идут в той же миграции, что и ядро отзывов.

**Настройка.**
- Поля добавляются в `CreateLocationDto`, `UpdateLocationDto`, `LocationResponseDto`, `LocationPublicResponseDto`, `LOCATION_SETTINGS_SELECT` (кэш настроек) и в `LOCATION_AUDIT_FIELDS` с подписями в `ru.json`. Права те же, что на остальные настройки филиала, новых claim не нужно.
- Валидация по образцу `OptionalMapWidgetUrl`: обрезка пробелов, пустое значение превращается в `null`, только `https`, до 2048 символов.
- Ссылка принимается только с хоста и пути своей площадки, чтобы менеджер не мог подставить произвольный адрес, который увидят клиенты. Шаблоны хостов и путей лежат в `regular-expressions.ts`, проверка — функция в `rules/`.

**Допустимые форматы (сверено с документацией и описаниями на 2026-11-10).**

| Площадка | Формат | Откуда взять | Источник |
| --- | --- | --- | --- |
| Google | `https://g.page/r/<код>/review` | Кабинет Google Business Profile: «Читать отзывы» → «Получить больше отзывов» → «Копировать» | Описания на сторонних сайтах, в документации Google такой ссылки нет |
| Google | `https://search.google.com/local/writereview?placeid=<PlaceID>` | Строится по Place ID | Широко используется, но в документации Google не описан: Google может изменить |
| Google | `https://www.google.com/maps/place//data=...!12e1` | Поле `googleMapsLinks.writeAReviewUri` в Places API (New) | Официальная документация Google (Places API, статус preview) |
| Яндекс | `https://yandex.ru/maps/org/<название>/<id>/reviews/?add-review=true` | Страница организации на Яндекс Картах, вкладка «Отзывы» | Описания на сторонних сайтах, в официальной справке параметра нет |
| Яндекс | `https://yandex.ru/maps/org/<название>/<id>/` | Профиль организации на Картах | Справка Яндекс Бизнеса: QR-код из «Промоматериалов» ведёт в профиль организации, форма отзыва доступна оттуда |
| Яндекс | `https://yandex.ru/profile/<id>` | Организации без точки на карте | Описания на сторонних сайтах |

Правила проверки:
- Google: хост `g.page` и путь `/r/...`, либо `search.google.com` и путь `/local/writereview`, либо `www.google.com` / `google.com` и путь `/maps/place`.
- Яндекс: хосты `yandex.ru`, `.by`, `.kz`, `.uz`, `.com`, путь начинается с `/maps/org/` или `/profile/`. Параметр `add-review=true` не обязателен и не проверяется: он не описан в официальной справке, поэтому принимаем и ссылку на профиль организации.
- Сокращённые ссылки (`maps.app.goo.gl`, `goo.gl`) не принимаем: это ссылка «Поделиться», она ведёт на профиль, а не на форму отзыва, и скрывает реальный адрес.
- В настройках на фронтенде показываем подсказку, откуда копировать ссылку, и просим проверить её в приватном окне.
- Форматы сторонних площадок могут измениться. Проверка хоста и пути лежит в одном правиле, поэтому список правится в одном месте.
- Декораторы выносятся в `decorators/` модуля `LocationModule`, по одному на площадку.

**Показ клиенту.** `ClientBookingResponseDto` (`GET /public/bookings/me` и ответ `PUT .../review`) получает поле `reviewLinks: { google: string | null, yandex: string | null }`. Данные берутся из кэша настроек филиала через публичный API `LocationService`, поэтому лишних запросов нет, а таблицы `Location` из bookings и reviews не читаются напрямую. Поле заполняется только когда у записи уже есть отзыв. Фронтенд показывает на экране «Спасибо» кнопки для непустых ссылок.

**Правила.**
- Ссылки показываются всем клиентам, оставившим отзыв, независимо от оценки. Фильтровать по оценке нельзя.
- Ссылки не связаны с нашими отзывами: ничего не импортируется и не синхронизируется, рейтинг считается только по нашим данным.
- Ссылку можно продублировать в письме `ReviewRequestNotification`. В v1 в письмо не включаем, чтобы не просить об отзыве на картах до того, как клиент оценил визит у нас. Решение можно пересмотреть.

**Тесты.** Валидация: пустое значение даёт `null`, `http` отклоняется, чужой хост отклоняется, поддомены и похожие хосты (`evilgoogle.com`, `google.com.evil.ru`) отклоняются, сокращённые ссылки отклоняются, каждый формат из таблицы принимается, неверный путь на правильном хосте отклоняется, длина 2048. Ответ клиента: ссылки присутствуют только при наличии отзыва; ссылки одного филиала не попадают в ответ для записи другого. Аудит фиксирует изменение полей. Контракт DTO обновляется вместе с `booking-channel-contract.spec.ts`.

### 6.2 Лёгкий импорт из xlsx

Реальные объёмы: у салона за годы работы это сотни или несколько тысяч отзывов, у сети — до десятков тысяч. Поэтому очередь заданий, промежуточные таблицы и фоновые процессы не нужны.

**Что берём из импорта клиентов:** проверку типа и размера файла, обязательные колонки и алиасы заголовков на русском и английском, схему «причина файла → `ErrorCode` + HTTP-статус», доступ через `Claim`, аудит с актором из токена, дедупликацию внутри файла и против БД.

**Что делаем иначе, потому что отзывов много:**

| | Импорт клиентов сейчас | Импорт отзывов |
| --- | --- | --- |
| Объём | 5 МБ и 2000 строк | 25 МБ и 50 000 строк на файл |
| Чтение файла | Целиком в памяти | Потоковое (`ExcelJS WorkbookReader`), в памяти одна строка |
| Запись | Один проход | Пачки по 500 строк, каждая в своей транзакции |
| Результат | Три счётчика | Счётчики, ошибки по кодам и первые 100 ошибок с номерами строк |
| Шаги | Один: сразу запись | Тоже один: сразу запись, без `dryRun` и подтверждения |
| Повтор и разбиение | По телефону | Идемпотентно по ключу отзыва: исправленный файл можно загрузить снова, уже принятые строки станут дубликатами |

**API:**

- `GET /locations/:locationId/reviews/import/template` — шаблон xlsx с заголовками, примером и листом подсказок.
- `POST /locations/:locationId/reviews/import` — multipart `file`. Ответ: `totalRows`, `importedCount`, `duplicateCount`, `errorCount`, `unmatchedStaffCount`, `errorsByCode`, `errors: [{ row, code }]` (первые 100). Тот же принцип, что у импорта клиентов: валидные строки записываются сразу, невалидные пропускаются и перечисляются в ответе. Расширение относительно клиентов — номера строк и коды, чтобы пользователь мог исправить файл.
- Поток для пользователя: загрузить файл, по ответу исправить строки с ошибками, загрузить исправленный файл (или только строки с ошибками) повторно. Серверу не нужны ни промежуточные таблицы, ни задания.
- Право `review:import` (запись, уровень локации). Новые `ErrorCode` для файла — по образцу `CLIENT_IMPORT_*`: `REVIEW_IMPORT_FILE_MISSING`, `_FILE_TOO_LARGE`, `_FILE_UNSUPPORTED`, `_FILE_CORRUPT`, `_MISSING_COLUMNS`, `_FILE_EMPTY`, `_TOO_MANY_ROWS`.

**Колонки:**

| Колонка (алиасы) | Обязательна | Правило | Код ошибки строки |
| --- | --- | --- | --- |
| Оценка (`оценка`, `рейтинг`, `rating`, `stars`) | да | Целое 1–5. Принимаем `5`, `5.0`, `5 звёзд`. Дробные, 0 и 6+ отклоняем | `RATING_INVALID` |
| Дата (`дата`, `дата отзыва`, `date`) | да | `dd.MM.yyyy`, `dd.MM.yyyy HH:mm`, `yyyy-MM-dd`, ISO и дата-ячейка Excel. Не в будущем и не раньше 2000 года | `DATE_INVALID` |
| Текст (`текст`, `отзыв`, `комментарий`, `text`) | да | До 2000 символов, разметка вычищается. Строки без текста отклоняются и учитываются в счётчике | `TEXT_REQUIRED`, `TEXT_TOO_LONG` |
| Автор (`автор`, `имя`, `author`) или `Имя` и `Фамилия` | нет | До 100 символов на часть, единая колонка делится по первому пробелу. Пусто — `null` в обоих полях | `AUTHOR_TOO_LONG` |
| Источник (`источник`, `source`) | нет | Любая строка до 100 символов, обрезаются пробелы. Неизвестные значения не ошибка. Хранится только для менеджеров | `SOURCE_TOO_LONG` |
| Сотрудник (`сотрудник`, `мастер`, `staff`) | нет | Один или несколько мастеров в ячейке через `,`, `;`, `/` или перенос строки (комбо-услуга). Каждое имя сопоставляется (без `ё`, регистра и лишних пробелов) с активными сотрудниками локации. Отзыв привязывается ко всем найденным, оценка у всех одна. Нет совпадений или несколько совпадений для имени — это имя пропускается с предупреждением, не ошибкой; если не найден ни один, отзыв остаётся на уровне локации | — |
| Ответ (`ответ`, `reply`) | нет | До 2000 символов | `REPLY_TOO_LONG` |
| ID отзыва (`id`) | нет | До 128 символов | `ID_TOO_LONG` |

Пустые строки пропускаются. Отсутствие обязательных колонок (`Оценка`, `Дата`, `Текст`) определяется до чтения данных и даёт `MISSING_COLUMNS`, как у клиентов.

**Дедупликация.** Ключ отзыва `importKey`: `ID` из файла, а если его нет, `sha256(автор | дата | оценка | текст)` после нормализации регистра и пробелов. Уникальность `(locationId, importKey)`, запись через `createMany` с `skipDuplicates`. Два разных отзыва с одинаковыми автором, датой, оценкой и текстом сольются в один, это принимаем. Повторная загрузка и разбиение на части с пересечением безопасны.

**Схема.** Поля `source`, `importKey`, `importBatchId` и индекс описаны в разделе 2. Откат партии не делаем. Ошибочно загруженный файл исправляется по одному через удаление или скрытие; если случай окажется массовым, партию снимет запрос по `importBatchId`, которое для этого и хранится.

**Показ.** Импортированные отзывы входят в рейтинг как обычные, без бейджа и без упоминания источника для клиентов. Менеджер видит `source` в админском списке и карточке. Ответ из файла записывается с `repliedByName = null`.

**Модули.** `ReviewImportModule` импортирует `ReviewsModule`, `StaffModule` и `LocationModule`. Он ничего не пишет в `Review` напрямую: вставка через `ReviewsFacade.insertImportedBatch`. Сотрудники — через новую именованную операцию `StaffService` («нормализованное имя → id»), чужие таблицы напрямую не читаем. `StaffModule` импортирует только `ReviewsModule` для сводок, поэтому цикла нет. Для каждой пачки берётся блокировка активной локации (`acquireActiveOperationLock`), как в крон-напоминаниях. После импорта один раз сбрасывается кэш сводок и пишется одна запись аудита `REVIEW_IMPORT_COMPLETED`.

**Часовой пояс дат.** Даты в файле считаются временем филиала: отзывы относятся к той же физической точке. Дата в файле — «стенное» время без пояса, поэтому:
- Строки разбираются по компонентам (`dd.MM.yyyy`, `dd.MM.yyyy HH:mm`, `yyyy-MM-dd`, ISO без пояса).
- Дата-ячейка Excel читается через UTC-геттеры (`getUTCFullYear` и т. д.): ExcelJS отдаёт «стенное» время как UTC-момент. Так результат не зависит от часового пояса сервера, в отличие от `XlsxUtils.cellText`, которая форматирует дату в поясе сервера. Для отзывов в `XlsxUtils` добавляется чтение типизированного значения ячейки.
- Из компонентов собирается строка `yyyy-MM-ddTHH:mm:ss` и переводится в UTC через `TimeUtils.localToUtc(..., location.timezone)`: он уже учитывает переходы на летнее время и используется в записях.
- Если в ячейке только дата, время ставится 12:00 по филиалу, чтобы день не сдвинулся ни в какую сторону.
- Проверка «не в будущем» сравнивается с текущим моментом.
- Тест запускается при `TZ`, отличном от UTC и от пояса филиала.
- Импорт клиентов, возможно, страдает тем же сдвигом, я это не проверял. Отдельная задача, не входит в отзывы.

**Производительность.** Фоновых задач нет. Лимиты 25 МБ и 50 000 строк, потоковое чтение и пачки по 500 строк. До начала разработки импорта нужно замерить на синтетическом файле в 50 000 строк время ответа и сверить его с таймаутом прокси на проде. Если не укладываемся, снижаем лимит строк, фоновые задания не добавляем.
