# Order ↔ Booking ↔ Product: редактор заказа и политика товаров при отмене брони

Oct 10, 2026 · @Pavel

## Зачем это

Сегодня заказ (`Order`) редактируется по принципу «всё или ничего»: эндпоинт `PUT /orders/:id` работает, только если **все** строки заказа — черновики (`DRAFT`). Как только хотя бы одна строка подтверждена (`CONFIRMED` — склад списан, комиссия начислена), форма редактирования перестаёт открываться: приходит ошибка `ORDER_ITEM_NOT_DRAFT`. Это блокирует главный кассовый сценарий салона — дозаказ товаров поверх уже оказанных услуг.

Корень в том, что `PUT` реализован как «удалить все строки и создать заново». Такой подход физически несовместим с подтверждёнными строками: на них висят движения склада, начисления сотрудникам и аудит-лог, привязанные к `OrderItem.id`. Пересоздание сменило бы id и порвало эти ссылки. Поэтому `PUT` и запрещён для не-черновиков — это не стиль, а защита целостности.

Решение: **изменяемость определяется статусом строки, а не статусом заказа.** Заказ редактируем, пока он `ACTIVE`; внутри меняется только подмножество `DRAFT`-строк, а `CONFIRMED`/`REVERSED` остаются неприкосновенными и показываются во фронте в read-only. Менеджер видит одну форму, свободно правит черновики, жмёт «Сохранить» один раз — бэк применяет точечный diff, сохраняя id неизменных строк.

Второй, смежный вопрос — что происходит с проданными товарами при отмене визита. Сейчас отмена завершённой брони молча сохраняет товары как проданные (это бизнес-корректно: клиент ушёл с товаром), но делает их недоступными для управления из UI. Документ фиксирует обе проблемы, бизнес-ценность решения и план внедрения.

## Как сейчас устроено

`Order` — внутренний чек/продажа на уровне `Location`. Он либо **standalone** (`bookingId = null`, продажа товаров с прилавка), либо **привязан к брони** (`bookingId @unique` — один заказ на одну `Booking`). Строки заказа (`OrderItem`) бывают двух типов:

- `SERVICE` — порождается из `BookingItem` при завершении брони; это snapshot услуги на момент завершения.
- `PRODUCT` — товар, ссылается на `catalogItemId` (productId) и `productLocationId`.

Разделение владения чистое: `Booking` владеет услугами и составом визита, `Order` — деньгами, складом (`InventoryMovement`) и комиссиями (`StaffEarning`).

**Статусы.** `OrderStatus` — только `ACTIVE` и `VOIDED` (нет `COMPLETED`: заказ «живёт», состояния на уровне строк). `OrderItemStatus`: `DRAFT → CONFIRMED → REVERSED`. Подтверждение строки — это списание склада + начисление комиссии; возврат (`REVERSED`) — откат обоих.

**Потоки.** Услуги попадают в заказ автоматически при `Booking → COMPLETED` (`syncCompletedBooking`): создаётся привязанный заказ, каждый `BookingItem` → `OrderItem(SERVICE, CONFIRMED)`. Товары добавляются либо в standalone-заказ (`POST /orders`, сразу или через черновик), либо в заказ брони (`addDraftProductToBookingOrder`), и подтверждаются отдельно.

**Текущие ограничения по действиям:**

| Действие                   | Endpoint                   | Разрешено при                                | Ограничения                         |
| -------------------------- | -------------------------- | -------------------------------------------- | ----------------------------------- |
| Update (замена всех строк) | `PUT /orders/:id`          | `ACTIVE` + **все** строки `DRAFT`            | удаляет и пересоздаёт всё           |
| Delete                     | `DELETE /orders/:id`       | `ACTIVE` + **все** `DRAFT`                   | hard delete                         |
| Void                       | `PATCH /orders/:id/status` | `ACTIVE`, только standalone                  | только OWNER/SUPPORT; нужен reason  |
| Confirm строку             | `.../confirm`              | заказ `ACTIVE`, строка `DRAFT`+`PRODUCT`     | списывает склад, пишет комиссию     |
| Reverse строку             | `.../reverse`              | заказ `ACTIVE`, строка `CONFIRMED`+`PRODUCT` | нужен reason; откат склада+комиссии |

Ключевая дыра: **нет способа добавить строку в заказ, где уже есть `CONFIRMED`-строки** — именно она ломает кассовый сценарий.

Услуги попадают в заказ сразу как `CONFIRMED`, товары — через `DRAFT` и отдельный confirm; при отмене брони только услуги уходят в `REVERSED`.

## Бизнес-кейсы

Конкретные сценарии салона, которые сейчас не закрываются.

**Кейс 1. Дозаказ товара после услуги.** Клиент пришёл, услуги оказаны → бронь завершилась → услуги `CONFIRMED` автоматически. На ресепшене клиент берёт шампунь. Сейчас добавить товар в заказ, где уже есть `CONFIRMED`-услуги, форма редактирования не позволяет — `ORDER_ITEM_NOT_DRAFT`.

**Кейс 2. Клиент передумал до оплаты.** В черновике заказа лежит шампунь, но клиент берёт маску вместо него. Нужно убрать одну черновую строку, добавить другую, поменять количество — всё в одной форме, одним сохранением. Сейчас это работает, только пока весь заказ — черновик.

**Кейс 3. Возврат проданного товара.** Товар уже подтверждён, клиент возвращает его. Это не «удалить строку», а возврат с причиной: товар назад на склад, комиссия сторнируется. Механизм уже есть (`reverseItem`), но к нему нет удобного входа в UI.

**Кейс 4. Отмена визита с купленным товаром.** Услугу отменили (визит не состоялся), но товар клиент уже забрал. Бизнес-логика: услуга сторнируется, товар остаётся продан. Сейчас так и происходит на бэке, но заказ отменённой брони недоступен из UI — товар нельзя ни увидеть, ни вернуть.

Так работает YClients: визит остаётся редактируемым после оказания услуг, товары добавляются и возвращаются поштучно, а «убрать подтверждённый товар» — это возврат, отдельное действие с причиной.

## Что это даёт

Фичи с привязкой к бизнес-кейсам выше.

| Фича                                                               | Закрывает кейс | Ценность для бизнеса                                               |
| ------------------------------------------------------------------ | -------------- | ------------------------------------------------------------------ |
| Редактирование заказа с подтверждёнными строками                   | 1, 2           | Дозаказ товаров прямо в карточке визита — основной способ допродаж |
| Свободное редактирование черновиков (add/remove/qty) в одной форме | 2              | Быстрая касса без модалок; одна кнопка «Сохранить»                 |
| read-only секция проданных с кнопкой «Вернуть»                     | 3              | Понятный возврат товара с причиной и откатом склада                |
| Доступ к заказу отменённой брони                                   | 4              | Проданный товар остаётся управляемым; нет «зависших» продаж        |
| Единый `POST items` для standalone и брони                         | 1, 2           | Убирает асимметрию API, одна логика добавления                     |

Стратегически это приводит модель заказа к отраслевому эталону (YClients): визит — живой чек, где услуги и товары живут вместе, а статус каждой строки определяет, что с ней можно делать.

## Решение 1: редактор заказа

Принцип: **статус строки определяет её изменяемость.** Заказ редактируем, пока `ACTIVE`. Фронт — одна форма, read-only секция сверху, одна кнопка «Сохранить», один `PUT` со всем редактируемым набором.

| Строка                | Фронт                                | Бэк при `PUT`                           |
| --------------------- | ------------------------------------ | --------------------------------------- |
| `CONFIRMED` (продано) | read-only, не в форме редактирования | игнорируется в diff, `id` неприкосновен |
| `DRAFT`               | редактируется свободно               | применяется                             |
| новая                 | добавляется                          | создаётся как `DRAFT`                   |
| `REVERSED`            | read-only (история)                  | игнорируется                            |

**Бэкенд.** `UpdateOrderDto` отделить от `CreateOrderDto`: убрать `confirmImmediately`/`idempotencyKey`, добавить `version` для optimistic concurrency, разрешить пустой набор (`ArrayMinSize` 0). `items` — желаемые редактируемые (draft) строки; подтверждённые во вход не входят.

**Защита от lost update.** Desired-state `PUT` удобен, но без версии даёт last-write-wins: менеджер B меняет `Shampoo x1 → x2`, а менеджер A со старой формой отправляет `Shampoo x1 + Mask x1` и незаметно откатывает количество обратно. Поэтому `Order` хранит монотонную `version`, `OrderResponseDto` отдаёт её фронту, а `PUT /orders/:id` принимает версию последнего прочитанного заказа:

```json
{
  "version": 17,
  "items": []
}
```

Перед применением diff сервер делает compare-and-bump версии внутри той же `$transaction`: `UPDATE Order WHERE id = :id AND version = :dto.version SET version = version + 1` (в Prisma — `updateMany`). Если затронуто `0` строк, версия уже изменилась и сервер возвращает `409 ORDER_CHANGED`; фронт показывает: «Заказ изменился другим пользователем. Обновите данные.» После успешного bump строка заказа удерживается транзакцией до `COMMIT`, поэтому параллельный editor-save не может применить старый desired-state. `refreshTotals` в этом flow пересчитывает суммы без повторного инкремента версии; остальные мутации заказа (добавление items, confirm/reverse, sync booking services, cleanup draft-products, void) также инкрементят `version`.

`OrdersFacade.update` применяет diff по `OrderItem.id`, а не «delete all + create again»:

1. `findInTransaction` читает заказ с items.
2. `assertActive` — заказ должен быть `ACTIVE`; **`assertDraftItems` не используется**.
3. `assertVersion(locked.version, dto.version)` отсекает явно устаревший read.
4. `incrementVersionIfCurrent(orderId, dto.version)` делает условный bump; если `count = 0` → `ORDER_CHANGED` (гонка между read и save).
5. `editable = locked.items.filter(type === PRODUCT && status === DRAFT)`.
6. Контракт входа: `items[].id?` есть только у существующей `DRAFT`-строки; `productId` обязателен у каждой строки как бизнес-атрибут товара.
7. diff `editable` vs `dto.items` по `id`: `id` есть → `update` существующего `DRAFT` (productId/qty/customUnitPrice/seller с RBAC из `assertCustomPriceAccess`); `id` отсутствует → `create` DRAFT; существующий `DRAFT id` отсутствует во входе → `delete` (draft, ссылок нет).
8. Если во вход прилетел `id`, который не принадлежит редактируемому набору этого заказа (чужая строка, сервисная строка, подтверждённая/списанная товарная строка и т.п.) → `ORDER_ITEM_IMMUTABLE`. Это defensive check для контракта фронта: locked/read-only строки вообще не отправляются в `items`, а ошибка описывает нарушение намерения — попытку изменить неизменяемую строку.
9. `refreshTotals(..., { incrementVersion: false })` считает по не-`REVERSED` → проданное остаётся в сумме, а версия уже поднята compare-and-bump шагом.
10. `ORDER_UPDATED` audit пишется в той же транзакции с `itemChanges.added/removed/changed`.

Ключ diff’а — `orderItemId`, не `productId`: identity строки остаётся identity сущности, а товар — это изменяемый бизнес-атрибут. Текущий инвариант «один товар в заказе максимум одной активной строкой» можно оставить как доменное правило (`assertProductItemsCanBeAdded`/валидация дублей), но он не должен определять способ сопоставления строк. Это оставляет архитектурный запас для будущих сценариев: один товар от разных продавцов, разные цены/скидки, партии, серийные номера, подарочный экземпляр рядом с обычным или частичный возврат. `OrderItemResponseDto` уже отдаёт `id` и `status` — фронт различает read-only/editable.

**Возврат проданной строки — отдельная операция** (`reverseItem`, reason уже есть). В редакторе возврата нет — удалить проданную строку через форму нельзя by design. Это разделяет намерения: возврат — это деньги и склад, он не должен быть побочным эффектом сохранения формы.

## Решение 2a: товары при отмене ПРЕДСТОЯЩЕЙ записи

Это отдельный от завершённой брони случай и **главная боль менеджера**. При ручном букинге товары добавляются в заказ брони как `PRODUCT/DRAFT` — склад ещё не списан, комиссия не начислена (предоплат нет). **Сейчас отмена предстоящей брони вообще не трогает заказ** (реверс в `executeCancellation` срабатывает только для `COMPLETED`). Значит `DRAFT`-товары висят в заказе отменённой брони — менеджеру приходится чистить вручную.

`DRAFT`-товар — это **намерение продать, которое ещё не свершилось**: на нём нет ни склада, ни комиссии, его можно безопасно удалить. Поэтому дефолт при ранней отмене — убрать, а не сохранить (противоположно завершённой брони, где товар уже отдан).

**Бизнес-вывод: сценарий «услугу отменили, товар всё равно продаём» возможен** (клиент забирает краску/шампунь, хотя стрижку отменил), но нечастый. Поэтому тихое автоудаление не подходит — оно отсекает этот кейс. Нужен дефолт + возможность оставить.

**Механизм (упрощённый).** Отложенный черновик не поддерживаем. При отмене/удалении брони `PRODUCT/DRAFT`-товары **всегда удаляются** вместе с отменой. Склад не трогаем (не списывался). Никакого диалога и выбора — менеджеру не нужно ничего чистить.

Важно: **«оставить = продать» было бы ошибкой.** `confirm` в момент отмены зафиксировал бы продажу, которой ещё не было (товар не передан, визит отменён заранее). Фиксация продажи — всегда отдельное осознанное действие по факту передачи товара.

Кейс «отменил услугу, товар забираю» редкий, и его **не нужно закрывать усложнением отмены**. Отмена записи и создание продажи товаров — разные операции, их не надо склеивать. Сейчас менеджер просто создаст новый standalone-заказ на товар вручную (`POST /orders`).

В дальнейшем этот редкий путь можно ускорить **отдельной фичей** — «создать заказ на товары из отменяемой записи» (предзаполнить standalone-заказ товарами брони). Она **не трогает логику отмены** и переиспользует существующий `POST /orders` — появится когда угодно позже, ничего не ломая. Архитектуру перерабатывать не придётся, потому что отмена и продажа изначально разведены.

## Решение 2b: товары при отмене ЗАВЕРШЁННОЙ брони

Бизнес-правило (стиль YClients): **при отмене визита услуги сторнируются, товары остаются проданы.** Услуга — это обещание визита, который не состоялся; товар — свершившийся переход ТМЦ (клиент ушёл с ним). Сторнировать склад по товару = нарисовать недостачу.

**Вывод: менять бэкенд-логику отмены НЕ нужно** — она уже делает правильно:

- `reverseCompletedBookingServices` реверсит строго `SERVICE/CONFIRMED`; товары `PRODUCT/CONFIRMED` остаются проданы.
- `reverseForBooking` по комиссиям фильтрует `bookingItemId IN … AND source = BOOKING` — товарные комиссии не трогаются.
- Брони только soft-delete (`deletedAt`), поэтому `Order.bookingId onDelete: SetNull` никогда не срабатывает — «осиротевших» заказов нет.

Значит проблема не в целостности данных, а в **доступности**: заказ живой и корректный, но к нему нет входа из отменённой брони.

**Что делать:**

- Фронт: открывать карточку заказа для `CANCELLED`/удалённой брони (read-only услуги + товары с кнопкой «Вернуть» → `reverseItem`).
- Опционально: аудит-событие при отмене с сохранёнными товарами (`retainedProductItemIds`) — для прозрачности.
- Никаких новых запретов, флагов или разбиения заказа на standalone.

Почему не блокировать отмену и не спрашивать флагом: клиент часто уже ушёл с товаром до решения об отмене визита; дефолт «товар остаётся продан» + ручной возврат покрывает оба исхода.

## Подтверждённые факты из кода

Проверено чтением исходников, чтобы план опирался на факты, а не гипотезы.

1. Брони только soft-delete (`deletedAt`); hard-delete брони нет нигде. `onDelete: SetNull` на `Order.bookingId` никогда не срабатывает.
2. `reverseCompletedBookingServices` реверсит **только** `SERVICE/CONFIRMED`; товары остаются `CONFIRMED` — бизнес-корректно.
3. `reverseForBooking` (→ `reverseBookingCommission`) фильтрует `bookingItemId IN … AND source = BOOKING` → товарные комиссии не трогаются. Рассинхрона нет.
4. `OrderItemResponseDto` отдаёт `id` и `status` — фронт различает read-only/editable.
5. `UpdateOrderDto` отделён от `CreateOrderDto`: принимает `version`, не наследует `confirmImmediately`/`idempotencyKey`, разрешает пустой `items`.
6. `UpdateOrderItemDto` содержит `id?`; существующие строки сопоставляются по `OrderItem.id`, новые строки создаются без `id`.
7. `update()` сейчас: `assertActive`, проверка/claim версии (`ORDER_CHANGED`), diff только `PRODUCT/DRAFT`, `ORDER_ITEM_IMMUTABLE` для попытки изменить locked/read-only строку, `refreshTotals` и `ORDER_UPDATED` audit в одной транзакции.
8. `ORDER_UPDATED` audit содержит `itemChanges.added/removed/changed`; удалённые DRAFT-строки остаются в истории через audit payload.
9. Отмена/удаление незавершённой брони удаляет `PRODUCT/DRAFT` через `removeDraftProductsForBooking`; `BOOKING_CANCELLED`/`BOOKING_DELETED` пишут `removedDraftProductItems` в той же транзакции.

## Аудит: история не теряется

Удалённые DRAFT-строки **не выпадают из истории** — все изменения с записями и заказами фиксируются в аудит-логе. Это снимает единственное возражение против hard-удаления DRAFT: держать «мёртвые» строки в таблице ради следа не нужно — след живёт в аудите. Вариант «переводить DRAFT в REVERSED» отпадает.

Условие: **каждая новая операция обязана писать аудит с деталями**, а не только итог.

Для чувствительных операций аудит является частью той же логической транзакции, что и изменение данных. Недопустимо сначала сохранить diff/totals, закоммитить, а потом пытаться записать audit через асинхронный listener: при сбое истории не будет, хотя заказ уже изменён. Также недопустимы частичные изменения строк: `delete DRAFT` и последующий `create DRAFT` живут в одном `$transaction`.

Обязательный порядок для `PUT /orders/:id`:

```text
BEGIN
read order
validate ACTIVE
claim version (UPDATE Order WHERE id AND version)
delete DRAFT
update DRAFT
create DRAFT
refreshTotals (without second version increment)
write audit log
COMMIT
```

Тот же принцип для отмены/удаления незавершённой брони: `cancel/delete Booking` + удаление `PRODUCT/DRAFT` + audit payload `removedDraftProductItems` выполняются в одном `$transaction`. Если audit write падает, откатывается и отмена/удаление, и чистка товаров.

| Операция                            | Событие                               | Состояние                                                                                        |
| ----------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Редактор (`update` на diff)         | `ORDER_UPDATED`                       | реализовано: `itemChanges.added/removed/changed` пишется вместе с diff/totals                    |
| Автоудаление DRAFT при отмене брони | `BOOKING_CANCELLED`/`BOOKING_DELETED` | реализовано: `removedDraftProductItems` пишется вместе с cancel/delete и удалением DRAFT-товаров |
| Добавление товара в заказ/бронь     | `ORDER_UPDATED`                       | реализовано для `addDraftItems`: audit пишется в той же транзакции с добавлением строк и totals  |

Существующие события заказа (`ORDER_CREATED/UPDATED/VOIDED/DELETED`, `ORDER_ITEM_CONFIRMED/REVERSED`) покрывают факт изменения; пробел — в **гранулярности payload**. Отдельное событие на удаление строки не нужно — достаточно обогатить `ORDER_UPDATED`.
