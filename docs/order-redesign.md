# Финальное ТЗ — Универсальная система продаж Booking CRM

## 1. Цель

Расширить существующий коммерческий модуль CRM, чтобы можно было продавать товары и другие коммерческие сущности:

- вместе с записью на услуги;
- во время визита;
- независимо от Booking.

При этом сохранить существующую логику календаря, зарплат сотрудников, склада и коммерческих корректировок.

**Главная коммерческая сущность — Order.**

Но Order не должен автоматически создаваться для каждой предварительной записи.

## 2. Основные бизнес-правила

### Booking

Операционная сущность, отвечающая за:
- услуги;
- время;
- клиента;
- исполнителей;
- статус;
- плановую стоимость и customPrice;
- факт оказания услуги.

### Order

Коммерческая сущность, объединяющая позиции одного согласованного расчёта с клиентом.

### OrderItem

Строка коммерческой продажи:
- `SERVICE`;
- `PRODUCT`;
- `BUNDLE`;
- `MEMBERSHIP` (в будущем);
- `CERTIFICATE` (в будущем);
- `PACKAGE` (в будущем);
- `CUSTOM`.

Все типы используют общую денежную модель, но имеют собственные правила подтверждения и исполнения.

### Ключевые ограничения

**Один Booking может иметь максимум один связанный Order.**

```text
Booking 1 → 0..1 Order
```

**Один Order может существовать без Booking.**

```text
Order.bookingId = null
```

**Обычная услуга не продаётся без Booking.**

Для `SERVICE` должна существовать связь с конкретным `BookingItem`.

Для составных услуг использовать существующую модель `ServiceBundle` и входящие в неё BookingItems.

**Товары и другие неоперационные коммерческие сущности могут продаваться без Booking.**

Отдельная продажа товара после завершения самостоятельного расчёта за визит создаёт отдельный Order без bookingId.

## 3. Основные пользовательские сценарии

### A. Онлайн-запись только на услугу

1. Клиент выбирает услугу и время.
2. Создаётся Booking с BookingItems.
3. Order не создаётся.
4. При переходе Booking в COMPLETED автоматически создаётся Order с подтверждёнными сервисными позициями.

Менеджер не выполняет дополнительных действий.

### B. Запись на услугу и товар

1. Клиент выбирает услугу и дополнительно товар.
2. Создаётся Booking.
3. Создаётся связанный Order с предварительной товарной позицией.
4. Услуги до завершения визита остаются плановыми в BookingItem.
5. Товарная позиция находится в DRAFT, пока продажа не подтверждена.
6. Когда Booking становится COMPLETED, в тот же Order добавляются подтверждённые сервисные позиции.

Простой выбор товара не означает его продажу или складское списание.

Если в будущем потребуется гарантировать наличие товара, это реализуется отдельно через складское резервирование.

### C. Менеджер добавил товар во время визита

1. Менеджер открывает Booking.
2. Нажимает «Добавить товар».
3. Товар добавляется в связанный Order, который при необходимости создаётся автоматически.
4. Менеджер подтверждает продажу.
5. Система выполняет складское списание и начисляет комиссию продавцу, если она предусмотрена.

Подтверждение товара не требует изменения Booking.status.

### D. Отдельная продажа товара

1. Менеджер открывает раздел продаж.
2. Создаёт новый Order без bookingId.
3. Добавляет товары.
4. Подтверждает продажу.

Это самостоятельная коммерческая операция.

Она не должна автоматически привязываться к существующей записи клиента.

### E. Отдельная покупка после визита

Если клиент уже закончил визит и позднее отдельно покупает товар, создаётся новый Order без Booking.

Если клиент ещё находится в рамках общего расчёта за визит, менеджер добавляет товар в существующий Order.

**Границу общего коммерческого расчёта определяет сценарий продажи, а не просто совпадение клиента или даты.**

## 4. Жизненный цикл Order

Order — общий коммерческий агрегат.

Он может содержать несколько коммерческих позиций с разными моментами подтверждения.

Не требовать проведения всего Order при продаже первого товара или завершении первой услуги.

Предлагаемые состояния:

```typescript
OrderStatus:
  ACTIVE
  VOIDED
```

В будущем можно добавить `CLOSED`, когда появится полноценный расчёт с клиентом.

Для отдельных позиций:

```typescript
OrderItemStatus:
  DRAFT
  CONFIRMED
  REVERSED
```

- `DRAFT` — предварительная позиция.
- `CONFIRMED` — подтверждённый коммерческий факт.
- `REVERSED` — позиция сторнирована с сохранением истории.

Статусы `OPEN / POSTED / VOIDED` существующего товарного модуля нужно мигрировать с сохранением обратной совместимости.

В частности, исторические POSTED-заказы не должны потерять историю проведения.

## 5. Изменения Prisma

Переиспользовать существующие `Order` и `OrderItem`.

### Order

Сохранить:
- locationId;
- bookingId nullable;
- clientId;
- currency;
- коммерческие суммы;
- историю создания и изменений.

Обеспечить уникальную связь Booking с Order:

```prisma
bookingId String? @unique
```

Это концептуальное изменение; перед миграцией проверить существующие данные и связанные отношения Prisma.

Самостоятельные заказы с `bookingId = null` должны создаваться без ограничений по количеству.

### OrderItem

Добавить необходимые поля для связи с Booking:

```prisma
bookingItemId String?
status OrderItemStatus
confirmedAt DateTime?
occurredAt DateTime?
```

Сохранять:
- источник позиции;
- snapshot названия;
- количество;
- цену;
- скидку;
- итог;
- исполнителя услуги или продавца товара;
- себестоимость товара, когда применимо.

Для `SERVICE` обязателен BookingItem, принадлежащий Booking связанного Order.

Для `PRODUCT` используется существующий ProductLocation.

Не создавать новый CatalogItem, если текущая архитектура не требует такой миграции.

## 6. Коммерческие корректировки

Подтверждённые продажи должны иметь сохраняемую историю.

Предусмотреть `OrderItemAdjustment` или аналогичный механизм.

Корректировки применяются при:
- изменении стоимости завершённой услуги;
- отмене завершения Booking;
- повторном завершении Booking;
- возврате товара;
- исправлении подтверждённой позиции.

Исходная подтверждённая позиция не должна бесследно перезаписываться.

Эффективная сумма продажи рассчитывается по подтверждённым строкам с учётом корректировок.

Необязательно создавать отдельную таблицу `OrderOperation`, если транзакционность, аудит и идемпотентность можно надёжно обеспечить более простой моделью.

## 7. Синхронизация Booking и Order

При `Booking.COMPLETED`:

1. Получить или создать Order.
2. Создать/подтвердить коммерческие строки услуг.
3. Сохранить эффективные цены BookingItem.
4. Связать коммерческие позиции с источниками.
5. Выполнить текущую логику начисления комиссий.
6. Зафиксировать результат транзакционно.

При изменении завершённого Booking:
- скорректировать соответствующие сервисные продажи;
- выполнить существующий StaffEarning CORRECTION;
- не затрагивать независимые товарные позиции.

При уходе из COMPLETED:
- сторнировать действующие начисления за услуги;
- сохранить коммерческую историю;
- не отменять подтверждённые продажи товаров.

Все повторные операции должны быть идемпотентными.

Ночной cron должен использовать тот же обработчик завершения Booking, что и ручное изменение статуса. Существующее автозавершение сохранить на этапе миграции; отдельно предусмотреть возможность отключать автоматическое признание визита состоявшимся.

## 8. Зарплаты

Не переписывать существующую систему:
- StaffCompensationPlan;
- StaffEarning;
- CORRECTION;
- PayrollPeriod;
- PayrollResult;
- версионирование планов;
- закрытые зарплатные периоды.

Для новых комиссий услуг сохранять связь с OrderItem дополнительно к BookingItem.

Использовать существующие формулы, ставки и snapshots.

Комиссии товара по-прежнему возникают при подтверждении товарной продажи.

Комиссии услуги — при COMPLETED.

Изменения стоимости и исполнителя должны создавать корректные зарплатные корректировки.

Не создавать дублирующие начисления при миграции или повторных событиях.

## 9. Склад

Переиспользовать существующий InventoryService.

Подтверждение товарной позиции:
- проверяет доступность товара;
- проверяет остаток;
- блокирует необходимые складские записи;
- создаёт SALE при trackInventory;
- сохраняет себестоимость;
- начисляет комиссию продавцу;
- фиксирует товарную коммерческую позицию.

Операция должна быть атомарной и идемпотентной.

Черновые позиции не списывают склад.

Возврат подтверждённой товарной продажи создаёт обратное движение.

Отмена Booking не должна возвращать уже проданный товар на склад.

Старый PUT, пересобирающий строки целиком, не должен удалять или переписывать подтверждённые позиции.

## 10. ServiceBundle

Использовать существующие:
- ServiceBundle;
- ServiceBundleItem;
- BookingItem;
- BundlePricingMode SUM / FIXED.

Не создавать параллельную ComboService.

Для первой реализации предпочтительно отражать коммерческую стоимость через сервисные строки BookingItems, сохраняя связь с исходным Bundle.

При фиксированной стоимости комбо необходимо проверить распределение цены между компонентами.

Не допускать двойной выручки или двойных комиссий.

## 11. Финансовая аналитика

После миграции источник коммерческих продаж — OrderItem с учётом подтверждения и корректировок.

Отдельно отображать:
- плановую стоимость записей;
- продажи оказанных услуг;
- товарные продажи;
- общую сумму коммерческих продаж.

Не считать стоимость BookingItem и соответствующую сумму OrderItem дважды.

Даты оказания услуг и даты подтверждения товарных продаж должны сохраняться отдельно от даты создания Order.

**Order не является платежом или фискальным чеком.**

Пока нет Payment, нельзя считать POSTED/CONFIRMED эквивалентом фактической оплаты.

## 12. Будущие коммерческие сущности

В перспективе универсальный OrderItem должен поддерживать:
- клубные карты;
- абонементы;
- пакеты посещений;
- сертификаты;
- произвольные коммерческие позиции.

Продажа этих сущностей может происходить без Booking.

Однако использование купленного абонемента или пакета для оказания конкретной услуги должно быть связано с Booking.

Купленное право клиента необходимо моделировать отдельно от строки его продажи.

Не реализовывать все эти механизмы сейчас. Обеспечить возможность их добавления без изменения основных отношений Booking и Order.

## 13. Payment — будущий модуль

Сейчас не требуется:
- онлайн-эквайринг;
- наличные/терминальные оплаты;
- частичные платежи;
- предоплаты;
- open balance;
- денежные возвраты.

В дальнейшем:

```text
Order
  ├── OrderItems[]
  └── Payments[]
```

Один Order может иметь несколько Payment.

Предоплата и окончательный платёж не требуют двух отдельных Order.

Корректировки стоимости смогут создавать переплату либо оставшийся к оплате баланс, когда будет введён учёт платежей.

## 14. Миграция существующего backend

Перед реализацией изучить:
- OrdersService.post/void;
- BookingsService и обработку COMPLETED;
- InventoryService;
- StaffEarning;
- PayrollService;
- cron автозавершения;
- текущие финансовые отчёты.

Миграция должна:
1. Сохранить существующие товарные Order.
2. Сохранить складские движения.
3. Сохранить StaffEarning и PayrollResult.
4. Создать коммерческие позиции исторических COMPLETED Booking.
5. Не пересчитывать старые зарплаты.
6. Не списывать товары повторно.
7. Не создавать дубли коммерческих операций.
8. Не объединять ошибочно самостоятельные заказы с Booking.
9. Проверить существующие дубликаты bookingId до добавления уникального ограничения.
10. Сверить суммы старой и новой аналитики.

Реализовывать поэтапно с совместимостью существующих API.

## 15. Основные тестовые сценарии

Обязательно проверить:

1. Создание Booking без Order.
2. COMPLETED создаёт один Order с сервисными позициями.
3. Изменение customPrice завершённой услуги корректирует коммерческую стоимость.
4. Повторный COMPLETED не создаёт дубли.
5. COMPLETED → PENDING сторнирует услуги, но не товары.
6. Запись с предварительно выбранным товаром создаёт связанный Order.
7. Черновой товар не списывается со склада.
8. Продажа товара внутри Booking добавляется к общему Order.
9. Продажа товара без Booking создаёт независимый Order.
10. Отдельная продажа после визита не привязывается автоматически к Booking.
11. Два конкурентных запроса не создают два Order для одного Booking.
12. Подтверждение товара списывает склад ровно один раз.
13. Возврат товара корректирует коммерческие и складские операции.
14. Комиссии услуг и товаров начисляются без дублей.
15. Закрытые зарплатные периоды защищены от недопустимых исправлений.
16. ServiceBundle корректно учитывает общую стоимость без дублирования.
17. Старые товарные Order продолжают работать после миграции.
18. Система работает без Payment.

## 16. Порядок реализации

**Этап 1 — аудит.** Изучить код и подготовить точный список изменений моделей, сервисов, API и миграций.

**Этап 2 — Order.** Расширить коммерческие позиции и реализовать независимое подтверждение строк, не нарушая исторические POSTED-заказы.

**Этап 3 — Booking.** Подключить автоматическое создание коммерческих строк при COMPLETED и корректировки при редактировании.

**Этап 4 — товары.** Обеспечить продажи внутри Booking и самостоятельные продажи без Booking.

**Этап 5 — Payroll и Inventory.** Интегрировать существующие механизмы без изменения зарплатных формул и складской логики.

**Этап 6 — миграция.** Перенести исторические данные, сверить отчёты, исключить двойные начисления.

**Этап 7 — тестирование и внедрение.** Проверить бизнес-сценарии, конкурентные операции и обратную совместимость.

---

## Итог

**Один Booking → максимум один Order.**

**Один Order → несколько коммерческих позиций.**

**Order без Booking → самостоятельная продажа любых поддерживаемых позиций, кроме обычных услуг.**

**Услуги → всегда через BookingItem.**

**Товары → с Booking или без него.**

**Payment → независимый будущий модуль.**

Главная задача — не перестраивать CRM, а сделать существующий Order универсальным коммерческим механизмом, сохранив простоту работы менеджеров с календарём.
