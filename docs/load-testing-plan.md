# Нагрузочное тестирование бизнес-эндпоинтов (k6, план)

Статус: план, не реализовано. Выполняется отдельной сессией после запуска стека из
`docs/replication-plan.md`.
Отклонение от решений раздела 1 — сначала правка этого документа.

Ветка: `feature/load-testing`. Каждый шаг раздела 3 — отдельный коммит, после каждого
`npm run lint && npm run typecheck && npm test` зелёные.

## 0. Цель

Узнать, с каким запасом приложение держит ожидаемый пик (десятки RPS, один VPS) и где оно
ломается первым: БД, пул соединений, CPU реплики, Redis или лимитеры. Результат — числа, а не
ощущения: p95/p99, доля ошибок и потолок RPS по каждому сценарию, записанные в
`docs/load-testing-results.md`.

Целевой запас: **расчётный пик ×5 держится в SLO, точка отказа найдена и записана (цель ≥ ×10)**.
Расчётный пик для плана — 30 HTTP-запросов/с суммарно (по долям журналов 2.1 это ≈ 7 итераций/с:
в среднем ~4 запроса на итерацию). Важно: в k6 `constant-arrival-rate` задаёт **итерации** в секунду,
не запросы — скрипты пересчитывают P в итерации по фактическому среднему числу запросов (считается
в `smoke`). Реальные числа уточнить у владельца до шага 8 (раздел 6).

Чего это **не** решает: проверку отказоустойчивости (она в разделе 4 replication-plan), нагрузку на
хостовый nginx и TLS, проверку внешних сервисов (SMTP, GCS). Пока хостинга нет, тест гоняется против
локального compose; результаты на Windows-машине, где k6 делит CPU с Docker, — нижняя оценка, а не
паспорт VPS (раздел 2.7). Когда появится хостинг, те же скрипты запускаются на сервере одной командой
со сменой профиля цели — без правок сценариев (раздел 2.10).

| Инструмент | k6, запуск в Docker (`grafana/k6`, закреплённая версия), скрипты на JS в `loadtest/`. Без установки на хост |
| Где запускать | Сейчас — локальный compose (`--profile local`). Когда появится хостинг — тот же запуск на сервере: k6 контейнером в той же compose-сети, через тот же `lb`; разница только в профиле цели `loadtest/targets/<имя>.env` (раздел 2.10). Стейдж — только по чек-листу 2.7. Прод с живыми пользователями — никогда |
| Профиль цели | `loadtest/targets/local.env`, `server.env`: адрес, разрешённые сценарии, потолок нагрузки, адрес БД для seed. Единая точка входа `loadtest/run.sh <цель> <сценарий>` с предстартовыми проверками и откатом SMTP после прогона (2.10) |
| Модель нагрузки | `constant-arrival-rate` / `ramping-arrival-rate` (открытая модель: RPS задаём мы, а не скорость ответов). `ramping-vus` только для сценария кабинета с сессией |
| Лимиты по IP | Прод-конфиг не трогаем. k6 шлёт уникальный `X-Forwarded-For` на каждую **итерацию** (journey = «один человек»; на VU нельзя: VU переиспользуются и за минуту упрутся в 300/мин) (работает на локальном `lb`, он дописывает XFF, docker-сеть доверенная). Дополнительно — уникальный телефон на каждую запись; ёмкость слотов в seed ≥ 3× ожидаемых броней (2.5). Нового флага в коде нет (раздел 2.3) |

| Тестовые данные | Отдельный seed `scripts/seed/seeds/loadtest.mjs`: отдельный бренд/локация, N мастеров/услуг, без GCS, идемпотентный, с командой очистки (раздел 2.5) |
| Токены кабинета | Один `login` в `setup()` k6 на пользователя из пула, токены раздаются VU. Refresh-cookie не нужен (токена хватает на прогон; длинный soak — `/auth/refresh` раз в N минут) |

| Наблюдаемость | Grafana (логи, `rt=`/`upstream=` из access-лога `lb`), `docker stats`, `pg_stat_activity`, `pg_stat_statements` (включается в `compose.loadtest.yaml`, 2.6), `redis-cli INFO`. Метрик Prometheus нет (раздел 5) |
| Результаты | `docs/load-testing-results.md` по шаблону 2.8, одна запись на прогон |
| L1-кэш | Решается по данным прогонов, по умолчанию «не делать». Раздел 2.9 |

## 2. Подробности

```
 k6 (docker, профиль loadtest)
    │ X-Forwarded-For: уникальный на VU
    ▼
 lb :3000 ──► api ×API_REPLICAS ──► postgres :5433 (pg_stat_statements)
                    │  └──────► redis
 worker ──► pg-boss email ──► mailpit (SMTP-приёмник, UI :8025)
 stdout ──► alloy ──► loki ◄── grafana :3200
```

### 2.1. Пользовательские сценарии (journeys) и SLO

Базовая точка: 1 VU = один «человек», проходящий цепочку. Пороги (`thresholds` в k6) считаются на
расчётной нагрузке ×1 (сценарий `load`), для ×5 допускается деградация p95 до ×2 от порога; выше —
это уже стресс, пороги не проверяем, ищем излом.

| Journey | Эндпоинты | Доля нагрузки | p95 | p99 | Ошибки |
| --- | --- | --- | --- | --- | --- |
| **A. Публичная запись** | `GET /public/booking-pages/:slug` → `GET /public/locations/:id/booking-setup` → `GET /locations/:id/calendar/public/available-slots` → (`booking-resolve`, `pricing` с вероятностью 0.5) → `POST /public/locations/:id/bookings` | 60% | чтения 300 мс, слоты 500 мс, запись 800 мс | чтения 600 мс, слоты 1000 мс, запись 1500 мс | 5xx и сетевые < 0.1%; 4xx кроме ожидаемых 409 = 0 |
| **B. Управление записью клиентом** | `GET /public/bookings/me` → `me/available-slots` → `reschedule` или `cancel` (Bearer из ответа создания) | 10% | чтения 300 мс, запись 800 мс | 600 / 1500 мс | то же |
| **C. Кабинет** | `login` (один раз) → `GET /locations/:id/calendar?from&to` → `GET /locations/:id/bookings` (пагинация, `search`) → `GET /brands/:id/clients` → иногда `POST .../bookings/manual` | 25% | календарь 400 мс, списки 400 мс, запись 800 мс | 800 / 800 / 1500 мс | 5xx < 0.1% |
| **D. Аналитика каналов** | `POST /public/booking-pages/:id/events` | 5% | 200 мс | 500 мс | 429 допустим только при превышении собственного лимита 120/мин на IP (уникальные XFF его не должны ловить) |

Дополнительно: `POST /public/locations/:id/bookings` в журнале A делается не в каждой итерации, а с
вероятностью 0.3 (остальные — «посмотрел и ушёл», как в реальной воронке); это же держит расход слотов в
пределах ёмкости seed. Лимит `login` 10/мин и access-токен 2 ч (`jwtExpirationConfig`): в `soak` токены
кабинета обновляются `/auth/refresh` не реже раза в 90 мин.

Общее правило: `http_req_failed` по всем журналам < 0.5%, `checks` > 99.5%. Пороги — стартовые;
после первого прогона `baseline` (шаг 7) пересматриваем по фактам и фиксируем в таблице решений.
В k6 пороги задаются через теги: `http_req_duration{journey:A,step:slots}` и т. д.

Не входят: `auth/register`, `confirm-email`, `reset-password` (шлют письма, `StrictRateLimit`),
OAuth, feedback, support.

### 2.2. Сценарии нагрузки

Расчётный пик P = 30 RPS (раздел 0). Все исполнители — `constant-arrival-rate` или
`ramping-arrival-rate`; `preAllocatedVUs` с запасом, `maxVUs` ограничен, чтобы не взорвать k6.

| Сценарий | Профиль | Длительность | Цель |
| --- | --- | --- | --- |
| `smoke` | 1 VU, 1–2 RPS, по одной итерации каждого journey | 1 мин | скрипт и данные корректны, все checks зелёные |
| `load` | `constant-arrival-rate` P (30 RPS), смесь журналов по долям | 15 мин | подтверждение SLO на расчётном пике |
| `stress` | `ramping-arrival-rate` 10 → 30 → 60 → 150 → 300 RPS ступенями по 3 мин, `abortOnFail` по порогам ошибок > 5% | ~20 мин | найти излом: ступень, на которой нарушается SLO и ступень, на которой растут 5xx |
| `spike` | 30 RPS → 150 RPS за 10 с → держать 2 мин → обратно 30 | 8 мин | поведение пула, очередей, восстановление без ручных действий |
| `soak` | `constant-arrival-rate` 0.5·P (15 RPS) | 2 ч (только локально, ночью) | утечки памяти (`docker stats`), рост пула соединений, рост таблиц `pg-boss`, стабильность p95 |

Дополнительные варианты (один раз на `baseline`, шаг 7):

- **cold vs warm кэш**: перед прогоном удаляются только ключи кэша (не `klendo:throttle:*`, не cron-локи;
  точный префикс подтвердить в шаге 2), первые 60 с — отдельное окно `warmup`, пороги в нём не
  проверяются. Итоговые числа — по прогретому кэшу, холодный старт фиксируется отдельной строкой
  (худший p95 после деплоя/рестарта Redis).
- **N реплик vs 1**: `load` и `stress` через `lb` с `API_REPLICAS` реплик (основной вариант, как в проде) и
  один раз с одной (`API_REPLICAS=1 bash scripts/deploy/rollout.sh api` перед прогоном, затем обратно
  без переменной; `lb` сам подхватит число реплик). Нужно, чтобы понять, что упирается: CPU api (масштабируется) или БД (нет).
- k6 ходит только через `lb`, не напрямую в `api-*`: иначе мимо остаётся балансировка и access-лог `rt=`.
- **Сброс данных между сценариями**: `seed --reset-bookings` (2.5) удаляет брони/клиентов k6, иначе слоты
  вырабатываются и растёт доля 409 — прогоны перестают быть сопоставимы. Если доля 409 > 5% — прогон
  недействителен (данные исчерпаны), это не «сервис ломается».

Порядок: `smoke` → `load` → `stress` → `spike` → `soak`. Результат `stress` — «потолок»
(последняя ступень в SLO), его делим на P, получаем реальный запас (цель ≥ ×5).

### 2.3. Лимиты запросов в нагрузочном прогоне

Глобальный `AppThrottlerGuard`: 300/мин на IP и
endpoint; `@StrictRateLimit` 10/мин, `@PublicRateLimit` 120/мин. `PublicBookingRateLimiter`: 10
попыток на телефон и 30 на IP за 10 минут. Флагов отключения нет, и **добавлять их не будем** —
ослабление лимитов в коде это риск попасть в прод.

Минимальный безопасный механизм, без изменений кода приложения:

1. **Уникальный `X-Forwarded-For`** на каждую итерацию (`10.<a>.<b>.<c>`, из `__VU` и `__ITER`).
   Лимитер берёт `req.ips[0] || req.ip` (`request-context.ts`; `trust proxy` по умолчанию `loopback, linklocal, uniquelocal`, то есть 10.x тоже «доверенный» адрес — поэтому в шаге 2 проверяем по ключам в Redis, какой адрес реально становится ключом, а не предполагаем), а локальный `lb` добавляет XFF через
   `$proxy_add_x_forwarded_for`, docker-сеть входит в доверенные подсети. Поэтому каждый VU
   попадает в свою корзину. Это работает **только** там, где порт приложения недоступен
   снаружи (локальный compose); на VPS XFF подделывается лишь при открытом порту 3000, потому
   на стейдже/проде этот приём не используется (2.7).
2. **Уникальный телефон на каждую запись** (`+37529` + 7 цифр из `__VU`/`__ITER`, формат
   проверить по `IsPhone`), иначе лимит 10/10 мин на телефон срезает тест.
3. **Первый шаг проверки (шаг 2 плана):** `curl` через `lb` серией разных XFF + `redis-cli --scan
   klendo:throttle:*` — убедиться, что корзины действительно разные. Если нет — стоп, пересматриваем
   решение (запасной вариант — очищать `klendo:throttle:*` и `klendo:booking-rate:*` между
   сценариями, но не во время).
4. **`login`**: 10/мин на IP — в `setup()` каждый пользователь логинится со своим XFF, один раз.
5. Тестовый трафик должен **упираться** в лимитер только в одном специальном отрицательном тесте
   (`ratelimit-check`: один XFF, 60 RPS, ожидаем 429 и `Retry-After`), чтобы убедиться, что
   лимитер вообще работает под нагрузкой.
6. Лимиты по IP теперь есть и в `lb`: `limit_req` 30 r/s с burst 60 плюс 10 r/min на
   `/auth/*` (см. [rate-limiting.md](rate-limiting.md#lb-лимиты-по-ip)). `lb` берёт IP из XFF
   так же, как приложение, поэтому уникальный XFF на итерацию уводит и от этих лимитов. В
   `ratelimit-check` (один XFF, 60 RPS) первые 429 вернёт nginx, без `Retry-After`. Лимитер
   приложения проверять по ответам с кодом `TOO_MANY_REQUESTS`, а не по любому 429.

Если выяснится, что XFF-подмена недостаточна, добавить флаг можно только отдельным решением с
правкой этого документа: `LOADTEST_RELAX_LIMITS=true`, действует только при
`NODE_ENV !== 'production'`, а в production приложение при его наличии **не стартует**.
В этот план флаг не входит.

### 2.4. Письма

`POST /public/locations/:id/bookings` создаёт письмо клиенту (только если передан `email`) и
уведомление персоналу через outbox → pg-boss → воркер → SMTP. Переключатель
`CLIENT_NOTIFICATIONS_ENABLED=false` (в `.env` уже false) гасит письма клиентам бизнеса, но не
письма аккаунта и, возможно, не письма персоналу (аудиторию `notifyStaff` проверить в шаге 2).

Решение: **SMTP-приёмник `mailpit`** (`axllent/mailpit`, закреплённая версия) в compose-профиле
`loadtest`, не публикующий порт SMTP наружу; UI `127.0.0.1:8025`. Профиль `loadtest` переопределяет
`SMTP_HOST=mailpit`, `SMTP_PORT=1025` для `api-*` и `worker` (переменной `SMTP_SECURE` в коде нет: TLS включается только при порте 465, порт 1025 = без TLS; транспорт всегда шлёт `auth`, поэтому mailpit запускается с `MP_SMTP_AUTH_ACCEPT_ANY=1` и `MP_SMTP_AUTH_ALLOW_INSECURE=1`) (через
`compose.loadtest.yaml`, файл-надстройка; основной `compose.yaml` не меняется). Так:

- письма в тесте доставляются «по-настоящему» (нагружается очередь и воркер, видна задержка),
  но уходят в песочницу;
- `environment` в compose сильнее `env_file: .env`, значения SMTP из `.env` (и `EMAIL_PW`) на реальный сервер не уйдут;
  защита от забывчивости: запуск k6 начинается с проверки `docker compose exec worker printenv SMTP_HOST` = `mailpit`,
  иначе отказ. Включить это в production нельзя: файл-надстройка не участвует в деплое (в шаге 2 проверить, что
  `deploy.yml` использует только `compose.yaml`);
- в тестах пользовательского сценария email указываем всегда (иначе не проверяется путь
  отправки), но домен `@loadtest.invalid`.

После прогона: `mailpit` API `DELETE /api/v1/messages` для очистки. Письма идут через pg-boss (очередь + воркер, пул 3 соединения): на 150+ RPS очередь отстаёт — это
ожидаемо, измеряем лаг очереди (`pgboss.job`, состояния `created`/`active`) и время разбора после
спада, а не требуем «письмо за секунду». Метрика «письма дошли»:
число писем в `mailpit` ≈ числу созданных броней (проверка в шаге 7).

### 2.5. Тестовые данные

Отдельный seed `scripts/seed/seeds/loadtest.mjs` (регистрация в `run.mjs`/`SEEDS`, описание в
`scripts/seed/README.md`, раздел «Add a new seed»):

- создаёт **отдельный бренд и локацию** с понятным slug (`loadtest-*`), так что к реальным
  данным разработчика не прикасаемся;
- параметры (ёмкость: мастера × слоты/день × дни ≥ 3× броней самого длинного прогона; 10 мастеров × 60 дней
  дают ≈ 10 тыс. слотов, а `soak` 2 ч создаёт больше — для него `LOADTEST_STAFF=30`,
  `LOADTEST_SHIFT_DAYS=90` или `--reset-bookings` между этапами): `LOADTEST_STAFF=10`, `LOADTEST_SERVICES=15`, `LOADTEST_CLIENTS=2000`,
  `LOADTEST_HISTORY_DAYS=90` — объёмы близки к «крупному салону» (на пустой БД кэши и планы
  запросов дают заниженные числа);
- мастера со сменами на 60 дней вперёд, привязки услуг к мастерам, опубликованная страница записи
  и виджет, открытая онлайн-запись (`assertOnlineBookingOpen`);
- пользователи кабинета: `LOADTEST_USERS=5` с подтверждённым email, правами `BOOKING`/`CLIENT`,
  пароль из `LOADTEST_PASSWORD`;
- **без GCS** (никаких картинок);
- идемпотентен: пересоздаёт только сущности с префиксом `loadtest`, повторный запуск даёт то же
  состояние (смены считаются от текущей даты, окно перегенерируется; брони k6 перед этим удаляются, иначе БД
  «толстеет» от прогона к прогону);
- `--reset-bookings` — удаляет только брони/клиентов/outbox-записи k6 в этой локации, структуру не трогает
  (быстрый сброс между сценариями);
- `--cleanup` удаляет всё созданное seed-ом (и брони, созданные k6 в этой локации);
- выводит JSON `loadtest/.data/fixtures.json` (id локации/страницы/виджета/услуг, логины) для
  k6, файл в `.gitignore`.

**Важно (найдено при проверке кода):** `scripts/seed/lib/db.mjs` читает `DATABASE_URL` **только из файла
`.env`** и игнорирует переменные окружения процесса. В `.env` сейчас стейдж (`45.87.219.81`), поэтому
команда `DATABASE_URL=... node scripts/seed/run.mjs loadtest` из первой версии плана **засеяла бы стейдж**.
В шаге 3 нужна правка `db.mjs`: приоритет у явного `--database-url`/`process.env`, а для loadtest-seed
источник URL вообще только явный (без чтения `.env`), чтобы забыть его было нельзя.

Защита от запуска не туда: seed берёт явный URL и **отказывается стартовать**, если хост не
`127.0.0.1`/`localhost`/`postgres`, без явного `--allow-remote` (стейдж — раздел 2.7). Запуск:
`node scripts/seed/run.mjs loadtest --database-url postgresql://crm:crm@127.0.0.1:5433/crm`.
Обычно его вызывает `loadtest/run.sh` с URL из профиля цели (`LOADTEST_DATABASE_URL`); на сервере
seed выполняется там же, где k6 (на VPS, а не с ноутбука), а хост БД сервера записан в профиле как
разрешённый (`LOADTEST_DB_HOSTS`), поэтому `--allow-remote` на ходу не нужен.

Брони от самого теста чистятся командой `--cleanup`, а не удалением руками.

### 2.6. k6 в Docker

- Папка `loadtest/`: `lib/` (хелперы: `xff.js`, `phone.js`, `auth.js`, `checks.js`), `journeys/`
  (`public-booking.js`, `booking-client.js`, `backoffice.js`, `channel-events.js`),
  `scenarios/` (`smoke.js`, `load.js`, `stress.js`, `spike.js`, `soak.js`, `ratelimit-check.js`),
  `README.md`, `.data/` (в `.gitignore`).
- `compose.loadtest.yaml` (надстройка, `docker compose -f compose.yaml -f compose.loadtest.yaml
  --profile local --profile loadtest ...`): сервисы `k6` (`grafana/k6:<версия>`, `profiles:
  [loadtest]`, том `./loadtest:/loadtest:ro`, сеть compose, `BASE_URL=http://lb`), `mailpit`,
  и переопределения `postgres` (`command: -c shared_preload_libraries=pg_stat_statements`; расширение
  создаётся `CREATE EXTENSION IF NOT EXISTS pg_stat_statements` в шаге 7, не миграцией приложения)
  и SMTP-переменных.
- Запуск: `docker compose -f compose.yaml -f compose.loadtest.yaml run --rm k6 run
  /loadtest/scenarios/load.js`.
- `BASE_URL` по умолчанию `http://lb` внутри сети — одинаково локально и на сервере (2.10).
  Защита: скрипт k6 в `setup()` отказывается работать, если `BASE_URL` не в белом списке
  (`http://lb`, `http://127.0.0.1:3000`) и не задан `ALLOW_REMOTE=1`; сценарий, не разрешённый
  профилем цели (`LOADTEST_SCENARIOS`), или нагрузка выше `LOADTEST_MAX_RPS` — тоже отказ.
- Сценарии не содержат ничего, привязанного к машине: адрес, множитель нагрузки, длительность и
  путь к `fixtures.json` приходят из переменных профиля цели.
- Ресурсы k6: `cpus`/`mem_limit`, чтобы не отнимал всё у api; по возможности `--no-summary` и
  `--summary-export` в файл.
- Опционально: вывод метрик `--out` в файл JSON/CSV (`loadtest/.data/<run>.json`) для разбора;
  `--out experimental-prometheus-rw` — только когда появится Prometheus (раздел 5).

### 2.7. Где запускать и защита

| Среда | Можно? | Условия |
| --- | --- | --- |
| Локальный compose (Windows) | да, основной | Ограничения контейнеров `api mem_limit 512m`, `DATABASE_POOL_SIZE=10` на реплику; k6 и Docker делят CPU — числа это нижняя оценка. Закрыть тяжёлые программы, замеры повторять 3 раза и брать медиану |
| Хостинг до запуска (будущий прод-VPS, живых пользователей ещё нет) | да, лучшее место для итоговых чисел | Профиль `server` (2.10): k6 контейнером на самом VPS внутри compose-сети → `http://lb`, XFF-приём работает так же, как локально. Своя БД или чистая БД до запуска, mailpit вместо SMTP. После прогона — `--cleanup` и возврат SMTP (делает `run.sh`) |
| Отдельный VPS-стенд (копия прода, своя БД) | да | Тот же профиль `server`. k6 с другой машины через интернет — только как отдельный прогон «снаружи» на малой нагрузке (TLS, хостовый nginx): XFF там не работает, лимиты не обходим |
| Стейдж (`45.87.219.81`, общая БД) | только с разрешения владельца | Общая БД и реальный SMTP: предварительно согласовать окно, подключить mailpit-подобный SMTP, не запускать `stress`/`soak`, `load` ≤ 0.5·P, seed только с `--allow-remote`, `--cleanup` после прогона |
| Прод с живыми пользователями | **никогда** | |

Перед любым запуском вне локального compose — чек-лист: (1) тип среды подтверждён, (2) БД не
общая либо согласована, (3) SMTP — песочница, (4) бэкап/снимок, (5) мониторинг открыт, (6) есть
кнопка «стоп» (Ctrl+C k6 / `docker compose stop k6`).

### 2.8. Наблюдаемость и результаты

Во время прогона (окна открыты заранее):

- **Grafana → «Klendo — логи»** (`127.0.0.1:3200`): 5xx/ошибки по контейнерам, `rt=` и `upstream=`
  из access-лога `lb`; по `X-Request-Id` разбор конкретной медленной запроса.
- **`docker stats`** (CPU/mem по репликам `api`, `worker`, `postgres`, `redis`, `lb`) — снимок раз в 5 с в
  файл: `docker stats --format ... > loadtest/.data/<run>-stats.txt`.
- **Postgres**: `pg_stat_activity` (число соединений: 2 api × (10 Prisma + 3 pg-boss) + worker (10 + 3) = 39 из `max_connections` 100; смотреть `count(*)` по `application_name`/`state` и `idle in transaction`. Исчерпание пула Prisma (10 на процесс) проявляется ростом `rt=` без роста CPU и 5xx по таймауту ожидания соединения — отдельная строка в результатах),
  `pg_stat_statements` (`SELECT query, calls, mean_exec_time, total_exec_time ... ORDER BY
  total_exec_time DESC LIMIT 15`), `pg_stat_statements_reset()` перед каждым прогоном.
  Требует пересоздания контейнера `postgres` (том и данные сохраняются, рестарт несколько секунд).
  Отдельный compose-проект `-p klendo-loadtest` не годится: порты 3000/5433/6379/3200 захардкожены в `compose.yaml`
  и заняты основным стеком. Принято: **один стек**, нагрузочные данные изолированы префиксом `loadtest` и
  `--cleanup`; единственное касание основного стека — рестарт postgres при первом `up` с надстройкой.
- **Cron-помехи**: `worker` запускает cron-задачи (`runsCrons`: очистка auth, подписки/биллинг и т. д.). На 15-минутном `load` влияние мало, на `soak` заметно: срабатывания отмечаем по логам `worker`; один раз `load` можно прогнать с остановленным `worker` для сравнения (письма копятся в очереди — только как справка).
- **Redis**: `redis-cli --stat`, `INFO commandstats` (число `eval`), `INFO memory`.
- **Число кэш-чтений на запрос** (для 2.9): `redis-cli INFO commandstats` до/после прогона;
  `(eval_calls_after - eval_calls_before - лимитер) / число запросов`.
- Метрики приложения (Prometheus) пока нет: раздел 5.

Результаты — `docs/load-testing-results.md`, одна секция на прогон:

```
## <дата> — <сценарий> — <среда>
- Коммит: <sha>, окружение: <CPU/RAM машины, версии>, команда запуска
- Данные: seed-параметры
- Нагрузка: <RPS/VU, длительность>
- Итог по journey: таблица p50/p95/p99, ошибки, доля 409, пороги пройдены/нет
- Потолок (для stress): ступень, где SLO нарушен; ступень, где пошли 5xx
- Ресурсы: пик CPU/mem по контейнерам, соединения БД, топ-5 запросов pg_stat_statements
- Узкое место и гипотеза; что предпринять (ссылка на задачу/коммит)
- Файлы: путь к JSON k6 и скриншоты Grafana (при необходимости)
```

Таблица «потолки» в начале файла сводит последние числа по сценариям. После любой оптимизации —
повторный прогон и новая запись, старые не переписываются.

### 2.9. Вердикт по L1-кэшу и его триггер

Анализ (раздел 5 replication-plan): L1 (`TieredCacheStore` + pub/sub) **сейчас делать не стоит**.
Замеры из контейнера: чтение кэша (EVAL) p50 ≈ 0.25 мс, p99 ≈ 1 мс; 12 чтений подряд ≈ 2.2 мс (в
pipeline 0.9 мс). Число чтений на запрос 2–12 (`booking-setup` = 12, из них 5 раз одно и то же
`location.settings`; публичный профиль = 2; слоты ≈ 7), цикла по дням/мастерам нет. Вклад кэша в
`booking-setup` ≈ 3 мс из ~16, на слотах — единицы процентов. Цена L1: pub/sub-инвалидация
между репликами, риск устаревших настроек брони/статуса подписки, гонки с refresh-ahead.
Дешёвая альтернатива сначала: мемоизация `location.settings` внутри запроса (12 → ~8, слоты 7 → ~4).

Как нагрузочные замеры связаны с решением. В каждом прогоне `load`/`stress` фиксируем:

1. Число кэш-чтений на запрос по эндпоинту (`INFO commandstats`, 2.8) и p95 Redis `eval`
   (по `redis-cli --latency` / `slowlog`).
2. Долю кэш-чтений во времени ответа горячих эндпоинтов (`booking-setup`, слоты, календарь):
   (чтений × p50 `eval`) / p50 запроса — на данных seed 2.5, а не на пустой БД.
3. CPU Redis и размеры значений (`MEMORY USAGE` крупнейших ключей) на реальных объёмах.

Триггеры для пересмотра (любой из): (а) сумма кэш-чтений > 20–30% p50 горячего эндпоинта или p99
чтения в запросе > 5–10 мс на данных seed; (б) нагрузка выросла до сотен RPS на реплику и CPU
Redis упирается; (в) Redis вынесен на другой хост/зону (RTT 1–5 мс); (г) значения выросли до
сотен КБ и парсинг JSON виден в профиле CPU. Порядок действий при срабатывании: сначала
профилирование (метрики Prometheus, раздел 5), затем мемоизация внутри запроса и/или pipeline, и
только потом L1. Если триггеры не сработали, в `docs/load-testing-results.md` пишется строка
«L1: триггеров нет» с числами.

### 2.10. Переключение на хостинг

Цель: когда появится сервер, нагрузочный тест запускается там **без правок сценариев**, одной
командой, с теми же предохранителями.

**Почему k6 на самом сервере, а не с ноутбука.** Снаружи запрос идёт через хостовый nginx: там TLS
и `limit_req`, а адрес клиента ставит nginx, так что приём с `X-Forwarded-For` (2.3) не работает,
и лимиты пришлось бы ослаблять флагом в коде. Изнутри compose-сети k6 бьёт в `http://lb` ровно как
локально: та же цепочка `lb → api` (все реплики), тот же XFF-приём, никаких флагов. Цена — k6 делит CPU
с приложением; на десятках RPS это несущественно, для `stress` k6 ограничен `cpus` (2.6), а его
потребление записывается в результаты. Отдельный прогон «снаружи» (TLS, хостовый nginx) — малой
нагрузкой и с одного адреса, только для замера накладных расходов на краю (раздел 5).

**Профили цели** — `loadtest/targets/<имя>.env`, в репозитории; секреты не хранят:

| Переменная | `local.env` | `server.env` |
| --- | --- | --- |
| `BASE_URL` | `http://lb` | `http://lb` |
| `LOADTEST_SCENARIOS` | все | `smoke,load,stress,spike,ratelimit-check` (`soak` — отдельным решением) |
| `LOADTEST_MAX_RPS` | без ограничения | потолок для `stress`, по ресурсам VPS |
| `LOADTEST_DATABASE_URL` | `postgresql://crm:crm@postgres:5432/crm` | из `DOCKER_DATABASE_URL` сервера (берётся из его `.env`, в профиле не пишется) |
| `LOADTEST_DB_HOSTS` | `postgres,127.0.0.1,localhost` | хост БД сервера |
| `LOADTEST_CONFIRM` | — | `1`: перед стартом `run.sh` печатает хост, БД и сценарий и ждёт `yes` |

**Единая точка входа** `loadtest/run.sh <цель> <сценарий>`. Одинаково на ноутбуке и на сервере
(по SSH, из каталога деплоя):

1. Подхватить профиль цели; для `server` — подтверждение.
2. `docker compose -f compose.yaml -f compose.loadtest.yaml --profile loadtest up -d mailpit` и
   пересоздать `api-*`/`worker` с SMTP на mailpit.
3. Проверки: `worker` видит `SMTP_HOST=mailpit`; сценарий разрешён профилем; БД из списка.
4. Seed (`--reset-bookings` или полный), затем `docker compose ... run --rm k6 run /loadtest/scenarios/<сценарий>.js`.
5. **Всегда в конце, даже при Ctrl+C** (`trap`): `bash scripts/deploy/rollout.sh api` и
   `docker compose -f compose.yaml up -d worker` (контейнеры снова с настоящим SMTP из `.env`; реплики API
   заменяются без простоя), `stop mailpit`, снимок результатов в
   `loadtest/.data/`. Если пропустить этот шаг, приложение на сервере осталось бы с SMTP на
   mailpit, и настоящие письма тихо терялись бы. Следующий деплой тоже вернул бы SMTP (он поднимает
   сервисы только из `compose.yaml`), но надеяться на это нельзя.

**Что сделать на сервере перед первым прогоном:** каталог деплоя уже содержит `loadtest/` и
`compose.loadtest.yaml` (приходят с `git checkout` при деплое). Образы `grafana/k6` и `mailpit`
скачиваются при первом запуске. Grafana с логами уже стоит (через SSH-туннель, `docs/logging.md`).
Пройти чек-лист 2.7 и записать в результаты среду «server, до запуска».

Пока хостинга нет, `server.env` лежит в репозитории как готовый шаблон и `run.sh` его проверяет
(сухой прогон `--dry-run`: печатает команды, ничего не запускает), чтобы переключение не стало
первым запуском непроверенного кода.

## 3. Порядок работы (коммиты)

1. `loadtest/` каркас: `README.md`, `lib/*` (xff, phone, auth, checks), `.gitignore` для `.data/`,
   `compose.loadtest.yaml` с `k6` и `mailpit` (ещё без переопределения postgres), профили
   `targets/local.env` и `targets/server.env`, `run.sh` с предохранителями, `trap`-откатом SMTP и
   `--dry-run` (2.10).
2. Проверки допущений без кода приложения: `curl` с разными XFF через `lb` + `klendo:throttle:*`
   (2.3), аудитория писем персоналу и маршрут в `mailpit`, имена полей `AvailableSlotsRequestDto`
   и обязательные поля `booking-resolve`/`pricing`, формат телефона `IsPhone`, допустимые `traffic`,
   `setGlobalPrefix`. Результат — раздел «Допущения подтверждены» в `loadtest/README.md`.
3. Отдельным коммитом правка `scripts/seed/lib/db.mjs` (явный URL важнее `.env`, тест), затем seed `loadtest.mjs` с защитой по хосту `--cleanup`/`--reset-bookings` + запись в `SEEDS`, `scripts/seed/README.md`.
4. Journey A (публичная запись) + `smoke` и `ratelimit-check`.
5. Journeys B и D, затем C (кабинет, `setup()` с логинами).
6. Пороги по таблице 2.1, сценарии `load`, `stress`, `spike`, `soak`; каждый коммит проверяется минутным `smoke`
   (скрипт собирается, пороги не падают на нулевой нагрузке).
7. Наблюдаемость: `pg_stat_statements` в профиле, скрипт снимка `docker stats`/Redis,
   шаблон `docs/load-testing-results.md`; первый прогон `baseline` (`smoke` → `load` →
   `stress`), запись результатов, пересмотр порогов.
8. Выводы: потолки, узкие места, строка про L1 (2.9), список оптимизаций отдельными задачами;
   правка раздела 5 `replication-plan.md` (ссылка на этот документ).

## 4. Проверка (обязательно руками, не только тестами)

Локально, `docker compose -f compose.yaml -f compose.loadtest.yaml --profile local --profile loadtest up -d --build`:

- [ ] `smoke` зелёный: все checks проходят, нет 4xx кроме ожидаемых 409.
- [ ] Seed идемпотентен: два запуска подряд дают одно состояние; `--cleanup` возвращает БД в
  исходное; запуск с `DATABASE_URL` на стейдж без `--allow-remote` отказывается.
- [ ] `ratelimit-check`: один XFF на 60 RPS получает 429 (лимитер работает), а 30 разных XFF на
  тех же 60 RPS — нет.
- [ ] Письма от тестовых броней попадают в `mailpit`, в реальный SMTP (`smtp.hoster.by`) ничего
  не уходит (в логах `worker` нет соединения с ним).
- [ ] `load` на 30 RPS: пороги 2.1 выполнены, `http_req_failed` < 0.5%.
- [ ] `stress`: найден потолок; зафиксировано, что ломается первым (БД/пул/CPU/Redis).
- [ ] `spike`: после спада p95 возвращается к базовому без ручных действий; очередь писем
  разгребается.
- [ ] `soak` (ночью): память контейнеров и число соединений БД не растут линейно.
- [ ] Seed не ушёл на стейдж: запуск без `--database-url` при `.env` со стейджем отказывается, а не читает `.env`.
- [ ] Основной стек не затронут (кроме одного рестарта postgres): `docker compose ps` после прогона такой же, как до; `--cleanup`
  выполнен; данные разработчика целы.
- [ ] Переключение готово без хостинга: `loadtest/run.sh server smoke --dry-run` печатает команды
  для сервера и ничего не запускает; запрещённый профилем сценарий отклоняется.
- [ ] Откат SMTP: после прогона (и после Ctrl+C посреди него) `docker compose exec worker printenv
  SMTP_HOST` снова показывает значение из `.env`, а не `mailpit`.
- [ ] `docs/load-testing-results.md` содержит запись по каждому прогону с числами, а не словами.

## 5. Вне задачи

- Метрики (Prometheus) и алерты — после них нагрузочные прогоны получат серверные p95 по
  эндпоинтам и вывод k6 в Prometheus (`experimental-prometheus-rw`).
- Нагрузочные прогоны в CI и регрессионные пороги на каждый PR.
- Нагрузка через хостовый nginx/TLS и проверка `limit_req`.
- Реализация оптимизаций, найденных тестом (мемоизация `location.settings`, pipeline чтений,
  индексы), и L1-кэш — отдельные задачи по результатам 2.9.
- Тесты отказоустойчивости под нагрузкой (останов реплики `api`/Redis) — расширение прогонов
  `spike` после шага 8, вне этой задачи.

## 6. Решения владельца и открытые вопросы

Решено (2026-11-23):

- Пока хостинга нет — гоняем локально. Рестарт локального `postgres` ради `pg_stat_statements`
  допустим (данные в томе сохраняются); нагрузочные данные — в ту же локальную БД, изолированы
  префиксом `loadtest` и `--cleanup`.
- Когда появится хостинг, переключение должно быть лёгким: раздел 2.10 (профиль `server`, тот же
  `run.sh`, k6 на самом VPS).
- Стейдж не трогаем.
- Нагрузка по умолчанию — допущения раздела 0 и 2.1 (30 RPS, доли 60/10/25/5%); это параметры
  профиля, их можно поменять без правок сценариев.

Открыто:

1. Реальный ожидаемый пик и структура трафика по журналам (уточнить до шага 8).
2. Подтвердить, что пороги 2.1 (p95/p99) приемлемы с точки зрения продукта.
3. Хостинг до запуска: можно ли прогнать `stress` на будущем прод-VPS до прихода живых
   пользователей (2.7), или для итоговых чисел нужен отдельный стенд.
