# Управление записью по клиентской ссылке

Клиенту не нужен аккаунт. Секретная ссылка даёт доступ только к одной записи: просмотр, отмена и перенос времени. Услуги, сотрудники, цены и длительности клиент менять не может.

## Выдача ссылки

`POST /public/locations/:locationId/bookings` возвращает в `responseValue` поля `id`, `token`, `manageUrl`. Ссылка доступна на экране успешной записи, даже если email не указан. Если email указан, письмо содержит полноценный URL управления.

Менеджер отдельно вызывает `POST /locations/:locationId/bookings/:id/client-token` с правом `booking.clientToken:write`. Ответ `200` содержит `{ token, manageUrl }` в `BaseResponseDto`. API проверяет принадлежность записи локации. Отправку этой ссылки клиенту менеджер выполняет самостоятельно.

Новая выдача не отзывает предыдущие ссылки. Нет клиентского восстановления доступа, ротации или одноразового использования ссылки.

## Фронтенд

Адрес ссылки: `${DOMAIN}/booking/manage#token=...`. Страницу `/booking/manage` реализует фронтенд; этот backend предоставляет API и формирует адрес.

Страница читает токен из fragment, убирает его из адресной строки через `history.replaceState`, сохраняет в памяти страницы и отправляет в `Authorization: Bearer <token>`. Если нужен доступ после перезагрузки, следует явно выбрать между повторным открытием исходной ссылки и хранением токена в пределах вкладки. Токен не передаётся в query API, логи, аналитику или сторонние скрипты. Для страницы нужны `Referrer-Policy: no-referrer` и HTTPS в production. Клиентские ответы API содержат `Cache-Control: no-store`.

| API | Назначение |
| --- | --- |
| `GET /public/bookings/me` | Данные записи, `canCancel`, `canReschedule`, `accessExpiresAt` |
| `GET /public/bookings/me/available-slots?from=2026-10-27&to=2026-11-02` | Свободное время для этой записи, даты включительно; диапазон до 62 дней |
| `POST /public/bookings/me/reschedule` | Перенос; тело `{ "startAt": "2026-10-29T14:00:00" }`, время в часовом поясе локации |
| `POST /public/bookings/me/cancel` | Отмена; тело `{ "reason": "Изменились планы" }`, причина необязательна |

Все ответы обёрнуты в `BaseResponseDto`. Перенос возвращает обновлённый `ClientBookingResponseDto`, отмена — `{ id }`. Профиль локации, адрес, часовой пояс и валюту фронтенд получает через существующий публичный профиль локации, используя `locationId`.

Идентификатор записи берётся только из проверенного токена. В клиентском ответе отсутствуют внутренние заметки, CRM clientId, идентификаторы календарных событий и внутренние составляющие цены.

## Срок доступа и действия

Доступ действует до текущего `endAt + 72 часа`. При переносе дедлайн следует за новым временем, исходная ссылка продолжает работать. JWT подписан отдельным секретом и содержит случайный `jti`; фиксированного `exp` у новых токенов нет. Срок обязательно проверяется стратегией на каждом запросе по актуальной записи в БД. Старые JWT с `exp` также проходят стандартную проверку этого поля.

Отмена и перенос разрешены только для `PENDING` и `CONFIRMED` строго до начала визита. После начала, отмены, завершения или неявки остаётся просмотр до истечения доступа. Удалённая запись или недоступная локация делают ссылку недействительной.

Перенос сохраняет сотрудников, услуги, длительности и взаимные смещения услуг, включая параллельные записи. Учитываются смены, блокировки, календарные события, сетка времени, минимальное время до записи и окно предварительной записи локации. Собственные события записи исключаются из занятости. Возможность управлять уже существующей записью не зависит от публичной видимости локации.

При сохранении сервер блокирует запись и слоты, повторно проверяет занятость и временные ограничения, затем обновляет календарь и запись одной транзакцией. При конфликте возвращается `409`; фронтенду нужно перечитать запись и свободное время. Перенос сбрасывает признак отправленного напоминания, записывается в аудит с ролью `CLIENT` и вызывает email-уведомление о новом времени, если есть email. Ссылка при этом не перевыпускается.

API принимает диапазон слотов строго в формате `YYYY-MM-DD`. Неактивные сотрудники, сотрудники без связи с услугой и пересекающиеся услуги одного сотрудника не дают доступных слотов. Перед сохранением право сотрудника выполнять услугу проверяется повторно внутри транзакции. Несуществующее местное время при переходе на летнее время отклоняется. Запрос с прежним временем не меняет запись и не отправляет новое уведомление. Ошибка подготовки уведомления после сохранения логируется и не отменяет успешный ответ о переносе.

Ошибки: `401` — недействительная или истёкшая ссылка; `403 / BOOKING_CLIENT_ACTION_UNAVAILABLE` — действия больше недоступны; `409 / BOOKING_SLOT_UNAVAILABLE` — время занято или вне разрешённых ограничений; `409 / BOOKING_CONCURRENT_UPDATE` — запись изменена параллельно.
