Удаление бренда и филиала сохраняет все связанные данные. Существующие DELETE endpoint возвращают 204 и выставляют `deletedAt`; SQL DELETE не выполняется.

Удаление запрещено, пока есть неудалённые записи в статусах `PENDING` или `CONFIRMED` с `endAt > now` — будущие или уже начавшиеся. Для бренда проверяются все его действующие филиалы. API возвращает `409 Conflict`, код `BUSINESS_HAS_OPEN_BOOKINGS` и `responseValue.openBookingsCount`. Владелец сначала отменяет записи или дожидается их завершения, затем повторяет удаление. Отменённые, завершённые записи, неявки, прошлые и мягко удалённые записи удалению не мешают. Автоматической отмены при удалении бизнеса нет.

Проверка и мягкое удаление выполняются в одной транзакции. При конфликте отметка `deletedAt` откатывается, и бизнес остаётся доступным.

У филиала два условия доступности: его `deletedAt` равен NULL и `deletedAt` родительского бренда равен NULL. Удаление бренда не меняет отметки филиалов, поэтому восстановление бренда не восстанавливает филиалы, удалённые отдельно.

Удалённый бизнес исключается из списков, профиля и новых JWT. Запросы к его данным возвращают 404, в том числе со старым JWT и под системным администратором. Публичные страницы, виджеты, клиентские ссылки и создание записей также недоступны. Автозавершение записей, начисления от автозавершения и напоминания останавливаются.

Восстановление выполняется администратором через БД, без удаления или пересоздания связанных сущностей:

```sql
UPDATE "Brand"
SET "deletedAt" = NULL,
    "updatedAt" = timezone('UTC', statement_timestamp())
WHERE "id" = 'brand-uuid' AND "deletedAt" IS NOT NULL;
```

Для филиала:

```sql
UPDATE "Location"
SET "deletedAt" = NULL,
    "updatedAt" = timezone('UTC', statement_timestamp())
WHERE "id" = 'location-uuid' AND "deletedAt" IS NOT NULL;
```

Если удалён также родительский бренд, восстановить нужно и его. Филиалы, удалённые отдельно, восстанавливаются отдельным UPDATE.

Триггер БД автоматически выставляет `restoredAt` при переходе из удалённого состояния в активное. Не очищать и не подменять это поле вручную. Миграция с триггерами обязательна: одного обновления Prisma Client недостаточно.

После восстановления записи, начавшиеся до или в момент последнего восстановления бренда либо филиала, остаются в исходных статусах для ручного решения. Фоновая задача не завершает их, не создаёт по ним заказы и не начисляет зарплату. Это предотвращает начисления за услуги, которые могли не состояться во время отсутствия бизнеса.

Сотрудник может вручную завершить, отменить или перенести такую запись. Если запись перенесена на время после восстановления, она снова подходит под обычную автоматическую обработку. Будущие записи обрабатываются в обычном порядке. Завершённая до удаления история сохраняется.

После восстановления фронтенду нужно обновить access token и профиль пользователя. Связи владельцев, сотрудников и остальные данные сохраняются; повторно выдавать доступ не требуется.

Истечение trial само по себе не выставляет `deletedAt`: здесь реализовано именно удаление пользователем или администратором. Система тарификации может отдельно вызывать удаление по своим правилам. Автоматической окончательной очистки данных нет.
