# Заказы, бронирования и товарные возвраты

В обозначениях ниже `claim:read` / `claim:write` двоеточие отделяет действие от ключа. В API это отдельные поля `claim` и `access`; в JWT — карта `claim → read | write | readWrite`. Точки группируют имена, но не выдают дочерние права.

Актуальные правила backend на 2026-10-17. Документ фиксирует инварианты домена; точные DTO и HTTP-ответы находятся в OpenAPI `/api-json`, permissions — в [карте API](./architecture/rbac-permissions-map.md).

## Модель и владение

`Order` принадлежит филиалу. Он бывает самостоятельным (`bookingId = null`) или связанным с бронированием; у бронирования не больше одного заказа. Статусы заказа — ACTIVE и VOIDED. Проведение определяется состоянием позиций, отдельного статуса COMPLETED у заказа нет.

- SERVICE создаются/синхронизируются из BookingItem при завершении бронирования. Их жизненный цикл управляется через бронирование.
- PRODUCT добавляются как DRAFT и проводятся отдельно. CONFIRMED означает проведённую продажу; REVERSED — полное сторнирование позиции.
- Чтение и изменение заказов проходят через `OrdersFacade`. Складские движения и комиссии выполняются через публичные API Inventory и Payroll в транзакции операции.
- Исполнитель, продавец и автор документа служат для операционных данных и аудита, а не для определения доступа. Permission действует на весь документ в доступном филиале.

## Редактирование и добавление товаров

Заказ редактируется в ACTIVE. Внутри него изменяются только PRODUCT/DRAFT; SERVICE, CONFIRMED и REVERSED сохраняются как история. Проведённая услуга или товар не мешает добавлению новых черновых товаров.

`PUT /locations/:locationId/orders/:orderId` принимает текущую `version` и желаемый полный набор редактируемых товарных черновиков:

- Существующая позиция сопоставляется по `OrderItem.id`; новая отправляется без ID.
- Непереданные PRODUCT/DRAFT удаляются, переданные изменяются с сохранением ID, новые создаются. Пустой `items` очищает только редактируемые черновики.
- Передача ID неизменяемой позиции отклоняется с `ORDER_ITEM_IMMUTABLE`; повторы ID/товара в одном payload запрещены.
- Устаревшая версия отклоняется с `ORDER_CHANGED`; запись использует условное увеличение версии в транзакции.
- Проведённые/сторнированные позиции не пересоздаются: их ID используются складом, начислениями и возвратами.

Добавление через `POST /orders/:orderId/items` и `POST /bookings/:id/items` дополняет заказ. Если товар уже есть в PRODUCT/DRAFT, количество увеличивается; если предыдущая строка уже проведена, создаётся новый черновик того же товара. Нельзя переносить запрет дубликатов внутри одного payload на весь исторический состав заказа.

Изменение/сброс произвольной цены требует `sale.price.override:write` вместе с базовым правом операции. Для товарной позиции отсутствие `customUnitPrice` сохраняет прежнее значение, `null` сбрасывает его. В ценовом patch бронирования пропущенное/пустое значение установленного `customPrice` может означать сброс; неизменённую цену нельзя неявно обнулять.

## Проведение, аннулирование и удаление

| Действие | Условия и эффект |
| --- | --- |
| Подтверждение товара | ACTIVE-заказ, PRODUCT/DRAFT. Выполняет продажу со складскими и комиссионными эффектами |
| Аннулирование заказа | Самостоятельный ACTIVE-заказ, обязательная причина. Сторнирует товарные эффекты и переводит заказ в VOIDED |
| Удаление заказа | ACTIVE и все позиции DRAFT; выполняет физическое удаление заказа |
| Возврат товара | Отдельная операция над проведённой товарной позицией; не удаление строки и не редактирование продажи |

Права независимы: проведение — `order.confirm`, аннулирование — `order.void:write`, удаление — `order.delete`, возврат — `order.return:write`. Автоматические складские движения и комиссии разрешённой продажи не требуют отдельных `inventory:write`/`payroll:write` у человека.

## Частичный и полный возврат

`POST /locations/:locationId/orders/:orderId/returns` создаёт возврат с `reason`, `idempotencyKey` и списком `{ orderItemId, quantity }`.

- Заказ должен быть ACTIVE, позиция — PRODUCT/CONFIRMED этого заказа.
- Количество положительное, соответствует единице товара и не превышает исходное количество минус уже проведённые возвраты.
- Возврат хранится отдельными OrderReturn/OrderReturnItem; исходная продажа не переписывается как новый факт.
- Склад получает обратные движения, комиссия сторнируется на возвращённую сумму. Итоги заказа учитывают проведённые возвраты.
- `PATCH /items/:orderItemId/reverse` возвращает весь ещё не возвращённый остаток и переводит позицию в REVERSED. После частичного возврата он не возвращает исходное количество повторно.
- Товарным API нельзя вернуть SERVICE; финансовые изменения услуги выполняются через бронирование.

Повтор финансовой операции должен сохранять исходный ключ и payload. Конфликт идемпотентности не означает разрешение автоматически повторить её с новым ключом.

## Отмена и удаление бронирования

Бронирования удаляются мягко через `deletedAt`; связанный заказ не превращается автоматически в самостоятельный. Услуги и товары имеют разные последствия отмены:

| Исходное состояние | Что происходит с заказом |
| --- | --- |
| Незавершённая запись | Черновые товарные позиции удаляются через `removeDraftProductsForBooking` |
| COMPLETED | Подтверждённые услуги сторнируются через `reverseCompletedBookingServices`; начисления за услуги также сторнируются |
| Проведённые товарные продажи при отмене/удалении записи | Сохраняются проведёнными; при необходимости оформляется явный товарный возврат |

Ручное завершение записи требует `booking.status.manage` + `order.confirm`. Отмена/удаление/откат COMPLETED требуют базового права действия над записью + `order.return:write`. Публичный клиентский токен не позволяет отменять COMPLETED.

Отмена/удаление освобождает календарные события. Возврат записи в расписание повторно проверяет доступность интервалов. Отмена записи не должна скрыто возвращать уже забранный клиентом товар.

## Идемпотентность немедленной продажи

При `confirmImmediately: true` создание заказа требует `idempotencyKey` и `order.confirm` в дополнение к `order.create`. В `creationRequestHash` хранится SHA-256 исходного намерения: филиал, клиент, явно заданное время, заметка, товары, количества, произвольные цены и продавцы. Числа/время нормализуются, товары сортируются по ID. Время по умолчанию и изменяемые цены каталога в hash не входят.

Ключ сериализуется до поиска/создания заказа. Повтор с тем же hash возвращает существующий заказ без новых движений, комиссий и аудита. Другой hash даёт 409 `ORDER_IDEMPOTENCY_CONFLICT` с `responseValue.orderId`. Изменение заказа после создания не переписывает исходный hash. Неудачное проведение откатывает заказ и hash в транзакции.

У старых продаж hash может быть NULL: исходное намерение нельзя восстановить из редактируемого заказа. Повтор такого ключа также возвращает конфликт с ID существующего заказа; требуется проверить его состояние.

## Аналитика товаров

`POST /brands/:brandId/products/analytics` требует `analytics.brand:read`.
Аналитика относится к бренду; маршрут товаров на уровне локации удалён.
Период, `keys`, сравнение с предыдущим периодом и фильтры `staffId`, `productId`,
`categoryId` сохраняются. Дополнительный фильтр `locationIds` выбирает места продаж:

- Без `locationIds` учитываются все активные локации бренда.
- Переданный список должен быть непустым, содержать уникальные UUID активных
  локаций этого бренда. `null`, чужие и недоступные локации отклоняются.
- Ответ: `BaseResponseDto<{ widgets, locationIds }>`, где `locationIds` — фактическая
  область расчёта. Интерфейс должен явно показывать «Все локации» либо выбранные
  локации и не подставлять скрыто последний открытый филиал.
- Для выбранных локаций нужна одна валюта. При разных часовых поясах необходимо
  передать общий `timezone` отчёта. Невыбранные локации не влияют на эту проверку.

Валовая прибыль суммируется по подтверждённым товарным позициям. Доля выручки —
выручка выбранных товаров, делённая на всю выручку товаров и завершённых услуг
в той же области локаций, периода и сотрудника. Фильтры товара и категории
влияют только на числитель этой доли.

Покупатели считаются уникально по всем выбранным локациям. Для повторной покупки
ищется более ранняя подтверждённая покупка в той же области локаций и с теми же
фильтрами товара, категории и сотрудника; она может предшествовать началу периода.
Анонимные покупки исключены из показателя повторных покупателей.
Проценты рассчитываются по общей выборке, а не усредняются между локациями.
Аналитика клиентов по-прежнему работает по всему бренду.

## Ответы и аудит

Операции изменения заказа возвращают `BaseResponseDto<{ id }>`, после чего актуальное состояние читается отдельным GET. Добавление товаров через бронирование возвращает ID заказа. DELETE отвечает 204 без тела. Связанный заказ доступен через поиск заказов с `bookingId`; не следует предполагать наличие `orderId` в DTO бронирования.

Изменения черновиков записываются в `ORDER_UPDATED.itemChanges` с добавленными, удалёнными и изменёнными строками. Удалённые при отмене/удалении незавершённой записи черновые товары отражаются в `removedDraftProductItems` события записи. Эти payload сохраняют смысл удалённых черновиков без пересоздания проведённых позиций.
