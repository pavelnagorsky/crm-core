# Контракты управления доступом

Реализовано в backend, 2026-10-16. Дополняет [матрицу ролей](./rbac-target.md) и [карту существующих API](./rbac-permissions-map.md). Экраны и обработчик ссылки приглашения относятся к отдельному frontend; API для них готов.

## 1. Пользовательский сценарий

Обычный путь: выбрать сотрудника или пригласить управляющего → выбрать готовую роль и филиал → скопировать ссылку. Настройки отдельных действий открывать не требуется. Рабочий профиль сотрудника без аккаунта и без приглашения остаётся полноценным участником расписания.

Дополнительный экран «Права ролей» доступен владельцу. Он показывает готовые группы действий, итоговое значение и источник: «По умолчанию», «Настройка бренда», «Настройка филиала». Включение права с зависимостями показывает все изменения перед сохранением. Локальный экран поясняет, что его настройки относятся к локальным назначениям и не ограничивают роль бренда.

Рекомендованный интерфейс назначения STAFF начинается с профиля сотрудника: область и профиль уже выбраны. Для нескольких филиалов выбираются соответствующие профили; создание пользователя для каждого филиала не требуется.

## 2. Контекст текущего пользователя

`GET /users/me/access` — авторизованный пользователь, без бизнес-permission. Возвращает доступные по JWT бренды и филиалы, прямые и наследуемые назначения, вычисленные permissions и `staffId` для связанных рабочих профилей. Разрешения B и G выдаются отдельно от L. Фильтра по выбранному бренду у этого endpoint сейчас нет.

Контекст описывает текущий аккаунт, а не всех участников бизнеса. Он не содержит токенов приглашений. Для платформенного ADMIN возвращается явный признак платформенного доступа, без создания фиктивных membership во всех брендах.

Роли и итоговые scoped permissions вычисляются при выпуске/обновлении JWT. Обычный запрос проверяет подпись, tokenEpoch через существующий кэш и claims в @Permissions; запросов в БД для проверки прав нет. После изменения назначений повышается epoch затронутых пользователей, после изменения шаблона — участников бренда. Старый JWT получает 409 TOKEN_PAYLOAD_STALE с action REFRESH_ACCESS_TOKEN. После refresh новый токен содержит актуальные права. Токен прежнего формата без permissions также требует refresh. Только операции управления доступом и принятия приглашений повторно проверяют актуальные полномочия в своей транзакции.

## 3. Настройки ролей

| Новый API | Назначение | Доступ |
| --- | --- | --- |
| `GET /brands/:brandId/access/policies` | Defaults, overrides и итоговые шаблоны MANAGER/STAFF | OWNER бренда |
| `PATCH /brands/:brandId/access/policies` | Атомарное изменение выбранных разрешений | OWNER бренда |
| `DELETE /brands/:brandId/access/policies/:role/overrides` | Сброс шаблона к встроенным значениям | OWNER бренда |
| `GET /locations/:locationId/access/policies` | Локальные шаблоны с источниками наследования | OWNER этого филиала или бренда |
| `PATCH /locations/:locationId/access/policies` | Изменение только L-разрешений локальных ролей | OWNER этого филиала или бренда |
| `DELETE /locations/:locationId/access/policies/:role/overrides` | Сброс к шаблону бренда | OWNER этого филиала или бренда |

Проверка для всех операций — `access.policy.manage` в целевой области. Пример тела PATCH:

```json
{
  "expectedVersion": 3,
  "changes": [
    { "role": "STAFF", "permission": "order.return", "value": "DENY" },
    { "role": "STAFF", "permission": "booking.export", "value": "INHERIT" }
  ]
}
```

`ALLOW`/`DENY` сохраняют boolean override; `INHERIT` удаляет соответствующую строку. Неупомянутые значения сохраняются. Дубликаты одной пары role/permission в запросе запрещены. Неизвестные permissions, OWNER, неподходящая область и недопустимые комбинации роли с permission отклоняются целиком. Номер версии предотвращает потерю изменений при двух одновременно открытых настройках; сброс тоже передаёт ожидаемую версию через `If-Match`.

Ответ GET/PATCH содержит версию и для каждой пары: встроенное значение, унаследованное значение, локальный override, итоговое разрешение, допустимость редактирования и зависимости. Для локальной политики версия учитывает также изменение родительского шаблона. При конфликте — 409, интерфейс перечитывает данные.

Удаление overrides бренда не удаляет overrides филиалов. Локальные настройки продолжают действовать поверх новых defaults. Сброс филиала сохраняет настройки бренда.

### Зависимости разрешений

Реестр содержит конечный список зависимостей, без произвольных выражений или скриптов:

- Действия `booking.*`, кроме самого `booking.read`, требуют `booking.read`.
- Действия `order.*`, кроме самого `order.read`, требуют `order.read`.
- `calendar.blocks.manage` требует `calendar.read`; `calendar.read` требует `booking.read`, поскольку календарь показывает записи.
- Изменение/импорт/экспорт клиентов требует `client.read`; действия товаров требуют соответствующего чтения товара; изменение услуг — `service.read`.
- Изменение/экспорт склада требует `inventory.read`; работа с персоналом и экспорт — `staff.read`; зарплатные изменения/экспорт — `payroll.read`.
- Изменение каналов записи требует `booking-channel.read`; изменение поставщиков — `supplier.read`.
- `sale.price.override` не является самостоятельной операцией: всегда требуется permission конкретного создания/изменения документа.

Сохранение проверяет согласованность изменяемого шаблона. UI предлагает выключить связанные действия вместе с чтением, backend не включает их молча. Изменение шаблона бренда может сделать старый локальный override неприменимым: итоговый вычислитель исключает действие, пока отсутствует необходимое чтение, а экран объясняет причину. Не требуется массово переписывать overrides всех филиалов.

Зависимости вычисляются отдельно внутри каждого источника назначения после overlay, до union. Это сохраняет правило: локальный запрет не выключает исправный брендовый источник. Неактивный из-за зависимости override остаётся сохранённым и снова действует, если зависимость восстановлена; интерфейс показывает это явно.

## 4. Участники и смена ролей

| Новый API | Назначение |
| --- | --- |
| `GET /brands/:brandId/access/memberships` | Назначения, которые вызывающий вправе администрировать |
| `GET /locations/:locationId/access/memberships` | Доступные для администрирования прямые локальные назначения |
| `PATCH /brands/:brandId/access/memberships/:membershipId` | Изменение роли прямого назначения бренда |
| `PATCH /locations/:locationId/access/memberships/:membershipId` | Изменение роли прямого назначения филиала |
| `DELETE /brands/:brandId/access/memberships/:membershipId` | Отзыв прямого назначения бренда |
| `DELETE /locations/:locationId/access/memberships/:membershipId` | Отзыв прямого назначения филиала |

Новый участник добавляется через приглашение, даже если у него уже есть аккаунт. Прямого публичного API «выдать роль произвольному userId» не требуется. Первое назначение создателю бренда и административная замена владельца — отдельные доверенные операции.

MANAGER видит и меняет только локальные STAFF-назначения в своём scope. OWNER видит назначения своего уровня и ниже. Локальный OWNER не получает управление брендовым назначением MANAGER, хотя у себя обладает большими операционными правами. Наследуемое назначение может показываться как объяснение доступа; изменить его из локального scope нельзя.

При PATCH проверяются полномочия на старую и новую роль, принадлежность назначения области, общая версия доступа бренда и ограничения STAFF-профиля. Тело: `{ role, expectedVersion, staffId? }`; `staffId` обязателен для STAFF. Версия берётся из списка memberships или политики; DELETE передаёт её в `If-Match`. Повышение STAFF до MANAGER не удаляет рабочий профиль; понижение до STAFF требует профиля этого филиала. Роль STAFF бренда отклоняется. Уникальность — одно прямое назначение на аккаунт и область.

Удаление локального назначения не означает полный отзыв доступа, если остаётся роль бренда. Удаление брендового назначения не удаляет независимые локальные назначения. Ответ интерфейса показывает сохраняющийся доступ. Для полного отзыва владелец явно отзывает все доступные ему назначения; массовый скрытый каскад не вводится.

### Владельцы — рекомендуемое завершение модели

Рекомендация для первой версии: несколько равноправных OWNER без отдельного «главного владельца». Создатель бренда получает обычную роль OWNER. Владелец может назначать, понижать и отзывать других владельцев в своём scope; подтверждение второго владельца не требуется. Это соответствует выбранному правилу управления своим уровнем и ниже, но является новым предлагаемым продуктовым решением.

Последнего OWNER активного бренда нельзя удалить, понизить или лишить аккаунта. Проверка выполняется под общей блокировкой строки бренда внутри транзакции для всех путей изменения; параллельные запросы не могут оставить ноль владельцев. Локальный OWNER не обязателен: бренд всегда имеет владельца. Самостоятельный выход владельца допускается с той же проверкой.

Платформенная замена владельца получает отдельный `POST /admin/brands/:brandId/owner-replacement`: только ADMIN, существующий целевой аккаунт, обязательная причина для аудита, точные исходное и целевое назначения. Добавление нового OWNER и понижение/отзыв заменяемого выполняются атомарно; независимых совладельцев операция не меняет. Другой платформенный ADMIN не может быть целью такой замены. Создание, понижение и удаление платформенных ADMIN через эту модель отсутствуют.

## 5. Единые приглашения

| Новый API | Назначение |
| --- | --- |
| `POST /brands/:brandId/access/invitations` | Создать приглашение с одним или несколькими назначениями |
| `GET /brands/:brandId/access/invitations` | Доступные вызывающему приглашения; фильтр филиала |
| `POST /brands/:brandId/access/invitations/:invitationId/reissue` | Новая ссылка с аннулированием старой |
| `DELETE /brands/:brandId/access/invitations/:invitationId` | Отозвать ещё не принятое приглашение |
| `POST /access/invitations/preview` | Минимальная информация по токену до входа |
| `POST /access/invitations/accept` | Принятие текущим авторизованным пользователем |

Бренд в URL — контейнер приглашения, не требование брендового членства. Для create/list/reissue/revoke проверяются `access.staff.manage`, `access.manager.manage` или `access.owner.manage` по каждой целевой роли и области. Локальный MANAGER может пригласить STAFF своего филиала через этот API. Приглашение с недоступными назначениями нельзя получить или изменить частично; списки фильтруются до пагинации.

Пример тела создания:

```json
{
  "grants": [
    { "scope": "LOCATION", "locationId": "<uuid>", "role": "STAFF", "staffId": "<uuid>" }
  ],
  "deliveryEmail": "employee@example.com"
}
```

Все назначения принадлежат одному бренду, в одной области не бывает двух grants. Для BRAND допустимы OWNER/MANAGER и отсутствуют locationId/staffId. Для локального STAFF staffId обязателен; в остальных grants профиль не назначается. Доставка письмом необязательна; `deliveryEmail` не доказывает личность принимающего и не превращает ссылку в адресное приглашение.

Рекомендованный default: одинаковая одноразовая ссылка для всех ролей, включая OWNER, срок 7 дней. Перед выдачей OWNER интерфейс явно показывает полный доступ и возможность управления совладельцами. Отдельного подтверждения принимающего аккаунта владельцем в первой версии нет. Это предлагаемое решение для простого единого сценария; адресные приглашения можно добавить отдельно при реальной потребности.

Токен — 32 криптографически случайных байта; в БД хранится хеш. Полная ссылка возвращается только при создании/перевыпуске. Токен не попадает в аудит, серверные логи и список приглашений; preview/accept передают его в теле POST. Фронтенд может получить токен из fragment ссылки и убрать его после чтения. Ограничение частоты запросов распространяется на preview/accept.

Минимальные поля хранения: brandId, issuerId, tokenHash, expiresAt, revokedAt, acceptedAt, acceptedById, version; отдельные grants содержат scope, locationId, role, staffId. Принятые назначения не ссылаются на приглашение как на условие действительности доступа; связь сохраняется только для аудита. Состояния PENDING/EXPIRED/REVOKED/ACCEPTED вычисляются из этих полей; истечение не требует cron для корректности.

Preview возвращает название бренда/филиалов, роли, срок и доступность принятия. Не возвращает списки людей, контакты, внутренние IDs профиля и операционные данные. Принятие требует явного действия после входа. Регистрация по такому сценарию создаёт аккаунт и возвращает к ссылке без обязательного собственного бизнеса.

### Транзакция принятия

1. Найти приглашение по хешу токена, затем заблокировать состояние доступа бренда и приглашение в этом порядке, перечитать его. Уже принятое тем же аккаунтом возвращает результат без повторной выдачи прав, даже после истечения срока; другим аккаунтом — конфликт. Для непринятого проверить отзыв, срок и версию. Повтор не восстанавливает впоследствии отозванное назначение.
2. Под той же блокировкой проверить актуальные полномочия автора на каждый grant и защиту платформенных ADMIN. Отзыв автора и принятие получают однозначный транзакционный порядок.
3. Через StaffService проверить принадлежность и активность STAFF-профилей, допустимость привязки к аккаунту. Нельзя занять профиль другого аккаунта или создать две привязки одного аккаунта к сотрудникам одного филиала.
4. Создать или повысить прямые назначения в запрошенных областях. Если существующая роль выше, сохранить её. Брендовое назначение не переписывается ради локального grant. Понижение возможно только явным PATCH участника.
5. Привязать STAFF-профили, отметить принятие, записать аудит и завершить одну транзакцию. Конфликт любого grant откатывает всё приглашение.

Перевыпуск сохраняет grants, заменяет токен/срок и делает старую ссылку недействительной; принятые приглашения не перевыпускаются. Изменение роли/области оформляется отзывом старого и новым приглашением. Отправка письма выполняется после успешной фиксации; её ошибка не отменяет готовую ссылку.

## 6. Профиль сотрудника и аккаунт

Рабочий профиль и membership имеют разный жизненный цикл. Удаление или деактивация профиля отзывает прямое STAFF-назначение этого аккаунта в данном филиале и отзывает непринятые приглашения с этим профилем, но не удаляет аккаунт и независимые OWNER/MANAGER-назначения. Если приглашение содержит несколько grants, оно отзывается целиком, без скрытого изменения состава. Отдельный статус приостановленного membership не вводится. Деактивация не стирает исторические записи, продажи и начисления.

Повторная активация рабочего профиля сама по себе не восстанавливает отозванный доступ: управляющий явно выдаёт его снова. Перепривязка к другому аккаунту проходит через отзыв прежнего STAFF-доступа и новое приглашение; обычный `staff.manage` не принимает произвольный userId. STAFF одного филиала не получает соседний филиал через совпадение имени, телефона или профиля.

## 7. Границы модулей

`AccessModule` владеет членствами, overrides и приглашениями, экспортирует операции формирования claims и управления доступом. Его чистый вычислитель остаётся приватным. Модуль не импортирует StaffModule, BrandModule, LocationModule или AuthModule. При загрузке собственных membership он использует связанные Brand/Location для определения активных областей и наследуемых филиалов; отдельных методов `resolveAccessBrands` / `resolveAccessLocations` нет.

`AccessManagementModule` — слой сценариев и новых controllers: импортирует AccessModule, AuthModule и публичные сервисы Staff/Brand/Location/User, проверяет существование областей и связывает доменные операции в транзакции. AuthModule использует AccessModule для формирования claims; guard проверяет готовый JWT. AccessModule не зависит от AuthModule через NestJS imports. Старые invitation-маршруты STAFF размещаются в этом слое как временные aliases: StaffModule не должен импортировать AccessManagementModule.

StaffService выполняет привязку/деактивацию собственного профиля; AccessService выполняет назначение/отзыв членства в переданной транзакции. Создание бренда вызывает операцию назначения первого OWNER в той же транзакции. Контекст транзакции не даёт вызывающему права напрямую читать чужие таблицы. Для исключения гонок бизнес-проверки и записи повторяются в транзакции, порядок блокировок фиксируется: бренд → приглашение/назначения → профили. Фактическое получение блокировок в acceptance следует этому порядку, даже если предварительно токен был найден без блокировки.

Для L-проверки вызывающий доменный сервис получает существующий филиал и его brandId через публичную операцию LocationService и передаёт AccessService доверенную область `{ brandId, locationId }`. Нельзя брать эту пару только из запроса клиента или читать Location внутри AccessModule. B/G-проверка получает brandId из проверенной области операции. Декоратор содержит требование, но не подменяет проверку принадлежности документа: если guard ещё не располагает разрешённой областью, окончательная проверка выполняется сервисом до изменения/выдачи данных. Предпочтителен явный сервисный вызов, а не новая цепочка модулей ради универсального guard.

Для сериализации изменений Access хранит собственную строку состояния на бренд, создаваемую с первым назначением, а не читает таблицу Brand. Блокировка «строки бренда» в правилах владельцев и приглашений означает эту строку состояния доступа. Увеличение её revision отражает изменения назначений/политик; до появления межзапросного кеша это служит контролем конкурентных обновлений и диагностикой.

Передача роли/permissions от клиента не считается доверенным контекстом. Обычные права endpoint проверяет @Permissions. Условные проверки выполняются в контроллере по JWT. Сервисы операций получают аудит, данные документа и, где результат зависит от вычислений, конкретные флаги (`canOverridePrice`, `canCreateClient`, `canComplete`); JWT и отдельного контекста доступа в них нет. Изменение сохранённого документа между проверкой и записью отклоняется под транзакционной блокировкой. Финансовые проверки не зависят от AuditActorRole. Системные jobs и клиентский booking token имеют отдельные явные сценарии, не превращаются в OWNER.

## 8. Финансовые эффекты и существующие ответы

Права относятся к целому документу; проверки продавцов и принадлежности отдельных строк отсутствуют. При этом отдельные HTTP-пути могут выполнять одно финансовое действие:

- Ручное завершение записи, которое проводит услуги заказа, требует также `order.confirm`.
- Отмена/удаление завершённой записи или возврат её статуса назад, которые сторнируют проведённые услуги, требуют также `order.return`.
- Эти условия определяются сохранённым состоянием и планируемым переходом внутри транзакции. Отсутствие права отклоняет весь запрос до записи изменений. Для непроведённой записи финансовое permission не требуется.
- Настройка «Запретить возвраты» таким образом действует и через бронирования. Запрет `order.void` относится к аннулированию целого заказа; возврат и отмена бронирования — самостоятельные действия с собственными правилами.
- Автоматическое завершение записей, расчёт комиссий и складские движения не требуют назначения человеку payroll/inventory permissions. Доверенная системная операция сохраняет бизнес-валидацию и аудит.
- При создании нового клиента из ручной записи/заказа требуется `client.create`; выбор существующего доступного клиента остаётся разрешённым. Автоматическая регистрация клиента через публичную запись — отдельный публичный сценарий.

Это добавляет проверки действий к существующим сценариям, без новой модели владения документом или переделки расчётов.

Подтверждённые последствия сохранения существующих DTO:

| Ответ | Уже присутствующие поля | Следствие целевого чтения |
| --- | --- | --- |
| [OrderItemResponseDto](../../src/modules/orders/dto/order-item-response.dto.ts) | unitCostSnapshot, lineCostSnapshot | STAFF с order.read видит себестоимость, если она заполнена |
| [StaffResponseDto](../../src/modules/staff/dto/staff-response.dto.ts) | phone, email, taxId, employeeNumber, payoutMethod, payoutNote | STAFF с staff.read видит контакты, налоговые данные и заметку о выплате; это не доступ к расчётным листкам |

Сохранение этих полей согласовано. Backend проверяет действия, существующие DTO не маскируются по ролям. Frontend ограничивает страницы STAFF; скрытие страницы не является запретом чтения соответствующего поля через разрешённый API.

Агрегаты и вложенные ответы проверяются по содержимому: аналитика с payroll-данными дополнительно требует `payroll.read`, со складскими данными — `inventory.read`. При отсутствии дополнительного права весь такой запрос отклоняется; новые частичные DTO не вводятся. Файлы общей медиатеки не должны позволять менять защищённую сущность удалением её вложения: удаление используемого файла отклоняется, пока владеющий домен не разрешил отвязку.

## 9. Ошибки, ответы и проверка реализации

Недостаток permission — NestJS ForbiddenException, отсутствие ресурса в заданной области — NotFoundException. Состояния приглашения, последнего владельца, конфликт версий и недопустимые настройки — записи ErrorCode и AppException с подходящим HTTP-статусом. Подклассы исключений и строковые сообщения AppException не добавляются.

Ответы новых endpoints оборачиваются в BaseResponseDto; DELETE возвращает 204 без тела. Списки участников/приглашений используют PaginationRequestDto/PaginationResponseDto. DTO, enums, interfaces, guards и decorators располагаются в собственных файлах и соответствующих каталогах. Сервис не возвращает transport DTO.

Проверки реализации: defaults без overrides; union источников; локальное наследование; запрет недопустимого повышения; доступ к общим справочникам; запреты на все пути финансовых действий; конкурентное принятие/отзыв приглашения; защита последнего OWNER; отзыв при действующем JWT; деактивация STAFF; существующие доменные регрессии. Перед миграцией провести аудит BrandMembership со STAFF и профилей без корректной связи с аккаунтом; автоматического повышения до MANAGER не делать.

## 10. Подключение и миграция

- Новые access endpoints используют `BaseResponseDto.responseValue`. GET policies возвращает `{ version, entries }`, где entry содержит `role`, `permission`, `defaultAllowed`, `inheritedAllowed`, `override`, `allowed`, `configurable`, `dependencies`.
- `GET /users/me/access` возвращает `{ platformAdmin, scopes }`. В каждом scope есть `brandId`, `locationId`, `directRole`, `inheritedRole`, `staffId`, `permissions`, `sharedPermissions`. UI строит навигацию по этим permissions. Для ADMIN флаг платформенного доступа действует без перечисления всех брендов.
- Создание/перевыпуск приглашения возвращает `{ invitation, token, url }`. Ссылка имеет вид `<frontend.domain>/invitation#token=...`. Frontend сохраняет token через регистрацию/вход, показывает preview, затем отправляет POST accept. Token не помещается в query backend и не возвращается в списках приглашений. Срок — 7 дней, ограничение preview/accept — 30 запросов в минуту на IP в пределах процесса.
- Изменения доступа сериализуются через `AccessState` бренда. Его общая `revision` используется как `version` для политик и memberships; изменение приглашения тоже может вызвать 409 в уже открытом редакторе. Нужно перечитать состояние. Права берутся из JWT; после смены роли или политики клиент обновляет токен по TOKEN_PAYLOAD_STALE.
- Удаление STAFF-membership освобождает связь профиля с аккаунтом для нового приглашения. Деактивация профиля делает это при отзыве STAFF; самостоятельные OWNER/MANAGER остаются. История операций и профиль сохраняются.
- Старые маршруты создания и принятия staff-приглашений перенаправлены на единый механизм. Старое поле `expiresAt` принимается для совместимости, но срок новой ссылки всегда 7 дней. Публичный клиентский token не позволяет отменять уже завершённую запись; финансовое сторнирование выполняет сотрудник с `order.return`.

Миграция: `src/database/migrations/20261016120000_action_permissions/migration.sql`. Она выполняется одной транзакцией. Перед применением должны отсутствовать STAFF бренда, активные бренды без OWNER, STAFF филиала без активного связанного профиля и дубли профилей одного userId в филиале. Миграция останавливается при несовместимых данных: автоматического повышения ролей или выбора владельца нет. Непринятые старые StaffInvitation отзываются, поскольку у них нет надёжной информации об авторе; их нужно выдать заново. Используемые файлы получают FK Restrict, чтобы удаление файла не обходило запрет изменения карточки.

Обычное развёртывание после проверки данных: `npx prisma migrate deploy`, `npm run db:generate`, `npm run build`. Настроенная удалённая БД при разработке не изменялась; миграция проверена на отдельном локальном PostgreSQL.

Проверки: `npm test`, `npm run lint`, `npm run build`. Интеграционный набор запускается после сборки: задать `RBAC_TEST_DATABASE_URL` на отдельную локальную базу с именем, заканчивающимся на `_test`, применить схему с миграциями и выполнить `npx vitest run --config vitest.config.e2e.ts test/access.e2e-spec.ts`. Тест использует собранный NestJS из `dist`, отключает уведомления и создаёт отдельные UUID-данные; без переменной пропускается. Он не предназначен для рабочей БД. Включены проверки отсутствия запросов к данным авторизации на обычном API, обеих областей складского перемещения и конкурентного изменения статуса записи.
