# Роли, permissions и области доступа

Актуальная модель backend на 2026-10-17. Реестр содержит 58 permissions; роли работают без overrides. [Карта API](./rbac-permissions-map.md), [контракты управления доступом](./rbac-contracts.md). Источники defaults и правил — `Permission`, `PERMISSION_REGISTRY` и `PermissionCalculator`.

## 1. Принятые принципы

- Роли фиксированы: `OWNER`, `MANAGER`, `STAFF`. Каждая роль — набор permissions.
- Бренд допускает `OWNER` и `MANAGER`; филиал допускает все три роли. `STAFF` бренда не назначается.
- Роль бренда действует во всех активных филиалах, включая новые. Локальная роль расширяет унаследованные права.
- `MANAGER` бренда + `OWNER` филиала А допустимы: в А пользователь имеет права владельца, в остальных филиалах — управляющего. Права владельца наверх не распространяются.
- Назначение роли сразу даёт готовый набор прав. Настройка permissions не является частью обязательного onboarding.
- Авторизация относится к действию над документом целиком. Ответственного за документ не добавляем, собственность строк не проверяем, `own/any` не вводим.
- Если STAFF разрешён возврат, он может вернуть любой допустимый заказ доступного филиала, включая смешанный заказ нескольких исполнителей.
- Клиенты и товары бренда доступны для чтения всем участникам этого бренда, включая пользователей только с локальным членством. Другие бренды недоступны.
- Цены в календаре не скрываются. Дополнительные варианты DTO по ролям ради этой модели не вводятся.
- Состояние документа, остатки, допустимые переходы, принадлежность сущностей филиалу и прочие бизнес-правила проверяются независимо от permission.
- Платформенный `ADMIN` имеет административный доступ, но не может менять аккаунт, роли или доступ другого платформенного `ADMIN` через административные операции.

## 2. Области разрешений

| Область | Обозначение | Правило |
| --- | --- | --- |
| Управление брендом | B | Требуется назначение на бренд; локальные роли не подходят. |
| Общие данные бренда | G | Подходит назначение на бренд или его филиал с нужным permission. Это явное правило для общего каталога и клиентской базы. |
| Операции филиала | L | Учитываются права роли бренда и прямой роли этого филиала. |
| Собственный аккаунт | U | Текущий авторизованный аккаунт; бизнес-роль не нужна. |
| Публичный/специальный сценарий | P | Существующие условия публичной записи, OAuth, refresh/email/client token. |

Область задаётся в описании permission и при его проверке. Нельзя определять её только по наличию `brandId` в URL: чтение каталога G и изменение бренда B имеют разные правила.

Сервер проверяет фактическую принадлежность объекта. Permission на филиал А не разрешает запросить заказ филиала Б через подстановку ID. Глобальный ADMIN также не отменяет бизнес-валидацию.

Для G доступ к общей карточке клиента не открывает записи и заказы других филиалов. Общий каталог товаров остаётся существующим каталогом бренда; локальные копии товаров не вводятся.

## 3. Матрица по умолчанию

OWNER имеет все разрешённые действия в своей области и не настраивается. Ниже приведены конкретные стартовые значения для MANAGER и STAFF; основные продуктовые решения перечислены в разделе 9.

В колонке «Настройка» указаны роли, для которых владелец может включить/выключить действие. `—` означает неизменяемое правило этой модели. «Да» не гарантирует успешное выполнение операции с недопустимым состоянием документа.

Создание записи/заказа с произвольной ценой требует базового разрешения создания и `sale.price.override`. Изменение такой цены требует базового разрешения изменения и `sale.price.override`. Сохранение существующей цены без изменения не должно само по себе требовать дополнительного права. Эта проверка относится к полю финансового действия, а не к принадлежности строки сотруднику.

Одинаковое действие должно проверяться во всех путях вызова: например, добавление товара через `/bookings/:id/items` и `/orders/:orderId/items`. Для добавления товара к бронированию проверяются `booking.read` и `order.update`; изменение самого бронирования не требуется, если оно не производится.

Ручное завершение записи с проведением услуг также требует `order.confirm`; отмена, удаление или откат статуса проведённой записи со сторнированием — `order.return`. Это проверка действия по состоянию целого документа, без принадлежности строк. Подробности и границы автоматических операций описаны в [контрактах](./rbac-contracts.md#8-финансовые-эффекты-и-существующие-ответы).

`staff.manage` управляет рабочим профилем, но не назначениями ролей, аккаунтом или перепривязкой профиля. Приглашение и привязка пользователя проходят через единый сценарий доступа. Деактивация профиля не снимает независимую роль OWNER/MANAGER.

Первая версия закрывает STAFF общие зарплатные endpoints. Индивидуальные расчётные листки не проектируются как обязательная часть этого изменения.

Чтение STAFF не предполагает новый набор скрываемых полей. Перед открытием существующего endpoint проверяется его полный DTO: например, разрешение чтения заказа может раскрывать себестоимость, если она включена в ответ. Такие последствия явно фиксируются при привязке API к матрице, а не маскируются обещанием «только розничные цены».

## 4. Что можно настроить

Владельцу показываются действия понятными группами: «Записи», «Продажи», «Клиенты», «Товары», «Склад». Технические ключи permissions в пользовательском интерфейсе не нужны.

Возможны три значения: «Наследовать», «Разрешить», «Запретить». После создания бизнеса все значения наследуются, никаких записей overrides не требуется.

- OWNER не настраивается: полный доступ сохраняется.
- OWNER бренда меняет шаблоны MANAGER и STAFF своего бренда. Шаблон STAFF бренда — настройка для локальных назначений STAFF, а не новая брендовая роль.
- OWNER филиала меняет локальные шаблоны MANAGER и STAFF только для L-разрешений.
- Настройки G и B меняет только OWNER бренда: локальный шаблон не может выдать общее право с эффектом на всю сеть.
- Настройка не создаёт членство и не открывает другую область.
- Настраиваются только комбинации permission/role из колонки «Настройка». Сервер проверяет этот список.
- STAFF нельзя выдать управление ролями, зарплатами, настройками бизнеса, каталогом или складскими документами.
- MANAGER нельзя выдать управление OWNER/MANAGER, настройками бизнеса или шаблонами permissions.
- Пользовательские роли и персональные исключения не вводятся.

Правила совместимости проверяются при сохранении. Например, включение `order.return` требует `order.read`, а `booking.update` — `booking.read`. UI показывает необходимые сопутствующие изменения; backend отклоняет несогласованный набор. Выключение чтения при оставленных изменяющих разрешениях не должно создавать скрытый обход через API. Зависимости применяются также при вычислении каждого источника до union: несовместимый локальный override после изменения шаблона бренда остаётся сохранённым, но не даёт разрешения. Точный порядок описан в контрактах.

Сброс локальных настроек удаляет локальные overrides и возвращает наследование бренда. Сброс настроек бренда возвращает встроенные значения. Эти действия должны иметь разные подписи.

## 5. Как вычисляется доступ

Для каждого permission хранятся область, разрешённые роли, default и возможность настройки. OWNER имеет полный набор своей области. Пример именования enum: `Permission.ORDER_RETURN`; ключ для хранения и API — `order.return`.

Для роли R встроенные значения обозначены D(R), переопределения бренда — B(R), филиала — L(R). Операция overlay заменяет только явно заданные значения, отсутствие значения означает наследование.

```text
Прямое назначение бренда:
  permissions = overlay(D(role), B(role))

Прямое назначение филиала:
  L-permissions = overlay(overlay(D(role), B(role)), L(role))

Доступ к операции филиала:
  разрешения брендового назначения для этой операции
  UNION разрешения прямого локального назначения
```

Локальный запрет влияет на локальный источник разрешения. Он не отменяет разрешение из брендового назначения. Например, MANAGER бренда продолжает иметь право возврата, даже если локальный шаблон MANAGER запрещает его местным управляющим. Изменить брендовый источник может только OWNER бренда.

Для G учитывается разрешение соответствующей роли по D+B и наличие подходящего членства. L-overrides для G не принимаются. Для B учитываются только брендовые назначения. До объединения источников применяются неизменяемые границы области и платформенные ограничения.

Отсутствие разрешения или неизвестный ключ означает отказ. Защищённый endpoint должен явно объявлять permission; отсутствие metadata не даёт доступ.

## 6. Хранение и архитектура

Существующие `BrandMembership` и `LocationMembership` остаются источниками назначений. Новая логика запрещает создание BrandMembership со STAFF. Перед миграцией нужно проверить существующие данные и определить перенос таких назначений в локальные роли с корректными профилями; молча повышать их до MANAGER нельзя.

Реализованные компоненты:

- `Permission` — один enum в `enums/`.
- Реестр permissions: область, defaults, настраиваемые комбинации и зависимости.
- Таблицы overrides отдельно для бренда и филиала, с уникальностью `(scopeId, role, permission)` и значением `allowed: boolean`. Отсутствие строки означает наследование. Отдельные таблицы не требуют nullable scope-ключей и неоднозначной уникальности.
- Чистый вычислитель permissions без DB и cross-module вызовов.
- Публичный сервис доступа, владеющий членствами и overrides.
- Декоратор `@Permissions` для действий B/G/L; условные проверки выполняются в контроллере.

Модули документов продолжают владеть своими таблицами. Guard/сервис доступа не запрашивает заказы, записи или сотрудников напрямую: их принадлежность проверяет владеющий сервис. Контроллер проверяет claims из `TokenPayloadDto`. При проверке по сохранённому состоянию он передаёт сервису загруженный документ; сервис сверяет состояние под блокировкой и возвращает 409, если оно изменилось. Бронирования и склад не получают JWT и не вызывают `assertPermission`. Расчёт цены и создание записи получают только конкретные флаги `canOverridePrice`, `canCreateClient`, `canComplete`, поскольку результат зависит от сохранённой цены, существования клиента или рассчитанного времени окончания. `AuditActorRole` больше не участвует в решении о доступе.

Не требуется переносить расчёт слотов, складские движения, возвраты, payroll или DTO-маппинг в модуль авторизации. Изменения сосредоточены в проверках доступа и сценариях управления участниками.

Permissions вычисляются при выпуске и обновлении JWT и сохраняются в подписанном payload по областям B/G/L. PermissionGuard проверяет готовые claims без повторной загрузки назначений. Отдельный TokenEpochGuard читает User.tokenEpoch из БД на авторизованном запросе; увеличение версии отзывает ранее выданные access JWT и сохраняется после перезапуска. Управление доступом дополнительно проверяет актуальные полномочия в транзакции.

Сохраняется существующий [TokenEpochRegistryService](../../src/modules/auth/services/token-epoch-registry.service.ts): проверка сохранённой в БД версии, 409 TOKEN_PAYLOAD_STALE и обновление JWT. Смена роли, принятие приглашения и отзыв STAFF повышают epoch затронутого пользователя в той же транзакции, что и изменение доступа; изменение шаблона повышает epoch участников бренда в своей транзакции. Создание филиала обновляет токены брендовых участников. При изменении встроенных defaults при развёртывании нужно инвалидировать затронутые токены; сами claims меняются при следующем выпуске.

Для текущего аккаунта реализован `GET /users/me/access` с доступными областями и вычисленными permissions. Это подсказка для интерфейса, сервер проверяет каждый запрос самостоятельно. При отзыве прав устаревший интерфейс получает отказ и обновляет контекст.

## 7. Единые приглашения и управление участниками

- Один сценарий приглашения для OWNER/MANAGER/STAFF. Главный результат — ссылка, письмо является дополнительным способом доставки.
- Пользователь может ещё не существовать. После регистрации/входа возвращается к приглашению; создание собственного бренда не требуется.
- Приглашение хранит роль, область, автора, срок, хеш токена и принимающий аккаунт. Для STAFF — также профиль сотрудника филиала.
- Несколько назначений одному человеку в рамках бренда можно оформить одним приглашением и применить атомарно.
- Переход по ссылке показывает минимальные сведения, но не принимает приглашение автоматически.
- При принятии сервер повторно проверяет действительность приглашения и текущие полномочия автора на каждое назначение.
- Одноразовость обеспечивается атомарно: повтор тем же аккаунтом идемпотентен, другим — отклоняется.
- Принятие не понижает существующую роль и не перепривязывает профиль другого пользователя.
- Изменение назначаемой роли/области и перевыпуск ссылки делают старый токен недействительным.
- Отзыв доступа автора лишает силы ещё не принятые приглашения, которые он больше не имеет права выдавать. Уже принятые назначения автоматически не удаляются.
- STAFF связан с профилем филиала. OWNER/MANAGER могут существовать без рабочего профиля.
- У активного бренда остаётся хотя бы один OWNER; локальный OWNER не обязателен при наличии владельца бренда.
- Все выдачи, изменения и отзывы доступа, overrides и административные замены владельца записываются в аудит.

Совладельцы равноправны и управляют друг другом в своём scope с защитой последнего OWNER бренда. Приглашение OWNER использует тот же механизм одноразовой ссылки. Сроки, контракты и конкурентные проверки описаны в [контрактах](./rbac-contracts.md).

## 8. Привязка к существующим API

Сопоставление бизнес-маршрутов с permissions, дополнительные проверки и специальные сценарии приведены в [карте API](./rbac-permissions-map.md). Примеры:

| API | Проверка |
| --- | --- |
| `GET /brands/:brandId/clients` | G: `client.read`, включая локальных участников бренда |
| `GET /brands/:brandId/products` | G: `product.read` |
| `PUT /brands/:brandId/products/:productId` | G: `product.catalog.manage` |
| `PUT /locations/:locationId/products/:productId` | L: `product.location.manage` |
| `GET /locations/:locationId/calendar` | L: `calendar.read` |
| `PUT /locations/:locationId/bookings/:id` | L: `booking.update`; при изменении произвольной цены также `sale.price.override` |
| `POST /locations/:locationId/bookings/:id/items` | L: `booking.read` + `order.update`; при соответствующем вводе также `sale.price.override` |
| `POST /locations/:locationId/orders/:orderId/returns` | L: `order.return`; без проверки продавцов отдельных позиций |
| `PATCH /locations/:locationId/orders/:orderId/status` | L: `order.void`; AuditActorRole не определяет доступ |
| `GET /locations/:locationId/payroll/periods` | L: `payroll.read`; STAFF по умолчанию и по допустимой настройке доступа не имеет |
| `PUT /locations/:locationId` | L: неизменяемое owner-разрешение `location.settings.manage` |
| `DELETE /brands/:brandId` | B: неизменяемое owner-разрешение `brand.settings.manage` |

Публичные endpoints и специальные токены не получают бизнес-permissions автоматически. Сценарии создания нового бренда и собственного профиля остаются доступны авторизованному пользователю без существующего бизнес-членства.

Важно проверить endpoints, возвращающие данные сразу нескольких областей: текущий список брендов для локальных участников, список локаций бренда, агрегаты, вложенные карточки и аудит. Доступ к G не должен случайно открывать весь список операций сети. Для `GET /brands` нужно показывать также бренды локальных участников с разрешёнными им филиалами; это навигация по доступам, а не выдача `brand.read`.

## 9. Продуктовые решения первой версии

Реализация использует следующие значения. Сохранение полей существующих DTO отдельно согласовано: лишние страницы для STAFF скрываются на уровне UI.

1. STAFF по умолчанию может менять все блокировки филиала; можно выключить `calendar.blocks.manage`, сохранив работу с записями.
2. STAFF по умолчанию читает все заказы филиала. Не добавляется фильтр «свои». Проверено: текущие DTO открывают себестоимость заказа, а карточка сотрудника — контакты, налоговые данные и заметки о выплатах. Сохранение этих ответов без изменений означает доступ STAFF к этим полям; это явно зафиксировано в контрактах.
3. STAFF по умолчанию не меняет произвольную цену, не скачивает XLSX, не удаляет бронирования и не выпускает клиентские токены; это настраиваемые действия. Полный JSON-список через `isExport` остаётся доступен по праву чтения.
4. Локальный OWNER может редактировать общий каталог бренда через G. Это влияет на общий справочник всех филиалов.
5. MANAGER по умолчанию ведёт склад и локальные настройки товара; общий каталог и упаковки ему закрыты, OWNER бренда может открыть их настройкой.
6. Взаимное снятие равноправных OWNER: свободное управление друг другом в своём scope без подтверждения второй стороны. Последний OWNER бренда защищён; создатель не имеет скрытого старшинства.
7. Приглашение OWNER: обычная одноразовая ссылка, как для STAFF/MANAGER, с явным объяснением полномочий перед выдачей. Срок всех приглашений — 7 дней; подтверждение контакта не вводится как отдельное условие этой модели.

Настраиваемые действия меняются владельцем через API политик; для обычного подключения сотрудников эта настройка не требуется.
