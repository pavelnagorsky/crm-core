# Роли, permissions и области доступа

Модель backend на 2026-10-18. Реестр содержит 53 permissions. [Карта API](./rbac-permissions-map.md), [контракты управления доступом](./rbac-contracts.md). Источники правил — [реестр](../../src/modules/access/constants/permission-registry.ts) и [вычислитель claims](../../src/modules/access/calculators/permission.calculator.ts).

## 1. Роли и области

- `STAFF` — мастер: свои записи, смены, результаты визитов и начисления.
- `MANAGER` — администратор/управляющий: работа филиала, клиенты, продажи, графики, склад, отчёты и возвраты.
- `OWNER` — владелец: все действия своей области, настройки, доступы и финансовые решения. `payroll.manage` доступен только OWNER.
- В бренде назначаются OWNER/MANAGER, в филиале — все три роли. STAFF требует активного рабочего профиля филиала, связанного с аккаунтом.
- Роль бренда действует во всех активных филиалах, включая новые. Прямая роль добавляет права. STAFF-профиль не ограничивает права унаследованного MANAGER или OWNER.
- Платформенный ADMIN имеет административный доступ. Бизнес-валидация и защита других платформенных ADMIN сохраняются.

| Область | Правило |
| --- | --- |
| B | Управление брендом; требуется назначение на бренд. |
| G | Общие данные бренда; подходят права назначения на бренд или его филиал. |
| L | Операции конкретного филиала; учитываются брендовые и прямые локальные права. |
| B/L | Проверяется целевая область назначения/политики. |

Принадлежность ID проверяет владелец домена независимо от permissions. Локальная роль не открывает операции соседнего филиала. Изменение общего каталога G отражается во всём бренде.

## 3. Свои записи и календарь

`booking.read` и `booking.manage` сохраняют полный доступ к филиалу. Новые `booking.read.own` и `booking.manage.own` не разрешают ручное создание.

Для STAFF достаточно хотя бы одного BookingItem со своим staffId, чтобы читать и управлять всей записью. Это включает услуги коллег: подтверждение, перенос, изменение исполнителей, неявку, отмену незавершённого визита и завершение. Отдельные статусы услуг не вводятся. После передачи всех услуг другим сотрудникам доступ прекращается.

Завершение проводит услуги и начисляет заработок всем исполнителям существующим способом; `order.manage` для этого не требуется. STAFF не редактирует завершённый визит и не может сторнировать его отменой или сменой статуса: для сторнирования требуется `order.return`. Удаление остаётся только у OWNER. Цены и продажи закрыты отдельными правами.

Обязательный фильтр участия применяется в БД до пагинации, сортировки по цене, JSON-выгрузки и подсчёта количества. Он пересекается с пользовательскими фильтрами. Карточки и изменения проверяют участие после загрузки документа. Транзакционная проверка версии записи отклоняет конкурентное переназначение между проверкой доступа и записью.

В календаре STAFF сервер принудительно выбирает его профиль. Общие блокировки (`staffId = null`) и собственные блокировки сохраняются. Прямой запрос чужого события запрещён. Для исключения событий редактируемого визита из доступных слотов проверяется участие. Доступность коллег для переназначения остаётся доступной; записи коллег она не открывает.

Владелец может включить STAFF `booking.read` на бренд или филиал: это открывает весь календарь и полные карточки записей филиала, включая контакты клиентов. `booking.manage.own` продолжает ограничивать изменения участием. Общие права редактирования STAFF не настраиваются.

`GET /locations/:locationId/staff/directory` возвращает ID, имя, должность и статус коллег для выбора исполнителя. Контакты, ИНН и сведения о выплатах в справочник не входят. Полный кадровый список и карточки коллег STAFF закрыты.

## 4. Клиенты, личные результаты и начисления

`client.read` у STAFF по умолчанию выключен и настраивается только на уровне бренда. Включение открывает всю клиентскую базу бренда: список, поиск и полные карточки с заметками и причиной бана. Это не выдаёт прав редактирования, импорта, экспорта или бана. MANAGER и OWNER сохраняют чтение.

Без `client.read` контакты доступны внутри разрешённых записей; поиск по имени, телефону и email выполняется через список этих записей. MANAGER продолжает выбирать клиентов при ручном создании. Автоматический поиск/создание клиента по телефону при разрешённом ручном или публичном создании сохраняется.

Собственный staffId клиент получает из `GET /users/me/access`. `staff.read.own` разрешает собственную карточку и смены; `payroll.read.own` — собственные начисления в списке и по ID сотрудника. Подстановка чужого ID не расширяет доступ. Общие периоды, ведомости, условия оплаты и зарплатные экспорты STAFF закрыты.

Аналитика записей принимает `booking.read.own`, принудительно устанавливая собственный staffId. Показатели и суммы считаются по услугам мастера. Включение `booking.read` не открывает общую аналитику. Другие аналитические разделы требуют управленческих permissions.

## 5. Проверки и наследование

Permissions вычисляются при выпуске/обновлении JWT. Overrides: встроенное значение → шаблон бренда → локальный шаблон для L/B-L. Наследуемые и прямые источники складываются; локальный DENY не отзывает независимый брендовый источник. Персональных overrides нет.

`@Permissions(A, B)` требует оба права; `@Permissions([A, B])` принимает любое из них. Guard проверяет claims и область. Контроллеры вызывают компактные BookingAccessService / StaffAccessService; сервисы бизнес-операций не получают JWT. StaffService разрешает активный профиль своего домена. При отсутствии профиля собственный доступ закрывается.

Существующие DTO записей не маскируются по ролям. Общие финансовые и кадровые endpoints закрыты; собственная карточка содержит собственные реквизиты. Публичные endpoints и клиентские токены имеют отдельные сценарии. Системное автозавершение и начисления сохраняют существующие правила и аудит.

## 6. Развёртывание

Миграция `20261018130000_staff_own_access` переносит прежние overrides booking.read/manage в own-права с сохранением приоритета бренда и филиала, удаляет недопустимые STAFF overrides и overrides payroll.manage. Явно включённое чтение всех записей сохраняется. Revision политик и tokenEpoch повышаются атомарно; старые access JWT требуют refresh.

Применение: `npm run db:deploy`, затем сборка/запуск совместимой версии backend. Автоматическое повышение STAFF до MANAGER не выполняется: сотрудникам с административными обязанностями владелец явно назначает MANAGER. Миграция меняет данные доступа, схему записей и расчётов не меняет.
