# Роли, permissions и области доступа

В обозначениях ниже `claim:read` / `claim:write` двоеточие отделяет действие от ключа. В API это отдельные поля `claim` и `access`; в JWT — карта `claim → read | write | readWrite`. Точки группируют имена, но не выдают дочерние права.

Модель backend на 2026-10-19. Реестр содержит 41 claim и 53 пары claim/access. [Карта API](./rbac-permissions-map.md), [контракты управления доступом](./rbac-contracts.md). Defaults ролей — [ROLE_BAGS](../../src/modules/access/constants/role-bags.ts). Источники правил — [реестр](../../src/modules/access/constants/permission-registry.ts) и [вычислитель claims](../../src/modules/access/calculators/permission.calculator.ts).

## 1. Роли и области

- `STAFF` — мастер: свои записи, смены, результаты визитов и начисления.
- `MANAGER` — администратор/управляющий: работа филиала, клиенты, продажи, графики, склад, отчёты и возвраты.
- `OWNER` — владелец: все действия своей области, настройки, доступы и финансовые решения. `payroll:write` доступен только OWNER.
- OWNER может назначать других владельцев, но не снимать и не понижать их (`403 ACCESS_OWNER_PROTECTED`); это правило действует в бренде и филиале. Самостоятельный выход разрешён, если бренд сохраняет хотя бы одного владельца. Принудительное изменение выполняет платформенный ADMIN.
- В бренде назначаются OWNER/MANAGER, в филиале — все три роли. STAFF требует активного рабочего профиля филиала, связанного с аккаунтом.
- Роль бренда действует во всех активных филиалах, включая новые. Прямая роль добавляет права. STAFF-профиль не ограничивает права унаследованного MANAGER или OWNER.
- Платформенный ADMIN получает глобальный claim `permissions: { "*": ["*"] }` при выпуске JWT. Проверки доступа используют permissions; сама роль ADMIN не разрешает операцию. Бизнес-валидация и защита других платформенных ADMIN сохраняются.

| Область | Правило |
| --- | --- |
| B | Управление брендом; требуется назначение на бренд. |
| G | Общие данные бренда; подходят права назначения на бренд или его филиал. |
| L | Операции конкретного филиала; учитываются брендовые и прямые локальные права. |
| B/L | Проверяется целевая область назначения/политики. |

Принадлежность ID проверяет владелец домена независимо от permissions. Локальная роль не открывает операции соседнего филиала. Изменение общего каталога G отражается во всём бренде.

## 3. Свои записи и календарь

`booking:read` и `booking:write` сохраняют полный доступ к филиалу. Новые `booking.own:read` и `booking.own:write` не разрешают ручное создание.

Для STAFF достаточно хотя бы одного BookingItem со своим staffId, чтобы читать и управлять всей записью. Это включает услуги коллег: подтверждение, перенос, изменение исполнителей, неявку, отмену незавершённого визита и завершение. Отдельные статусы услуг не вводятся. После передачи всех услуг другим сотрудникам доступ прекращается.

Завершение проводит услуги и начисляет заработок всем исполнителям существующим способом; `order:write` для этого не требуется. STAFF не редактирует завершённый визит и не может сторнировать его отменой или сменой статуса: для сторнирования требуется `order.return:write`. Удаление остаётся только у OWNER. Цены и продажи закрыты отдельными правами.

Обязательный фильтр участия применяется в БД до пагинации, сортировки по цене, JSON-выгрузки и подсчёта количества. Он пересекается с пользовательскими фильтрами. Карточки и изменения проверяют участие после загрузки документа. Транзакционная проверка версии записи отклоняет конкурентное переназначение между проверкой доступа и записью.

В календаре STAFF сервер принудительно выбирает его профиль. Общие блокировки (`staffId = null`) и собственные блокировки сохраняются. Прямой запрос чужого события запрещён. Для исключения событий редактируемого визита из доступных слотов проверяется участие. Доступность коллег для переназначения остаётся доступной; записи коллег она не открывает.

Владелец может включить STAFF `booking:read` на бренд или филиал: это открывает весь календарь и полные карточки записей филиала, включая контакты клиентов. `booking.own:write` продолжает ограничивать изменения участием. Общие права редактирования STAFF не настраиваются.

`GET /locations/:locationId/staff/directory` возвращает ID, имя, должность и статус коллег для выбора исполнителя. Контакты, ИНН и сведения о выплатах в справочник не входят. Полный кадровый список и карточки коллег STAFF закрыты.

## 4. Клиенты, личные результаты и начисления

`client:read` у STAFF по умолчанию выключен и настраивается только на уровне бренда. Включение открывает всю клиентскую базу бренда: список, поиск и полные карточки с заметками и причиной бана. Это не выдаёт прав редактирования, импорта, экспорта или бана. MANAGER и OWNER сохраняют чтение.

Без `client:read` контакты доступны внутри разрешённых записей; поиск по имени, телефону и email выполняется через список этих записей. MANAGER продолжает выбирать клиентов при ручном создании. Автоматический поиск/создание клиента по телефону при разрешённом ручном или публичном создании сохраняется.

Собственный staffId клиент получает из `GET /users/me/access`. `staff.own:read` разрешает собственную карточку и смены; `payroll.own:read` — собственные начисления в списке и по ID сотрудника. Подстановка чужого ID не расширяет доступ. Общие периоды, ведомости, условия оплаты и зарплатные экспорты STAFF закрыты.

Аналитика записей принимает `booking.own:read`, принудительно устанавливая собственный staffId. Показатели и суммы считаются по услугам мастера. Включение `booking:read` не открывает общую аналитику. Другие аналитические разделы требуют управленческих permissions.

## 5. Проверки и наследование

Permissions вычисляются при выпуске/обновлении JWT. Overrides: встроенное значение → шаблон бренда → локальный шаблон для L/B-L. Наследуемые и прямые источники складываются; локальный DENY не отзывает независимый брендовый источник. Персональных overrides нет.

Управление доступами мастеров (`access.staff:write`) зависит от чтения сотрудников (`staff:read`) в том же филиале. OWNER/MANAGER всегда имеют это чтение, оно не настраивается. Управление рабочими профилями (`staff:write`) остаётся отдельным разрешением: его можно отключить, сохранив список сотрудников и управление приглашениями.

`@Permissions(A, B)` требует оба права; `@Permissions([A, B])` принимает любое из них. Guard проверяет claims и область. Контроллеры вызывают компактные BookingAccessService / StaffAccessService; сервисы бизнес-операций не получают JWT. StaffService разрешает активный профиль своего домена. При отсутствии профиля собственный доступ закрывается.

Существующие DTO записей не маскируются по ролям. Общие финансовые и кадровые endpoints закрыты; собственная карточка содержит собственные реквизиты. Публичные endpoints и клиентские токены имеют отдельные сценарии. Системное автозавершение и начисления сохраняют существующие правила и аудит.

## 6. Развёртывание

Миграция `20261019120000_claim_access` переносит существующие overrides в отдельные поля claim/access, сохраняя ALLOW/DENY и независимое наследование каждого действия. Повышает revision/tokenEpoch. Новые JWT содержат `permissionsVersion: 2`; старый формат требует refresh.

Применение: `npm run db:deploy`, `npm run db:generate`, `npm run build`. Frontend необходимо обновить под карты claim/access и новые поля политик. Миграция не меняет назначения ролей, участие в записях и бизнес-ограничения.

## 7. Добавление прав

Добавить ключ в [Claim](../../src/modules/access/enums/claim.enum.ts), допустимые read/write, scope, настраиваемые роли и зависимости — в реестр. Явно добавить defaults нужным ролям в ROLE_BAGS через Read/Write/ReadWrite. На endpoint использовать `@Permissions(Read(Claim.BOOKING))` или `@Permissions(Write(Claim.BOOKING))`. Несколько аргументов требуют все права, массив аргумента — любое из них. Для own дополнительно проверяется участие или собственный профиль в доменном сервисе.

ReadWrite объединяет два действия одного claim. Например, booking:readWrite не включает booking.delete:write или booking.export:read. При новой операции не появляются неявные разрешения по родительскому ключу.
