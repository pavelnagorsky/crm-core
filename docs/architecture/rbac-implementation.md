# RBAC: итог реализации

Состояние на 2026-10-16, после ревью и упрощения. Это сводка реализованного backend. Frontend и применение миграции к рабочей БД остаются отдельными шагами.

## Что изменилось для бизнеса

Роли остались фиксированными: `OWNER`, `MANAGER`, `STAFF`. Теперь роль даёт готовый набор permissions — разрешений на конкретные действия. Ничего настраивать при начале работы не требуется. Владелец может изменить отдельные разрешённые настройки шаблонов `MANAGER` и `STAFF`; произвольных ролей и персональных наборов прав нет.

| Роль | Область и основные возможности |
| --- | --- |
| Платформенный `ADMIN` | Доступ ко всем областям, административная замена владельца бренда. Не может менять доступ другого платформенного администратора. |
| `OWNER` бренда | Полный доступ к бренду и его филиалам, управление участниками и настройками прав. |
| `OWNER` филиала | Полный доступ к своему филиалу, управление его участниками. Не управляет настройками бренда и соседними филиалами. |
| `MANAGER` | Операционная работа, услуги, цены, возвраты, персонал. Может управлять STAFF в своей области, но не назначать MANAGER/OWNER и не менять настройки бренда/филиалов. |
| `STAFF` | Только назначение на филиал, связанное с активным профилем сотрудника. По умолчанию доступны календарь, записи, продажи, возвраты и аннулирование заказов. Настройки бизнеса, каталог товаров, зарплаты и управление доступами закрыты. |

Точная матрица, включая склад, экспорт и исключения для отдельных действий: [rbac-target.md](./rbac-target.md).

Роль бренда наследуется всеми его активными филиалами. Прямая локальная роль добавляет права: `MANAGER` бренда + `OWNER` филиала А означает права владельца в А и управляющего в остальных филиалах. Локальная настройка не отнимает права, полученные от роли бренда. Для локальных назначений сначала применяются настройки шаблона бренда, затем настройки филиала.

Клиенты и общий каталог товаров доступны для чтения всем участникам соответствующего бренда, в том числе с одной локальной ролью. Это не открывает операции соседних филиалов. Редактирование общего каталога по умолчанию доступно OWNER, включая локального; управление размещением и настройками товара в своём филиале — также MANAGER.

Авторизация относится к действию над документом целиком. Ответственный за документ не добавлен, принадлежность строк сотруднику не проверяется. Разрешение на возврат действует и для смешанного заказа с несколькими продавцами.

## Как проверяется запрос

```mermaid
flowchart LR
  Login[Вход или refresh] --> Compile[Загрузка назначений и настроек]
  Compile --> JWT[JWT: роли, scoped permissions, tokenEpoch]
  JWT --> Signature[Проверка подписи]
  Signature --> Epoch[Проверка tokenEpoch через кэш]
  Epoch --> Guard[Permissions: проверка claims]
  Guard --> Controller[Контроллер: условия конкретного действия]
  Controller --> Service[Сервис: бизнес-правила и сохранение]
```

В реестре зафиксированы 58 permissions. В подписанном JWT они сгруппированы по ключам:

| Ключ | Значение |
| --- | --- |
| `B:<brandId>` | Действия на уровне бренда: например, изменение его настроек. |
| `G:<brandId>` | Общие данные бренда: например, клиентская база и каталог товаров. |
| `L:<locationId>` | Действия конкретного филиала: записи, продажи, склад и другие операции. |

`@Permissions(Permission.ORDER_RETURN)` проверяет готовое разрешение из JWT для области маршрута. При нескольких permissions нужны все перечисленные. Обычная проверка доступа не загружает роли и настройки из БД. Запросы за самими заказами, записями и прочими бизнес-данными выполняются как обычно.

После изменения доступа повышается `tokenEpoch` затронутых пользователей в существующем кэше. Старый JWT получает `409 TOKEN_PAYLOAD_STALE` с действием `REFRESH_ACCESS_TOKEN`; после refresh клиент получает актуальные claims. Старые токены без поля `permissions` тоже требуют refresh. Инвалидация выполняется после успешного commit. Изменение шаблона инвалидирует токены участников бренда; создание филиала — токены брендовых участников.

Актуальные полномочия повторно читаются из БД внутри транзакций управления доступами и принятия приглашений. Это защищает выдачу ролей, проверку полномочий автора приглашения и последнего владельца. Предпросмотр приглашения также проверяет текущие полномочия автора.

## Где остались условные проверки

Основное разрешение задаётся декоратором. Контроллер проверяет дополнительные условия: например, немедленное проведение продажи требует `order.confirm`, изменение произвольной цены — `sale.price.override`, перемещение товара — доступа к обоим филиалам.

Если решение зависит от сохранённого документа, контроллер загружает его через владеющий сервис и проверяет права. Сервис получает этот документ и сверяет его состояние под транзакционной блокировкой. Если запись или складской документ успели измениться, операция возвращает конфликт, а не выполняется по устаревшей проверке.

Сервисы бронирований, заказов и склада не получают JWT для проверки permissions. В отдельных расчётных сценариях оставлены конкретные флаги:

- `canOverridePrice` — можно ли менять сохранённую произвольную цену; её сравнение выполняется при обработке заказа.
- `canCreateClient` — можно ли создать отсутствующего клиента при ручной записи. Если нельзя, разрешено использовать существующего клиента.
- `canComplete` — можно ли создать уже завершённую walk-in запись. Начальный статус зависит от рассчитанного времени окончания.

Эти значения вычисляет контроллер из claims. Они не содержат ролей или токена. Допустимые переходы статусов, остатки и принадлежность объектов филиалу остаются бизнес-проверками. `AuditActorRole` используется для аудита, а не для решения о доступе.

## Назначения, настройки и приглашения

Создатель бренда получает первое назначение OWNER в транзакции создания. Совладельцев может быть несколько; удалить или понизить последнего OWNER бренда нельзя. При смене роли проверяется право управлять и прежней, и новой ролью. Поэтому MANAGER не может сначала понизить OWNER до STAFF, а затем удалить его.

Добавление участника проходит через единое приглашение, даже если аккаунт уже существует:

1. OWNER или MANAGER выбирает допустимые роли и области. Для STAFF указывает профиль сотрудника филиала.
2. Backend выдаёт ссылку со случайным токеном; в БД хранится только его хеш. Срок — 7 дней. Отправка письма необязательна.
3. Человек регистрируется или входит и принимает приглашение. Backend заново проверяет автора и назначения, затем атомарно выдаёт весь набор ролей.
4. Повторное принятие тем же аккаунтом не выдаёт роли заново и не восстанавливает отозванный доступ. Перевыпуск ссылки делает предыдущий токен недействительным.

Отзыв STAFF-назначения освобождает связь с профилем. Деактивация сотрудника отзывает его STAFF-доступ и ожидающие приглашения на этот профиль; самостоятельные назначения OWNER/MANAGER сохраняются. Профиль сотрудника без аккаунта по-прежнему можно использовать в операционной работе.

Настройки хранятся как overrides: `ALLOW`, `DENY`, `INHERIT`. Последнее удаляет override. Шаблон OWNER не редактируется; недопустимые настройки и нарушенные зависимости отклоняются. `AccessState.revision` защищает изменения политик и назначений от перезаписи параллельным запросом. Это версия редактируемых данных, отдельная от `tokenEpoch` пользователя.

Основные API:

| Путь | Назначение |
| --- | --- |
| `GET /users/me/access` | Прямые и наследуемые роли, permissions, связанные `staffId`, признак платформенного ADMIN. |
| `/brands/:brandId/access/policies`, `/locations/:locationId/access/policies` | Чтение и изменение шаблонов; сброс через `DELETE .../:role/overrides`. |
| `/brands/:brandId/access/memberships`, `/locations/:locationId/access/memberships` | Список назначений; изменение и отзыв через `PATCH`/`DELETE .../:membershipId`. |
| `/brands/:brandId/access/invitations` | Создание и список приглашений; перевыпуск и отзыв по ID. |
| `POST /access/invitations/preview`, `POST /access/invitations/accept` | Предпросмотр ссылки и принятие после входа. |
| `POST /admin/brands/:brandId/owner-replacement` | Административная замена владельца с указанием причины. |

Тела запросов, ответы и точные методы: [rbac-contracts.md](./rbac-contracts.md). Старые маршруты staff-приглашений сохранены как адаптеры к единому механизму.

## Что убрано и зачем остались изменения сервисов

Удалены старые RBAC guards/decorators и вспомогательные проверки ролей. `AccessSession` и `AccessContext` не используются. Убраны `resolveAccessBrands` / `resolveAccessLocations`, зависимости Auth от Brand/Location и повторная загрузка назначений при сборке claims. Пользовательский ответ мапится в DTO без промежуточной искусственной Prisma-модели. Убраны неиспользуемые зависимости и лишняя перестановка импортов.

Оставшиеся компоненты имеют конкретные задачи:

| Компонент | Ответственность |
| --- | --- |
| [AuthService](../../src/modules/auth/auth.service.ts) | Выпуск JWT с ролями, permissions и epoch. |
| [PermissionGuard](../../src/modules/auth/guards/permission.guard.ts) | Проверка готовых claims без БД. |
| [AccessService](../../src/modules/access/access.service.ts) | Загрузка назначений и настроек для claims, операции первого OWNER и отзыва STAFF, блокировка и журнал изменений доступа. |
| [PermissionComputeService](../../src/modules/access/services/permission-compute.service.ts) | Чистое вычисление defaults, overrides, зависимостей и объединения источников; приватен для AccessModule. |
| [AccessAdministrationService](../../src/modules/access/services/access-administration.service.ts) | Правила управления ролями, политиками и приглашениями. |
| [AccessManagementService](../../src/modules/access-management/access-management.service.ts) | Объединение операций доступа с Brand/Location/Staff/User в транзакции, уведомления и инвалидация токенов. |

BrandService вызывает AccessService для назначения первого OWNER, StaffService — для отзыва доступа при деактивации/удалении. Эти зависимости нужны для изменения назначений, а не для авторизации обычных операций. В остальных операционных сервисах изменения связаны с конкретными флагами, аудитом и защитой от конкурентного изменения документов.

При ревью исправлена проверка филиала назначения складского перемещения: ранее сервис ожидал токен, который контроллер уже не передавал. Проверки перенесены в контроллер. Удаление используемого файла также запрещено через FK Restrict, чтобы через медиатеку нельзя было косвенно изменить защищённую карточку.

## Подключение и проверенное состояние

Frontend должен использовать `GET /users/me/access` для навигации, сохранять токен приглашения через регистрацию/вход и выполнять refresh после `TOKEN_PAYLOAD_STALE`. Поля существующих ответов не маскируются по ролям: STAFF может получить себестоимость заказа и кадровые поля через разрешённые API; ограничение страниц выполняется в UI, как согласовано.

Подготовлена [миграция](../../src/database/migrations/20261016120000_action_permissions/migration.sql). Она проверяет несовместимые данные: STAFF бренда, отсутствие OWNER активного бренда, STAFF без активного связанного профиля. Добавлена уникальность профиля пользователя внутри филиала. Старые непринятые staff-приглашения отзываются и требуют перевыпуска. Порядок применения описан в [контрактах](./rbac-contracts.md#10-подключение-и-миграция); рабочая БД не изменялась.

Текущий кэш epoch находится в процессе приложения. Для нескольких экземпляров backend потребуется согласованное общее хранилище версий. При изменении встроенных defaults уже выданные JWT сами не пересчитываются: нужна инвалидация токенов.

Результаты проверки после итогового рефакторинга:

- 549 unit-тестов и 17 интеграционных тестов на отдельном локальном PostgreSQL прошли.
- Сборка, линтер и `git diff --check` прошли.
- Все 184 прежних API-маршрута сохранены; всего стало 204, без дублирующихся маршрутов.
- Проверены отсутствие загрузки прав на обычном API-запросе, наследование и объединение ролей, отзыв при действующем JWT, приглашения, последний OWNER, доступ к обоим филиалам перемещения и конкурентное изменение записи.

Эти результаты относятся к реализации на указанную дату; при изменении кода проверки нужно повторить.
