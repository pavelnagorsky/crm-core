# Подтверждение записей и уведомления: инструкция для фронтенда

Бэкенд готов: изменилось поведение подтверждения записей и писем клиентам и сотрудникам. Документ описывает, что поменялось в API и что нужно на экранах. Почему так решено — [booking-notifications-plan.md](./booking-notifications-plan.md). Полный контракт — Swagger (`/api`, `/api-json`). Ответы, как обычно, обёрнуты в `BaseResponseDto`.

## Коротко

- Подтверждение записи — решение салона. Оно действует только на онлайн-записи. Запись, созданная администратором, всегда сразу подтверждена.
- Неподтверждённая заявка (`PENDING`) не завершается автоматически, по ней нет напоминания, заказа и начисления мастеру. Если время визита прошло, а заявку никто не подтвердил, она остаётся `PENDING`, пока её не закроют вручную.
- Письма клиенту о создании и переносе записи администратором уходят **через 2 минуты**: за это время ошибку можно исправить, и клиент ничего не получит.
- Менеджеры филиала и мастера записи получают письма о новых онлайн-записях, заявках, отменах и переносах клиентом.

## 1. Настройки филиала

`GET` и `PUT /locations/:locationId` — новое поле:

| Поле | Подпись | По умолчанию |
| --- | --- | --- |
| `notifyClientOnStaffChanges: boolean` | «Сообщать клиенту о записях, созданных или перенесённых администратором» | `true` |

Подсказка под переключателем: «Клиент получит письмо о новой записи или новом времени. Письмо уходит через 2 минуты — если вы ошиблись, исправьте запись, и клиент ничего не получит. Работает, если у клиента указан email».

У существующего `isBookingConfirmationRequired` поменялся смысл, подсказку нужно обновить: «Онлайн-записи сначала попадают в заявки. Салон связывается с клиентом и подтверждает запись. Записи, созданные администратором, подтверждаются сразу».

## 2. Создание записи администратором

`POST /locations/:locationId/bookings/manual` — новое необязательное поле `notifyClient: boolean`.

- В форме — чекбокс «Уведомить клиента». Значение по умолчанию — `notifyClientOnStaffChanges` филиала.
- Чекбокс показывать, только если у клиента есть email. Без email письма не будет в любом случае, поле можно не передавать.
- Не передали поле — бэкенд берёт настройку филиала.
- Снятая галочка действует на всю запись: по ней не будет ни письма о создании, ни писем о переносе. Напоминание, письма об отмене и подтверждении это не затрагивает.
- Запись всегда создаётся `CONFIRMED`, даже если у филиала включено подтверждение. Исключение — запись задним числом со своим временем: она сразу `COMPLETED`, писем по ней нет.

Ответ поменялся: раньше `{ id }`, теперь

```ts
{
  id: string;
  clientNotice: { type: 'CREATED' | 'RESCHEDULED'; sendAt: string } | null; // UTC
}
```

`clientNotice !== null` — клиенту уйдёт письмо в `sendAt`. Тост: «Запись создана, клиенту придёт письмо». При `null` — просто «Запись создана». Правила, когда письма не будет (нет email, галочка снята, запись в прошлом), фронтенд у себя не повторяет — достаточно смотреть на `clientNotice`.

## 3. Редактирование и перетаскивание

`PUT /locations/:locationId/bookings/:id` — новых полей в запросе нет, переключателей в форме и при перетаскивании не нужно. Письмо о переносе уходит по настройке филиала и выбору при создании записи.

Ответ поменялся так же: `{ id, clientNotice }`.

После переноса:
- `clientNotice !== null` → тост «Перенесено на 15:00, клиенту придёт письмо · Отменить»;
- `clientNotice === null` → «Перенесено на 15:00 · Отменить».

«Отменить» — обычный `PUT` с прежним временем (и прежними назначениями мастеров, если их меняли). Отдельного эндпоинта нет: возврат на исходное время сам снимает письмо.

Как ведёт себя письмо за 2 минуты:

| Что сделали | Что получит клиент |
| --- | --- |
| Перетащили несколько раз подряд | Одно письмо: «Было» — время до первого переноса, «Стало» — итоговое |
| Вернули на исходное время | Ничего |
| Поменяли только мастера, услугу или цену | Ничего |
| Перенесли запись, созданную меньше 2 минут назад | Одно письмо о создании с итоговым временем |
| Отменили запись, созданную меньше 2 минут назад | Ничего — ни о создании, ни об отмене |

Ошибки не изменились. `409 BOOKING_CONCURRENT_UPDATE` — запись изменили в другом окне, нужно перечитать её. Отправка отложенных писем и напоминаний эту ошибку больше не вызывает: форму, открытую сразу после создания записи, можно сохранить и через 2 минуты.

## 4. Карточка записи

`GET /locations/:locationId/bookings/:id` и списки возвращают два новых поля:

| Поле | Смысл |
| --- | --- |
| `notifyClient: boolean` | Пишет ли администратор клиенту по этой записи. Ставится при создании, потом не меняется |
| `clientNotice: { type, sendAt } \| null` | Письмо, которое ещё ждёт отправки |

Показывать необязательно. Если захочется — строка «Клиенту уйдёт письмо в 15:02» в карточке.

## 5. Заявки и просроченные заявки

- Список «Ждут подтверждения» — обычный поиск записей с `status=PENDING`, без ограничения по датам.
- Просроченная заявка: `status === 'PENDING'` и `endAt` в прошлом. Отдельного статуса нет — подсветить в списке и календаре, например «Не подтверждена, время прошло».
- Действия по просроченной заявке — смена статуса через `PATCH .../status`:
  - «Клиент пришёл» → `COMPLETED`: заказ, начисление мастеру и просьба об отзыве появятся в этот момент;
  - «Не пришёл» → `NO_SHOW`;
  - «Отменить» — обычная отмена.
- Виджет `PENDING_CONFIRMATION` на дашборде считает заявки в выбранном периоде, включая просроченные. Отдельного числа просроченных нет.

## 6. Публичная запись

Экран успеха при `booking.status === 'PENDING'`: «Заявка принята. Салон свяжется с вами, чтобы подтвердить запись». У большинства клиентов нет email, поэтому этот экран — единственное, что они увидят до звонка салона.

## 7. Письма сотрудникам

Кнопка «Открыть запись» в письме ведёт на `/app/locations/:locationId/bookings/:bookingId` — существующий маршрут `crm-frontend`. Если маршрут поменяется, сообщите бэкенду: ссылка собирается на сервере.

Кто получает: менеджеры филиала (назначенные на филиал или на весь бренд) и мастера записи с привязанным аккаунтом, если у них есть право видеть записи. Владелец бренда писем не получает. Отписки пока нет.
